## 19. Field, Custom-Field and Reporting-Tag Mapping

This section answers one question precisely: **where does the CAPEX code, the WBS code and the budget head actually live inside a Zoho ERP record?** Every downstream control — commitment recognition, actual CWIP attribution, availability checking, reconciliation and capitalisation — depends on that answer being unambiguous and machine-readable.

The answer is constrained, not chosen freely. Zoho ERP offers exactly three carriers at line level, and the set of carriers available differs by document type. §19.2 states which carriers exist where; §19.3 makes the assignment and defends it; §19.4 states the manual prerequisites that must be completed in the Zoho ERP user interface before any of it works.

### 19.1 The binding rule: line level only

**Every CAPEX, WBS and budget-head mapping in this design is defined at line-item level. Header-level mapping is prohibited.**

The reason is a single evidenced asymmetry: a bill **header** carries no `project_id`, while a bill **line** does. If coding were carried at header level, it would be lost on the one document that creates Actual CWIP. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

The full evidence, per document, per level:

| Document | Header coding fields | Line coding fields | Line carries a link to the PO line? |
|---|---|---|---|
| Purchase Order | `tags`, `custom_fields`, `location_id`, `crm_custom_reference_id`, `delivery_customer_id`, `is_update_customer` | `project_id`, `tags`, `item_custom_fields`, `account_id`, `location_id`, `line_item_category`, `hsn_or_sac`, `tax_id`, `tds_tax_id`, `unit`, `quantity`, `rate` | not applicable (it is the PO) |
| Bill | `tags`, `custom_fields`, `location_id`, `purchaseorder_ids` — and **no `project_id`** | `project_id`, `tags`, `item_custom_fields`, `account_id`, `location_id`, `line_item_id`, **`purchaseorder_item_id`**, `is_billable`, `customer_id`, `serial_numbers` | **Yes — `purchaseorder_item_id`** |
| Purchase Receive | `custom_fields`, `receive_number`, `date`, `notes`; the PO link is header-level, returned as `purchaseorder_id` and `purchaseorder_number` | `line_item_id`, `item_id`, `name`, `description`, `item_order`, `quantity`, `unit` — **and nothing else** | **No** |
| Journal | `tags`, `custom_fields`, `location_id`, `reference_number`, `journal_type` | `project_id`, `tags`, `account_id`, `location_id`, `line_id`, `amount`, `debit_or_credit` — **and no custom field node of any kind** | not applicable |
| Fixed Asset | `tags`, `custom_fields`, `asset_account_id`, `fixed_asset_type_id`, `asset_purchase_date` | no lines | **No** — no `project_id`, no PO link, no bill link |

`[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

Three consequences follow immediately, and they drive the rest of this section:

1. **The PO-to-bill leg works.** A bill line carries `purchaseorder_item_id`, so commitment relief and double-count prevention can be executed against a documented field. This is the enabling fact for §22 Budget and Commitment Calculation Logic.
2. **The receipt leg does not.** A purchase-receive line carries neither a PO-line link nor any coding field. Received-but-unbilled exposure must be reconstructed by the Hub. See §24.5.
3. **A journal line cannot carry a custom field.** So whichever carrier is chosen for the WBS code must be usable on a journal line, or capitalisation postings become uncodeable. That single constraint decides §19.3.

### 19.2 The three available carriers

| Carrier | What it is | Available on PO line | Available on Bill line | Available on Journal line | Available on Purchase Receive line | Available on Fixed Asset | Definition creatable by API? |
|---|---|---|---|---|---|---|---|
| `project_id` | Foreign key to a Zoho ERP Project | Yes | Yes | Yes | No | No | Yes — `POST {BASE_V3}/projects` |
| Reporting tag option (`tags[]` with `tag_id` and `tag_option_id`) | A tenant-wide analytical dimension with a defined option list | Yes | Yes | Yes | No | Header field `tags` present in the create body | Yes — `POST {BASE_V3}/reportingtags` and `PUT {BASE_V3}/reportingtags/{tag_id}/options` |
| `item_custom_fields[]` | Line-level custom field values | Yes | Yes | **No** | No | Header `custom_fields` only | **No — definition cannot be created by API** |

`[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

Supporting evidence on reporting tags:

- A reporting tag's `preference` node supports `transaction` and `line_item`, so a tag can be applied at line level rather than only at document level. `[source: https://www.zoho.com/erp/api/v3/reporting-tags/ — verified 2026-08-05]`
- The taggable entity enumeration on the Reporting Tags page lists Sales, Purchases, Journal and Inventory Adjustment. `[source: https://www.zoho.com/erp/api/v3/reporting-tags/ — verified 2026-08-05]` Purchases and Journal are the two families this design needs.
- Reporting tags are described on the Purchase Order page as organising and filtering data across reports for detailed analysis. `[source: https://www.zoho.com/erp/api/v3/purchase-order/ — verified 2026-08-05]`
- The Fixed Asset create body carries `tags`. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` However, whether a reporting tag can be **defined** with a fixed asset as its entity — that entity name is not in the enumeration quoted above — is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. The capitalisation design in §27.4 does not depend on it being true.

Supporting evidence on custom fields:

- There is no endpoint anywhere in the specification that creates a custom field **definition**. The only custom-field paths are value-setting paths on eight modules: `/bill/{bill_id}/customfields`, `/customerpayment/{customer_payment_id}/customfields`, `/estimate/{estimate_id}/customfields`, `/invoice/{invoice_id}/customfields`, `/item/{item_id}/customfields`, `/purchaseorder/{purchaseorder_id}/customfields`, `/salesorder/{salesorder_id}/customfields`, `/subscriptions/{subscription_id}/customfields`. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`
- Custom fields carry a `cf_`-prefixed API name, illustrated on the Tasks page by a field labelled Project Code with the API name `cf_project_code`. `[source: https://www.zoho.com/erp/api/v3/tasks/ — verified 2026-08-05]`
- Custom field index is capped: the Contacts page documents that the index can hold any value from 1 to 10. `[source: https://www.zoho.com/erp/api/v3/contacts/ — verified 2026-08-05]` Whether the same cap of ten applies to line-level `item_custom_fields` on Purchase Orders and Bills is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**; the design below uses two line custom fields, well inside any such cap.

### 19.3 Carrier assignment and the reasoning

| Business dimension | Carrier | Zoho path | Cardinality | Why this carrier |
|---|---|---|---|---|
| **CAPEX code** (Hub `Project.capex_code`, illustrative form `CAPEX-2026-001`) | `project_id` | `line_items[].project_id` on PO, Bill and Journal | One Zoho Project per Hub CAPEX Project | It is a first-class foreign key, filterable on `GET {BASE_V3}/bills?project_id=` and `GET {BASE_V3}/journals?project_id=`, and it survives on all three document families. It is also the only carrier Zoho's own project reporting understands |
| **WBS code** (Hub `WBS Element.wbs_code`) | Reporting tag option | `line_items[].tags[]` with `tag_id` = the WBS tag, `tag_option_id` = the element | One tag option per released WBS element | It is the **only** carrier available on all three of PO line, bill line and journal line. A custom field would work on PO and bill lines but would be unusable on the capitalisation journal, breaking traceability at exactly the point where CWIP becomes an asset |
| **Budget head** (Hub `Budget Head.code`) | Primary: `account_id`. Secondary: a second reporting tag option | `line_items[].account_id`, plus `line_items[].tags[]` with `tag_id` = the budget-head tag | One CWIP-family general-ledger account per budget head, plus one tag option per budget head | The budget head is a spending category, which is what a general-ledger account is. Binding it to `account_id` makes the Hub's Actual CWIP agree with the Zoho trial balance by construction. The parallel tag option exists so that a head can be reported on documents where the account is a control account rather than the head |
| **Hub line key** (opaque back-reference) | `item_custom_fields` | `line_items[].item_custom_fields[]` | One per line | Machine-readable echo of the Hub `PO Line.id`, so a returned document can be matched back without string parsing. Not available on journals; there the `reference_number` header carries the Hub key instead |
| **Plant** (Hub `Plant`) | `location_id` | header `location_id` and `line_items[].location_id` | One Zoho Location per Hub Plant | Native concept, present at both levels |
| **Hub document reference** (PR number, capitalisation request number) | Header `reference_number` plus a header custom field | header `reference_number`, header `custom_fields[]` | One per document | `reference_number` is filterable on the bill, journal and vendor-credit list endpoints, which makes it the pre-flight idempotency lookup key of §18.8 Mechanism B |

**The decisive argument, stated plainly.** Three carriers exist. Only one of them — the reporting tag — is present on a PO line, a bill line **and** a journal line. Because the CWIP-to-asset transfer is a journal, and because that journal must be attributable to the WBS element whose CWIP it is clearing, the WBS code must be a reporting tag. Anything else leaves the capitalisation posting uncoded and makes §27.4 unreconcilable.

**Provenance note.** The WBS layer itself is `provenance=MASTER-PROMPT`. The client PDF contains no WBS hierarchy at all — its budget structure is CAPEX/CWIP project code plus budget head only (CONF-02). A tenant that does not adopt WBS still works: the WBS tag is simply left unpopulated, and control operates at project plus budget head exactly as the client document describes. The carrier assignment above degrades cleanly to two dimensions.

### 19.4 Manual prerequisites — no API can do these

**There is no API to create a custom field definition.** `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` Therefore the following must be created by a Zoho ERP administrator in the Zoho ERP user interface, per organisation, **before** the connector's first sync. They are a go-live gate, not a nice-to-have: the connection test in §14 Zoho ERP Connector Setup Module fails closed if any of them is absent.

| # | Prerequisite | Where it is created | What the connector does afterwards | Blocks what if missing |
|---|---|---|---|---|
| 1 | Reporting tag named for the WBS dimension, `preference` set to `line_item`, associated with the Purchases and Journal entities | Zoho ERP UI, reporting-tag settings | Discovers it via `GET {BASE_V3}/reportingtags` and stores `tag_id` in `Field Mapping` | All WBS attribution; the Hub falls back to project plus budget head |
| 2 | Reporting tag named for the budget-head dimension, same preference and entities | Zoho ERP UI | Same discovery | Budget-head attribution on documents that post to a control account |
| 3 | Line-level custom field on Purchase Order holding the Hub line key | Zoho ERP UI | Discovers `customfield_id`; writes values into `line_items[].item_custom_fields[]` | Idempotency Mechanism A on POs; the connector degrades to Mechanism B |
| 4 | Line-level custom field on Bill holding the Hub line key | Zoho ERP UI | Same | Bill-line back-matching falls back to `purchaseorder_item_id` only |
| 5 | Header custom field on Purchase Order holding the Hub Purchase Request reference | Zoho ERP UI | Used as `X-Unique-Identifier-Key` for upsert, and as the `custom_field` query parameter on `GET {BASE_V3}/purchaseorders` | Idempotency Mechanism A and the pre-flight lookup |
| 6 | Header custom field on Project holding the Hub CAPEX code | Zoho ERP UI | Used as `X-Unique-Identifier-Key` on `PUT {BASE_V3}/projects` | Project upsert; falls back to name matching, which is fragile |
| 7 | CWIP-family general-ledger accounts, one per budget head | Zoho ERP UI or `POST {BASE_V3}/chartofaccounts` — but see §18.7 action #16, which classifies Hub-side creation as NOT-RECOMMENDED | Discovers via `GET {BASE_V3}/chartofaccounts` and maps to `Budget Head` | Actual CWIP attribution and the trial-balance tie-out in §27 |
| 8 | Locations enabled, one per Plant | Zoho ERP UI; `POST {BASE_V3}/settings/locations/enable` exists but is an organisation-wide switch | Discovers via `GET {BASE_V3}/locations` | Plant-level reporting |
| 9 | An internal Contact per legal entity, to satisfy the mandatory `customer_id` on project creation | Zoho ERP UI | Referenced from Master Data Configuration (SCR-30) | Zoho Project creation, and therefore CAPEX-code carriage |

The Setup Wizard (SCR-31) presents this list as a checklist with a live pass or fail state per row, driven by discovery calls. A connection profile cannot be promoted out of Draft while any row fails. The user-facing message for a missing custom field is the `MSG-INT-001` pattern, naming the field rather than the scope.

> **Estimating note for the roadmap.** Nine manual configuration items, multiplied by the number of Zoho organisations, is the true onboarding cost of this integration. It is not automatable and must be shown as such in §41 Implementation Roadmap.

### 19.5 Reporting-tag option design

The WBS tag's option list is the projection of the Hub's WBS register into Zoho ERP. It is not a copy — it is a controlled subset.

**Option naming convention** (DERIVED-RECOMMENDATION):

```
<capex_code>.<wbs_path>  —  <wbs_name>
e.g.  CAPEX-2026-001.03  —  Plant and machinery
```

Rules:
1. Only WBS elements in status `Released` are published as tag options. Draft and Rejected elements are never published, because a tag option is visible to every Zoho user and implies it is a valid coding target.
2. Publication is APPROVAL-GATED (§18.7 action #3). A reporting tag is a tenant-wide dimension; uncontrolled growth pollutes every Zoho report, not only CAPEX reports.
3. An element that is closed or abandoned is marked inactive via `POST {BASE_V3}/reportingtags/{tag_id}/option/(\d+)/inactive`, never deleted. Deletion would orphan historical postings.
4. `is_tag_mandatory` should be set on the WBS tag for the Purchases entity so that a capital PO cannot be raised without a WBS code. Whether this flag can be scoped to capital documents only, rather than to all purchases in the organisation, is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** — and it matters, because making a tag mandatory on all purchases would obstruct routine operational buying. Until confirmed, the design leaves the flag off and enforces the requirement in the Hub with message `MSG-BUD-004`.

**Volume.** The proof-of-concept dataset is 3 projects × 11 illustrative WBS elements at 3 levels, which produces at most 33 WBS tag options plus 10 budget-head options. Whether Zoho ERP imposes a maximum option count per reporting tag is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**, and it is a live scaling question for a real estate of capital projects: a hundred projects at eleven elements each is 1,100 options on a single flat list. §42 Risk Register carries this.

**Structural limitation.** A reporting tag option list is flat. It expresses no parent-child relationship, so the WBS hierarchy exists only in the Hub. The `line_item_category` field on a PO line — allowed values `line_item`, `header` and `subtotal` — provides only a visual grouping inside the item table; a header row is not a parent node and carries no identifier relationship to the lines beneath it, so it cannot be used as a WBS roll-up. `[source: https://www.zoho.com/erp/api/v3/purchase-order/ — verified 2026-08-05]` Roll-up arithmetic is therefore always performed in the Hub, never read back from Zoho.

### 19.6 The custom-field schema inconsistency between Purchase Order and Bill

This is a concrete, evidenced trap for anyone writing a shared serializer.

| Document | Line custom-field key name | Sub-attributes present |
|---|---|---|
| Purchase Order line | `customfield_id` (no underscore) | `customfield_id`, `value` |
| Bill line | `custom_field_id` (with underscore) | `custom_field_id`, `index`, `value`, `label` |

`[source: https://www.zoho.com/erp/api/v3/purchase-order/ — verified 2026-08-05]` and `[source: https://www.zoho.com/erp/api/v3/bills/ — verified 2026-08-05]`

**Rule for the coding agent.** Do not share one serializer between PO lines and bill lines. Implement two adapters behind one interface, driven by a per-module descriptor held in the `Transformation Rule` entity:

```
PO_LINE_CUSTOM_FIELD_SHAPE   = { id_key: "customfield_id",  extra: [] }
BILL_LINE_CUSTOM_FIELD_SHAPE = { id_key: "custom_field_id", extra: ["index", "label"] }
```

A conformance test in §39 Test Scenarios asserts both shapes against a captured response, and fails the build if a single shape is emitted for both.

There is a matching path irregularity: the value-setting endpoints use the **singular** module segment while the collection endpoints use the plural — `PUT {BASE_V3}/purchaseorder/{purchaseorder_id}/customfields` against `GET {BASE_V3}/purchaseorders`, and `PUT {BASE_V3}/bill/{bill_id}/customfields` against `GET {BASE_V3}/bills`. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` A path builder that pluralises by rule will produce 404s. Paths must come from the `API Endpoint Catalogue` entity, never from string construction.

A third irregularity affects scopes rather than paths: the fixed-asset scope family is **singular**, `ERP.fixedasset.READ` and `ERP.fixedasset.CREATE`, while the path is plural `/fixedassets`. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

**Resolution order for a bill line's WBS attribution.** Applied in order; the first that resolves wins, and the resolution path is stored on the `Bill Line` so an auditor can see how the attribution was reached:

1. Hub line key in `item_custom_fields` — exact, if the manual prerequisite is in place.
2. `purchaseorder_item_id` → the matched `PO Line` → that line's WBS code. Preferred in practice, because the PO line was coded by the Hub itself.
3. Line-level WBS reporting tag option.
4. Line `project_id` plus line `account_id`, giving CAPEX code and budget head but **no WBS element**. Attribution lands on the project's unallocated node.
5. Nothing resolves — the line is parked in the Reconciliation Exception Queue (SCR-27) with message `MSG-INT-006`, and is excluded from Actual CWIP until a human codes it. It is never guessed.

```

```

This convention is the only machine-usable tie from a Zoho fixed asset back to the CWIP that funded it, and it is a string convention, not a foreign key. §27.4 treats it as such and reconciles accordingly.

### 19.12 Mapping validation rules the Hub enforces

These are Hub-side validations. They exist because Zoho ERP will happily accept an uncoded capital line.

| # | Rule | Failure behaviour | Message |
|---|---|---|---|
| 1 | Every capital PO line must resolve to a CAPEX code and a budget head before the outbound intent is released | Block release; do not create the PO | `MSG-BUD-004` |
| 2 | Where the tenant has adopted WBS, every capital PO line must also resolve to a released WBS element | Block release | `MSG-BUD-004` |
| 3 | A WBS code with no published tag option must not be silently omitted from the payload | Block release; queue a tag-option publication request for System Administrator approval | `MSG-INT-001` variant naming the mapping |
| 4 | An inbound bill line that resolves to no WBS element by any of the five steps in §19.8 is parked, not attributed | Line excluded from Actual CWIP; exception raised | `MSG-INT-006` |
| 5 | An inbound bill line whose value exceeds the PO line it references | Attribute it, but raise the excess for confirmation | `MSG-PRC-004` |
| 6 | A `project_id` on an inbound line that maps to no Hub CAPEX Project | Park the line; never auto-create a Hub project from a Zoho project | `MSG-INT-006` |
| 7 | A discovered `customfield_id` that no longer matches the stored mapping | Fail the connection test; the field was edited or deleted in the Zoho UI | `MSG-INT-001` variant |
| 8 | A reporting tag whose `preference` is not `line_item` | Fail the connection test — a transaction-level tag cannot carry WBS attribution | `MSG-INT-001` variant |
