## 36. User Stories

### 36.1 How to read this section

One story per POC capability, in role–goal–benefit form. Every story names a role from the frozen 13-role registry, a requirement identifier from the frozen requirement registry, the demonstration step from §35 POC Scope that exercises it, and the screens it lives on. §37 Acceptance Criteria carries the given/when/then for each story with concrete numbers; §39 Test Scenarios carries the executable cases.

**Identifier note.** `US-nn` is a sequence authored in this section, in the same way that `RISK-nn` is authored in §42 Risk Register. It is not drawn from a frozen registry, because the frozen identifier table in the authoring conventions defines no scheme for user stories. The sequence is stable: a story is never renumbered, only superseded.

**Provenance tags.**

| Tag | Meaning | Count |
|---|---|---|
| `CLIENT-PDF` | Derived from a requirement the client stated | 39 |
| `MASTER-PROMPT` | Introduced by the brief, not by the client (CONF-02, CONF-07) | 17 |
| `DERIVED-RECOMMENDATION` | Neither — a control this blueprint proposes and marks as a recommendation | 4 |

Stories tagged `MASTER-PROMPT` cover the WBS layer and the entire connector setup module. They must never be presented to Atha Group as confirmed client requirements. The client PDF contains no WBS hierarchy at all, and its complete statement on integration mechanics is a single architecture line.

**Priority** uses the client's own MUST / SHOULD grading carried through from the requirement registry. Where a story serves requirements of mixed priority, the highest applies.

**Design decision carried by US-15 and US-17.** CONF-10 records the client document's own inconsistency: it requires a budget availability check at the Purchase Request stage, but its control formula counts only Actual CWIP and Open PO Commitments, so an approved Purchase Request reserves nothing. Two Purchase Requests of ₹10,00,000 each can therefore both pass a check against ₹15,00,000 available. The POC implements the client's behaviour as the default — a soft, advisory check at the Purchase Request with no reservation — and provides hard reservation as a configurable switch per entity or per project. US-17 exists so that where the client chooses hard reservation, the race is genuinely closed rather than narrowed. This is a design decision, not a confirmed requirement, and it is an open question for the client.
