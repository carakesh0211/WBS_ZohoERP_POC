**Recommendation.**

1. **Adopt F1 as the primary design.** The Purchase Request is owned by the CAPEX and CWIP Control Hub. It is the only option that makes the budget availability check synchronous and blocking, keeps one approval authority, needs no unverified Zoho mechanism, and leaves a complete audit trail in one place. This is also the default the conflict register anticipated for CONF-01.
2. **Offer F2 as an optional mirror, not as the master.** Where Atha Group wants Purchase Requests visible to Zoho ERP users who never log into the Hub, the Hub can project approved requests into a Zoho custom module. Custom module records are delta-syncable, so the mirror can be verified rather than assumed. This is a phase-2 item, not proof-of-concept scope.
3. **Reject F3, F4, F5 and F6 for production.** F3 makes the control retrospective, which defeats the requirement. F4 pollutes the purchase-order register and creates two approval chains over one document. F5 rests on a delivery mechanism that is not proven (§24.6). F6 is outside the evidence base of this blueprint entirely.
4. **Document F7 as the degraded mode, not as a choice.** If Atha Group decides the Purchase Request stage is not worth the effort, the control still functions — it simply moves entirely to Purchase Order approval, and the client's own workflow steps 3 and 4 disappear. State that consequence to the client rather than allowing it to arrive by omission.

**Residual risk of F1.** A user can still raise a Purchase Request directly in the Zoho ERP user interface, bypassing the Hub, and Procurement can still create a Purchase Order in Zoho that the Hub never authorised. The Hub detects this on the next PO delta poll — an inbound PO with no matching outbound intent — and raises it as an unauthorised-commitment exception. Detection is after the fact; prevention would require removing PO creation rights from Zoho users, which is an Atha Group policy decision, not a technical one. This is carried in §42 Risk Register and as a question in §45 Client Clarification Questionnaire.

### 24.5 The receipt-linkage gap and the workaround

**The finding, stated precisely.** The line-level matching problem has two legs and only one is broken.

- **PO line to bill line: intact.** A bill line carries `purchaseorder_item_id`. Commitment-to-actual conversion and double-count prevention are achievable against documented fields.
- **PO line to receipt line: broken.** A purchase-receive line exposes only `line_item_id`, `item_id`, `name`, `description`, `item_order`, `quantity` and `unit`. It carries no `purchaseorder_item_id`, no `project_id`, no `tags` and no custom-field node. The PO link exists at header level only, returned as `purchaseorder_id` and `purchaseorder_number`.
- **And the module has no list endpoint.** The complete path set is `POST /purchasereceives`, `GET /purchasereceives/{purchasereceive_id}`, `PUT /purchasereceives/{purchasereceive_id}`, `DELETE /purchasereceives/{purchasereceive_id}`. There is no `GET /purchasereceives`.
- The purchase-receive schema also contains no status field.

`[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` and `[source: https://www.zoho.com/erp/api/v3/purchasereceives/ — verified 2026-08-05]`

**Why it matters.** REQ-GRN-001 requires that receipt is recorded against the PO and that commitment remains for the unbilled PO balance. More sharply, the anti-under-count control ruled for this blueprint requires an explicit received-but-unbilled exposure bucket so that nothing falls between commitment relief and actual cost. Without receipt data the Hub cannot populate that bucket from Zoho, and the position that SAP would call goods-received-not-invoiced is invisible.

**What is genuinely lost.** Two things, and it is worth being blunt about which:

- **Discovery** — the Hub cannot find out that a receipt happened. This is the harder loss, and it is caused by the missing list endpoint, not by the missing line link.
- **Line attribution** — even given a receipt, the Hub cannot tell which PO line each received quantity belongs to when the same item appears on more than one line of the same PO.

**The workaround, in four parts.**

*Part 1 — Hub-owned goods receipt capture as the primary path.* SCR-16 (GRN and Unbilled Receipt View) lets the Project Manager or storekeeper record receipt against an open PO line directly in the Hub. This is deterministic: the user selects the PO line, so attribution is exact and coding is inherited from the PO line. The `GRN Reference` and `GRN Line` entities exist for this purpose. This path does not depend on any Zoho capability.

*Part 2 — opportunistic retrieval where an identifier is known.* Where a `purchasereceive_id` reaches the Hub — from a workflow webhook if one is ever proven, from a user pasting the receipt number, or from a receipt the Hub itself created during the proof of concept via `POST {BASE_V3}/purchasereceives` — the Hub retrieves the document by id and reconciles it against the Hub-captured receipt. This is a verification path, not a discovery path, and the design never pretends otherwise.

*Part 3 — quantity-based allocation when a retrieved receipt must be attributed.* Deterministic algorithm, applied per retrieved receipt, so that two runs over the same receipt produce the same result:

```
for each receipt_line in receipt.line_items ordered by item_order:
    candidates = PO lines of receipt.purchaseorder_id
                 where item_id == receipt_line.item_id
                   and open_receipt_qty > 0
                 ordered by item_order ascending          # deterministic, FIFO by line order
    remaining = receipt_line.quantity
    for po_line in candidates:
        take = min(remaining, po_line.open_receipt_qty)
        allocate(receipt_line -> po_line, qty = take, value = take * po_line.rate)
        po_line.open_receipt_qty -= take
        remaining -= take
        if remaining == 0: break
    if remaining > 0:
        raise reconciliation exception "receipt quantity exceeds ordered quantity"
        # the residual is never silently dropped and never allocated to a guessed line
```

Allocation confidence is recorded on every allocation: `EXACT` when only one candidate PO line existed, `DERIVED` when FIFO was applied across two or more candidates, `UNRESOLVED` when the exception fired. Screens display the confidence; reconciliation in §27.7 treats `DERIVED` as reviewable and `UNRESOLVED` as blocking.

*Part 4 — the received-but-unbilled figure.* Per PO line:

```
received_value   = allocated_received_qty * po_line.rate
billed_value     = sum of matched bill line values      (via purchaseorder_item_id)
received_unbilled = max(0, received_value - billed_value)
open_commitment   = max(0, ordered_value - billed_value)
```

Note the deliberate design: `open_commitment` is relieved by **billing**, not by receipt. This is the anti-under-count ruling of this blueprint — commitment is relieved only on the event that also creates actual cost, and the received-but-unbilled bucket is reported separately so nothing falls between the two. It is the mirror of the anti-double-count control.

The arithmetic is consistent with the frozen commitment-to-actual position, quoted verbatim: **PO ₹20L, actual bill ₹12L, open commitment ₹8L, budget exposure ₹20L.** Adding a receipt to that position changes neither exposure nor the commitment-plus-actual split; it only populates the separately-reported received-but-unbilled bucket, which is why exposure is stable across the receipt event.

**What the client must accept.** Received-but-unbilled is reconstructed by the Hub from Hub-captured receipt data, not read from Zoho ERP. If a receipt is entered in Zoho ERP and never entered in the Hub, the Hub will not know about it. Mitigations: SCR-16 shows an ageing list of PO lines with no receipt recorded, message `MSG-PRC-005` warns on received-but-unbilled ageing, and §27.7 raises an exception where a bill arrives against a PO line that has no recorded receipt. This is a real, permanent limitation of the vendor's API surface as specified on 2026-08-05, and it is carried as an open question to Zoho in §44 Open Questions.

### 24.6 Webhooks — treated as unproven throughout

**What is evidenced.**

- Webhooks exist in Zoho ERP as a workflow **action**, described as user-defined HTTP and HTTPS callbacks triggered when a particular event occurs at the source site. Configuration is entirely through the user interface; no API for creating, listing or managing them is mentioned. `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`
- The outbound method is selectable among PUT, POST and DELETE, with POST selected by default. There is no GET option. `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`
- The payload format is selectable among Default Payload, `x-www-form-urlencoded` and Raw body parameters. `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`
- A webhook can be secured with a secret token which cannot be edited or viewed once the webhook is created, and which must be alphanumeric and 12 to 50 characters. `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`
- The absence of a webhook management API from the ERP REST surface survived adversarial testing: the API navigation was independently re-enumerated with no webhooks, events, notifications, subscriptions or callbacks page; probes of those slugs returned 404; and a case-insensitive scan across all 78 specifications returned zero webhook-management paths, with the strings `webhook` and `callback` not occurring anywhere in any specification. `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`

**What is not evidenced, and is therefore not designed against.**

| Question | Status |
|---|---|
| Which Zoho ERP modules can trigger a workflow webhook | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| Whether the Purchase Request module is workflow-enabled | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| The schema of the Default Payload | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** — the help page names the option but does not document its shape |
| Delivery guarantees: at-least-once, at-most-once, ordering, retry policy, dead-lettering | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| Whether the secret token is an HMAC signature over the body or a shared bearer value | The documented behaviour is a shared secret that helps verify the webhook was sent from Zoho ERP; no body signature and no replay protection is documented. Treated as a shared secret |
| Whether webhooks can be provisioned per tenant without manual configuration | No — configuration is a user-interface action per tenant |

**Design ruling.** Polling is the primary and sole authoritative ingestion mechanism. Every inbound flow in §18.9 is a poll. If Atha Group's Zoho administrator chooses to configure a workflow webhook, the Hub accepts it at a signed endpoint and treats it purely as a **hint to poll early** — it enqueues an immediate delta poll for the named object and never writes ledger data directly from the webhook payload. Consequences of that ruling:

1. A missed webhook costs latency, never correctness.
2. A duplicated webhook is harmless, because the poll it triggers is idempotent.
3. A spoofed webhook cannot inject data, because no payload field is trusted.
4. The proof of concept can be delivered and accepted without any webhook being configured at all.

This resolves CONF-16, which recorded an internal inconsistency in the master prompt over whether webhook availability could be assumed. It cannot, and the design does not.

| Bill header has no `project_id` | Medium | Line-level mapping throughout (§19.1) | None; it is a design constraint, not a defect |
| No custom-field definition API | High | Nine manual prerequisites, gated by the connection test (§19.4) | Onboarding cost per organisation; a field edited in the Zoho UI breaks a mapping until re-discovered |
| No custom-field node on journal lines | Medium | WBS carried as a reporting tag, which works on all three document families (§19.3) | Reporting-tag option volume at scale is unquantified |
| Fixed assets carry no source link | High | Traceability anchored on the Hub `Capitalisation Request`; naming convention plus tags as a secondary tie (§19.10) | An asset created directly in Zoho cannot be traced to CWIP |
| Fixed assets cannot be delta-synced | Medium | Full-refresh reconciliation (§27.4) | Cost grows linearly with the asset register |
| Vendor and item masters cannot be delta-synced | Low | Nightly full refresh | Cost grows with master-data size |
| No `is_advance` flag on vendor payments | Medium | Derived rule: a payment with an empty bill allocation array is an advance | Derivation may misclassify a payment awaiting allocation; treated as a reviewable exception |
| Webhooks unproven | Medium | Polling is authoritative; webhooks are a latency hint only (§24.6) | Higher latency than an event-driven design; acceptable for a financial control cycle |
| 14 modules on v1 | Low | Base path resolved per module from the `API Endpoint Catalogue` (§18.1) | A hard-coded base path fails silently on those modules |
| Scope families absent from the published OAuth page | Medium | Scope list driven from the specification, validated live at connection test (§15) | A scope may be rejected at authorisation; discovered at setup, not at run time |

### 24.9 Overall integration verdict

Zoho ERP is a viable transaction system of record for this design, and is not a viable control system for it.

- **Viable as the transaction backbone.** Purchase orders, bills, journals, vendor credits, vendor payments, chart of accounts and fixed assets are all readable and, where appropriate, writable, with line-level analytical coding that survives from purchase order to bill to capitalisation journal. That is enough to build the client's control loop on documented fields.
- **Not viable as the control layer.** There is no multi-level WBS, no budget by head, no open-commitment computation, no availability control, no Purchase Request API and no received-but-unbilled position. Every one of those is the control the client actually asked for. They must live in the Hub.

This supports the architecture recommendation in §12 Recommended Architecture, and it is also the honest answer to CONF-05, where the client's own document proposed solving the requirement inside Zoho ERP with controlled customisation. That approach is not wrong in principle; it is defeated in practice by rows 12 through 15 and 19 of §24.2. The blueprint says so directly, with the evidence in the row, rather than departing from the client's stated approach without explanation.
