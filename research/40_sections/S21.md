## 21. Detailed Business Rules

### 21.1 How to read this section

Every rule below is written so a coding agent can implement it without reinterpreting a business requirement. Each rule carries:

- a **rule identifier** of the form `BR-nn`;
- a **statement** in one sentence, in the imperative;
- a **formula** where the rule is arithmetic;
- a **worked example** with real Indian rupee figures;
- the **message** raised, from `C10_messages.json`, and the **screen** it appears on, from `C8_screens.json`;
- the **provenance** — `CLIENT-PDF`, `MASTER-PROMPT` or `DERIVED-RECOMMENDATION` — and any conflict the rule inherits.

**On the rule identifiers.** `BR-nn` codes are section-local labels, in the same way §13 uses `IM-nn` and `RC-nn` and §7 uses `UC-n`. They are not registry identifiers and no registry defines them. Requirement, screen, message, entity, status, role and conflict identifiers below all come from their frozen registries and are never invented.

**Numeric conventions, binding on every rule.**

| Convention | Rule |
|---|---|
| Storage | All amounts are stored as signed integer minor units (paise) in a single base currency, INR |
| Rounding | Round half away from zero (round-half-up) at every presentation boundary. Never round an intermediate |
| Percentage rounding | One decimal place, round-half-up. `78.75%` prints as `78.8%`, which reproduces the client's own printed figure |
| Display | Indian digit grouping with the rupee symbol prefixed and no space: `₹1,50,00,000`. Two decimals on transaction screens, none on dashboard tiles |
| Negatives | In parentheses |
| Lakh and crore | Permitted only on dashboard tiles and chart axes, with the full grouped value on hover or drill-down |
| Dates | `dd-MMM-yyyy` in prose and user interface; ISO-8601 in payloads, exports and audit records |

**The one invariant that governs every rule in this section**, quoted from the frozen formula registry and never restated in other numbers:

> Exposure = Open PO Commitment + Actual CWIP
> Available Budget = Current Approved Budget - Exposure
> Utilisation % = Exposure / Current Approved Budget
> Current Approved Budget = Original Budget + Approved Supplements - Approved Returns +/- Approved Transfers

§22 Budget and Commitment Calculation Logic carries the full arithmetic, the frozen worked examples and the seventeen-position state matrix. This section states the rules; that section proves them.

### 21.4 Group A — Budget availability

#### BR-01 — The control object of an availability check

**Statement.** Every availability check is evaluated against exactly one **control object**, which is the tuple `(Project, WBS Element, Budget Head)`. Where the project has no WBS elements, the WBS component is null and the control object degenerates to `(Project, Budget Head)`, which is precisely the two-level structure the client document describes.

**Resolution rule.** Where a transaction line is coded to a WBS element that is not budget-carrying, the check climbs to the nearest budget-carrying ancestor and evaluates there. This mirrors SAP, where actual costs and commitments of subordinate elements roll into the parent's assigned value only when the subordinates do not themselves carry budget `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/f711d553088f4308e10000000a174cb4.html — verified 2026-08-05]` (SAP S/4HANA on-premise, Project System).

**Worked example.** A purchase request line coded to `CAPEX-2026-001.03.02` (Machine foundation, not budget-carrying), whose parent `CAPEX-2026-001.03` (Plant and machinery, budget-carrying) holds the budget. The check evaluates on `.03`. The line's own element `.03.02` shows the same availability, marked "inherited from CAPEX-2026-001.03".

**Provenance.** `CLIENT-PDF` for the project-and-head form (REQ-BUD-014, REQ-BUD-015); `MASTER-PROMPT` for the WBS component (CONF-02).

#### BR-02 — Mandatory coding

**Statement.** A CAPEX code and a budget head are mandatory on every line of every capital procurement document. A line without both cannot be submitted.

**Worked example.** A three-line purchase request where line 2 carries no budget head. Submission is blocked with MSG-BUD-004 on SCR-14: *"A CAPEX code and budget head are mandatory on capital procurement. Select a budget head for line 2 before submitting."* Lines 1 and 3 are not lost; the form retains them.

**Provenance.** `CLIENT-PDF`, REQ-SEC-002, REQ-PRJ-006.

#### BR-03 — The availability decision and its three outcomes

**Statement.** An availability check returns exactly one of three outcomes, and the outcome determines the approval route.

| Outcome | Condition | Route | Status | Message |
|---|---|---|---|---|
| `PASS` | Requested value ≤ Available Budget, and Utilisation % after the transaction < 80.0% | Normal approval | Approved | none |
| `PASS-WITH-WARNING` | Requested value ≤ Available Budget, and Utilisation % after the transaction ≥ 80.0% | Normal approval, warning displayed | Approved | MSG-BUD-002 at 80%, MSG-BUD-003 at 90% |
| `FAIL` | Requested value > Available Budget | Exception approval **or** budget revision. Never silent approval | Exception Pending, or Budget Exceeded if the transaction is forced through by override | MSG-BUD-001 |

**Formula.**

```
shortfall = requested_value - available_budget          (only meaningful when positive)
utilisation_after = (exposure + requested_value) / current_approved_budget
```

**Worked example, using the frozen client case.** The client's own over-budget example, quoted verbatim from the formula registry:

> 80L Budget - 35L Actual CWIP - 30L Open PO Commitment = 15L Available. A new PO of 20L exceeds available budget by 5L and must route to exception approval or budget revision.

Rendered as MSG-BUD-001 on SCR-13: *"The proposed Purchase Order value of ₹20,00,000 exceeds the available budget of ₹15,00,000 for CAPEX-2026-001.02 (Plant & Machinery) by ₹5,00,000. Submit a budget revision or request exception approval."*

**Design note on message semantics.** `PASS-WITH-WARNING` is advisory and does not block, and `FAIL` blocks pending a decision. SAP draws the same distinction: a warning-type tolerance limit still allows budget to be used after the limit is exceeded `[source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/c56f622a2edf491b9f1b596b55587009/183ab1f86115419da31288fe18dcbbd0.html — verified 2026-08-05]` while an error-type tolerance limit blocks the posting of commitments such as purchase orders or purchase requisitions once exceeded `[source: https://help.sap.com/docs/SAP_S4HANA_CLOUD/c56f622a2edf491b9f1b596b55587009/183ab1f86115419da31288fe18dcbbd0.html — verified 2026-08-05]` (SAP S/4HANA Cloud; the cited page does not distinguish public from private edition).

**Provenance.** `CLIENT-PDF`, REQ-BUD-004, REQ-BUD-018, REQ-PRC-002.

#### BR-04 — Which level binds

**Statement.** Budget-head availability is the **binding** check. The project-level check is evaluated and displayed on every transaction but can only bind where an unallocated project reserve exists — that is, where the project budget exceeds the sum of its head budgets.

**Supporting validations.**

1. The sum of head budgets may not exceed the project budget. Attempting to save a budget version that breaches this is rejected at the version, not at the line.
2. Any remainder is displayed on SCR-09 as an explicit `Unallocated` line with its own availability figure, so it cannot be spent invisibly.
3. Allocating from `Unallocated` to a head is a budget transfer (BR-53) and follows the same approval path.

**Worked example.** Project budget ₹1,50,00,000; five head budgets totalling ₹1,45,00,000. `Unallocated` shows ₹5,00,000. A purchase request of ₹6,00,000 against a head with ₹4,00,000 available **fails** the head check even though the project has ₹5,00,000 of unallocated reserve plus the head's own ₹4,00,000. The requestor's next action is a transfer of ₹2,00,000 from `Unallocated`, not an exception.

**Provenance.** `DERIVED-RECOMMENDATION` resolving CONF-20. The client document requires budgets at both levels and raises an exception when a transaction "exceeds available project or budget-head limit", but its own section 6 makes the heads sum exactly to the project, so the project check would never fire independently. Confirm with Atha Group whether an unallocated project reserve is permitted and which authority may allocate it.

#### BR-05 — Revalidation after a budget change

**Statement.** After any approved budget revision, transfer or return, every derived value is recomputed from the **current** budget and never from the frozen original, and every in-flight transaction on the affected control objects is revalidated.

**Revalidation set.** All Purchase Request Reference and Purchase Order Reference records on the affected control object whose status is Submitted, Under Review, Exception Pending or Budget Exceeded. Records already Approved are not revalidated; their commitment already stands.

**Worked example.** Head D1 with Current Approved Budget ₹1,00,00,000, exposure ₹96,00,000, available ₹4,00,000, and a purchase request of ₹6,00,000 sitting in Exception Pending. A supplement of ₹10,00,000 is approved. Current Approved Budget becomes ₹1,10,00,000; available becomes ₹14,00,000; the purchase request revalidates to `PASS` and returns to the normal approval route. MSG-BUD-005 confirms: *"Revision R-004 approved by CFO on 12-Aug-2026. Current approved budget for D1 is now ₹1,10,00,000 (original ₹1,00,00,000, revisions ₹10,00,000). The original budget is unchanged."*

**Corroboration.** SAP recomputes the same way: after supplements, returns or transfers, all derived display values are recomputed from the current budget, never from the frozen original budget `[source: https://help.sap.com/doc/acd8b65334e6b54ce10000000a174cb4/3.6/en-US/0213d553088f4308e10000000a174cb4.html — verified 2026-08-05]` (SAP classic on-premise Project System documentation).

**Provenance.** `CLIENT-PDF`, REQ-REV-007.

### 21.5 Group B — Commitment calculation

#### BR-06 — The commitment ledger is append-only

**Statement.** Commitment is never stored as a mutable balance. Every change writes a signed Commitment Ledger row carrying the control object, the source document line, the signed amount, the event that caused it and the timestamp. Open commitment for any control object is the sum of its ledger rows.

**Why.** A mutable balance cannot be audited, cannot be replayed after an integration failure, and cannot answer "why is this number what it is". The append-only ledger makes every figure on every screen traceable to a source event, which is REQ-SEC-001.

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-07 — Open commitment for a purchase order line

**Statement.** Open commitment for a purchase order line is its commitment base less the value already billed against it, floored at zero.

**Formula.**

```
commitment_base(line) =
    ordered_value(line)      if line status is live      (Approved, Partially Actualised, ...)
    received_value(line)     if line status is Closed or Cancelled
    0                        if line is Cancelled with no receipts

open_commitment(line) = max(0, commitment_base(line) - billed_value(line))
```

This one expression reproduces every position in the client's own commitment-to-actual table and every extension case in §22.7 without a special case. The `received_value` branch is what stops a closure or cancellation from dropping received-but-unbilled value out of exposure.

**Worked example, the client's own part-billed row, quoted verbatim from the frozen registry:**

> po 20L; actual_bill 12L; open_commitment 8L; budget_exposure 20L

Under the formula: line is live, `commitment_base = ₹20,00,000`, `billed_value = ₹12,00,000`, `open_commitment = max(0, 20,00,000 − 12,00,000) = ₹8,00,000`. Exposure = ₹8,00,000 + ₹12,00,000 = ₹20,00,000. The client's figures follow from the formula, not the other way round.

**Provenance.** `CLIENT-PDF` for the four anchor positions (REQ-PO-004 to REQ-PO-007); `DERIVED-RECOMMENDATION` for the closed-and-cancelled branch.

#### BR-08 — Commitment is relieved only by the event that creates actual cost

**Statement.** A goods receipt never relieves commitment. Only a vendor bill does, and it relieves exactly the value it books as actual.

**Why this is not the SAP default, and why we depart.** SAP's behaviour is controlled by two independent switches. The goods receipt indicator on the purchase order item decides whether commitment reduction and actual cost arise at goods receipt or at invoice receipt `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/1b7cd0531d8b4208e10000000a174cb4.html — verified 2026-08-05]` (SAP S/4HANA on-premise, Project System). The goods-receipt-non-valuated flag independently overrides this, so that invoice information is used instead `[source: https://help.sap.com/docs/SUPPORT_CONTENT/spmm/3362167804.html — verified 2026-08-05]` (SAP support content, classic on-premise materials management). Where the first is set and the second is also set, commitment is relieved at receipt while actual cost arrives only at invoice, and the value sits in neither. Our design forecloses that case by construction: one relief event, and it is the one that also creates cost. §22.5 works the case through with numbers.

**Provenance.** `DERIVED-RECOMMENDATION`, from the `commitment_reduction_gates` ruling in the frozen formula registry. It is also consistent with the client's own step 7, which states that commitment remains for the unbilled purchase order balance (REQ-GRN-001).

#### BR-09 — Received-but-unbilled is a decomposition, not an addition

**Statement.** Received-but-unbilled is a reported subdivision of open commitment. It is never added to exposure, because the value it represents is already inside open commitment.

**Formula.**

```
received_but_unbilled(line) = max(0, min(received_value, commitment_base) - billed_value)
ordered_not_received(line)  = open_commitment(line) - received_but_unbilled(line)
open_commitment(line)       = received_but_unbilled(line) + ordered_not_received(line)
```

The client invariant is therefore untouched: `Exposure = Open PO Commitment + Actual CWIP`, exactly as frozen.

**Worked example.** Purchase order line ₹20,00,000; six of ten units received (₹12,00,000); nothing billed. Open commitment ₹20,00,000, of which received-but-unbilled ₹12,00,000 and ordered-not-received ₹8,00,000. Exposure ₹20,00,000. Available on D1 ₹80,00,000. Nothing has moved; the decomposition is disclosure only.

**Zoho constraint that makes this our work, not Zoho's.** Purchase receive lines expose only description, item id, item order, line item id, name, quantity and unit — no purchase order line link and no project, tag or custom-field coding — and the module has no list or search endpoint (OAS-03) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. Received-but-unbilled must therefore be reconstructed in the Control Hub by matching receipt lines to purchase order lines on `item_id` and quantity in receipt sequence, and the match confidence must be shown on SCR-16. Where a purchase order carries two lines for the same `item_id`, the match is ambiguous and the row is flagged for manual assignment rather than guessed.

**Message.** MSG-PRC-005 ages the bucket: *"D1 has ₹12,00,000 received but not yet billed, the oldest for 34 days. This is included in exposure and will convert to actual CWIP when the vendor bills."*

**Provenance.** `DERIVED-RECOMMENDATION`, from the `commitment_reduction_gates` ruling.

### 21.6 Group C — Actual calculation

#### BR-10 — What counts as Actual CWIP

**Statement.** Actual CWIP is the sum of capitalisable value booked to the control object through: vendor bills, approved journal adjustments, and approved allocations of common cost. It excludes vendor payments, vendor advances, purchase orders, purchase requests and goods receipts.

**Formula.**

```
actual_cwip(control_object) = Σ bill_line_capitalisable_value
                            + Σ approved_journal_debit  −  Σ approved_journal_credit
                            − Σ vendor_credit_value
                            − Σ reversed_bill_value
```

**Provenance.** `CLIENT-PDF`, REQ-BILL-001, REQ-CWIP-001.

#### BR-11 — The actual ledger is append-only and line-scoped

**Statement.** Every actual is written as an Actual Ledger row keyed to `(bill_id, line_item_id)` and to the control object, carrying gross, tax and net amounts as three separate columns.

**Why three columns.** The client document never states whether budgets are tax-inclusive or tax-exclusive, and that single answer changes the value of every figure in its own sections 6, 7 and 12 (CONF-15). Carrying gross, tax and net separately means either policy can be configured without a schema change.

**Provenance.** `DERIVED-RECOMMENDATION` resolving CONF-15.

#### BR-12 — A bill with no purchase order reference

**Statement.** A bill line carrying a CAPEX code but no `purchaseorder_item_id` increases actual with no commitment to relieve. Exposure therefore rises by the full line value. The row is written with `match_state = UNMATCHED` and appears on SCR-18 for review.

**Worked example.** Head D1: exposure ₹20,00,000 (one open purchase order), available ₹80,00,000. A direct bill of ₹3,00,000 coded to D1 with no purchase order posts. Actual becomes ₹3,00,000, open commitment stays ₹20,00,000, exposure becomes ₹23,00,000, available becomes ₹77,00,000.

**Control consequence to state to the client.** Direct CWIP bills bypass the pre-approval budget check entirely, because the check happens before a purchase order is raised and no purchase order exists. The client document is silent on this case. The recommended control is a Zoho ERP-side restriction that capital-coded bills require a purchase order reference, with a named exception list; this is a client policy decision, not a blueprint ruling.

**Provenance.** `DERIVED-RECOMMENDATION`. The client PDF does not state the treatment of bills booked without a purchase order.

#### BR-13 — Matching key for commitment-to-actual conversion

**Statement.** Commitment-to-actual conversion is matched on `purchaseorder_item_id` carried on the bill line. Header-level matching is never used.

**Evidence.** Bill lines carry `purchaseorder_item_id`; the purchase-order-to-bill leg of line-level matching is intact (OAS-03) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. Bill headers do not carry `project_id`; bill lines do (OAS-10) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`.

**Do not confuse the two legs.** The receipt leg has no such link and must be reconstructed (BR-09). The bill leg is fully supported by documented fields.

**Provenance.** `MASTER-PROMPT`, evidenced from the vendor specification.

### 21.7 Group D — Exposure and utilisation

#### BR-14 — Exposure

**Statement.** Exposure = Open PO Commitment + Actual CWIP. No other term is added, and specifically not received-but-unbilled, which is already inside open commitment (BR-09).

**Worked examples, quoted verbatim from the frozen formula registry:**

> **Budget head - Civil:** budget 25,00,000; commitment 5,00,000; actual 12,00,000; available 8,00,000
> **Budget head - Plant & Machinery:** budget 80,00,000; commitment 30,00,000; actual 35,00,000; available 15,00,000

**Provenance.** `CLIENT-PDF`, REQ-BUD-001.

#### BR-15 — Exposure thresholds

**Statement.** Two exposure thresholds are configured per organisation, defaulting to the client's own values of 80 percent and 90 percent, plus a hard `budget exceeded` event at 100 percent. Each is evaluated at both project level and budget-head level, defaulting to both. Each fires once on crossing and re-arms on any approved budget revision.

**Decision table.**

| Utilisation after the transaction | Level | Behaviour | Message | Recipients |
|---|---|---|---|---|
| < 80.0% | Both | Silent | none | — |
| ≥ 80.0% and < 90.0% | Head | Warn, do not block | MSG-BUD-002 | Project Manager, Project Finance Controller |
| ≥ 80.0% and < 90.0% | Project | Warn, do not block | MSG-BUD-002 | Project Manager, Plant Head |
| ≥ 90.0% and ≤ 100.0% | Head | Warn, further commitments require exception approval | MSG-BUD-003 | Project Finance Controller, CAPEX Committee |
| ≥ 90.0% and ≤ 100.0% | Project | Warn, further commitments require exception approval | MSG-BUD-003 | Project Finance Controller, CFO |
| > 100.0% | Either | Status Budget Exceeded; the object appears on SCR-25 | MSG-BUD-001 | Project Finance Controller, CAPEX Committee, CFO |

**Worked example.** D1 at ₹1,00,00,000 budget, exposure ₹78,00,000, utilisation 78.0%. A purchase order of ₹4,00,000 is approved. Exposure becomes ₹82,00,000 and utilisation 82.0%, crossing 80 percent. MSG-BUD-002 fires once: *"D1 has reached 82.0% of its approved budget of ₹1,00,00,000. Exposure is ₹82,00,000 (₹47,00,000 committed, ₹35,00,000 actual). Review before approving further commitments."* A subsequent purchase order taking utilisation to 85.0% does **not** re-fire the 80 percent alert.

**Provenance.** `CLIENT-PDF` for the two threshold values (REQ-ALT-001, REQ-ALT-002, REQ-ALT-003); `DERIVED-RECOMMENDATION` for the level, one-shot and re-arm semantics, resolving CONF-18. The client document never states the basis of its percentages; the definition adopted is the one its own section 12 data satisfies at every row.

#### BR-16 — Utilisation and its distinct spend-only sibling

**Statement.** Utilisation % = Exposure / Current Approved Budget, rounded half-up to one decimal place. Where a spend-only measure is needed it is named **Actual Utilisation %** = Actual CWIP / Current Approved Budget, and the two are never presented under the same label.

**Worked examples, quoted verbatim from the frozen formula registry:**

> **Dashboard - Production Line:** budget 1.50 Cr; commitment 30L; actual 85L; available 35L; utilisation 76.7%
> **Dashboard - Warehouse Expansion:** budget 80L; commitment 15L; actual 48L; available 17L; utilisation 78.8%

The Warehouse Expansion row is the reason the rounding rule is stated explicitly: the unrounded figure is 78.75%, which reproduces the client's printed 78.8% only under round-half-up.

**Provenance.** `CLIENT-PDF` for the figures; `DERIVED-RECOMMENDATION` for the naming separation, resolving CONF-19. The client's single column headed "Utilisation / Exposure" treats the two as one measure, and the equivalence was inferred from the data because the document states no formula for that column.

### 21.8 Group E — Purchase Request reservation

#### BR-17 — PR reservation is configurable, and defaults off

**Statement.** Whether an approved Purchase Request reserves budget before a purchase order exists is a configuration flag, `pr_reservation_mode`, set per organisation and overridable per project. The default is `SOFT`, which is the client document's own behaviour.

| Mode | At PR submission | At PR approval | On PR-to-PO conversion | On PR expiry or cancellation |
|---|---|---|---|---|
| `SOFT` (default) | Advisory availability shown | No ledger entry. Availability re-evaluated and shown | Commitment created from the purchase order only | No effect |
| `HARD` | Advisory availability shown | Reservation row written to the Commitment Ledger with `source = PR` | Reservation released; purchase order commitment created. Net effect on exposure is the difference between the two values | Reservation released |

**Provenance.** `CLIENT-PDF` for `SOFT` — the client's core control formula counts only actual CWIP and open purchase order commitments, so an approved Purchase Request reserves nothing. `MASTER-PROMPT` for `HARD`. Recorded as CONF-10 and as a direct question to Atha Group: should an approved Purchase Request block budget before a purchase order is raised?

#### BR-18 — The two-concurrent-PR case, worked both ways

**Statement.** Under `SOFT`, two Purchase Requests may each pass a check against the same available budget and both proceed. Under `HARD`, the first reserves and the second fails.

**Worked example.** Head D1, Current Approved Budget ₹1,00,00,000, exposure ₹85,00,000, available ₹15,00,000. PR-A for ₹10,00,000 and PR-B for ₹10,00,000 are both submitted on the same day.

| Step | `SOFT` mode | `HARD` mode |
|---|---|---|
| PR-A availability check | Available ₹15,00,000 → `PASS` | Available ₹15,00,000 → `PASS` |
| PR-A approved | No ledger entry. Available still ₹15,00,000 | Reservation ₹10,00,000 written. Available ₹5,00,000 |
| PR-B availability check | Available ₹15,00,000 → `PASS` | Available ₹5,00,000 → `FAIL`, shortfall ₹5,00,000 |
| PR-B approved | Approved. Available still ₹15,00,000 | Routed to exception approval, MSG-BUD-001 |
| PO-A raised for ₹10,00,000 | Commitment ₹10,00,000. Available ₹5,00,000 | Reservation released, commitment ₹10,00,000. Available ₹5,00,000 |
| PO-B raised for ₹10,00,000 | Availability check at PO **fails**: available ₹5,00,000, shortfall ₹5,00,000. MSG-BUD-001 | Cannot arise; PR-B never reached approval |

**The point to put in front of the client.** Under `SOFT`, the control still holds — nothing over-commits, because the purchase order check is binding. What `SOFT` costs is **rework**: PR-B was approved, procurement began sourcing, and the failure surfaces only when the purchase order is raised. Under `HARD`, the failure surfaces at approval, before anyone spends effort. That is the trade-off, stated in the terms Atha Group will care about.

**Provenance.** `DERIVED-RECOMMENDATION` resolving CONF-10.

#### BR-19 — Concurrency control on the availability check

**Statement.** The availability check and the ledger write that follows it execute inside one serialisable transaction scoped to the control object. A second check on the same control object waits.

**Implementation note for the coding agent.** Take a row-level lock on the control object's Budget Ledger head row before reading exposure, and release it only after the commitment or reservation row is written. Two simultaneous approvals on the same head are then ordered, not raced. The race exists only where the client has chosen `SOFT`, and there it is a business choice rather than a defect.

**Provenance.** `MASTER-PROMPT` concurrency edge case; `DERIVED-RECOMMENDATION` for the mechanism.

#### BR-20 — Reservation ageing

**Statement.** Under `HARD`, a reservation expires after a configurable period, default 45 days, and is released with a notification to the requestor. Expired reservations are listed on SCR-23.

**Why.** A reservation that never converts is indistinguishable from a budget cut nobody approved. SAP treats purchase requisition commitments the same way, reducing them on a quantity basis by purchase orders that reference the requisition, and driving them to zero either by a purchase order for the full amount or by a change to the requisition `[source: https://help.sap.com/docs/SAP_ERP/c399b33df2754c54960dfa51045cba22/0c7cd0531d8b4208e10000000a174cb4.html?version=6.02.latest — verified 2026-08-05]` (SAP classic on-premise ECC, Project System commitment management).

**Provenance.** `DERIVED-RECOMMENDATION`.

### 21.9 Group F — Purchase order commitment

#### BR-21 — When commitment is recognised

**Statement.** Commitment is recognised when the Zoho ERP purchase order status becomes approved or open, detected by incremental polling of `GET /purchaseorders` filtered on `last_modified_time` with a stored cursor and a look-back window.

**The control limitation, stated rather than hidden.** Between the moment a purchase order is approved in Zoho ERP and the moment the next poll detects it, budget is consumed in Zoho but not yet visible in the Control Hub. The window equals the polling interval plus processing time. At a five-minute interval the worst case is roughly six minutes. This is a stated control limitation, quantified in §33 Non-Functional Requirements, and is the reason the binding budget check is performed **before** the purchase order is raised, not after.

**Draft purchase orders.** A draft purchase order does not commit budget. The client document conflates creation and approval into one event and never says whether a draft consumes budget (CONF-21); confirm with Atha Group.

**Provenance.** `CLIENT-PDF` for "approved/open Purchase Orders are committed expenditure" (REQ-PO-001); `DERIVED-RECOMMENDATION` for the detection mechanism.

#### BR-22 — Amendment revalidation

**Statement.** A purchase order amendment revalidates only the **incremental** value, never the whole order.

**Formula.**

```
delta = new_line_value - old_line_value
if delta > 0:  availability check on delta only
if delta < 0:  no check; commitment reduces
floor:         new_line_value >= max(billed_value, received_value)
```

**Worked example, upward.** Head D1, available ₹80,00,000, one purchase order line at ₹20,00,000. The line is amended to ₹26,00,000. Delta ₹6,00,000 is checked against ₹80,00,000 → `PASS`. Commitment becomes ₹26,00,000, exposure ₹26,00,000, available ₹74,00,000. MSG-PRC-001 on SCR-15: *"PO-2026-0114 has increased from ₹20,00,000 to ₹26,00,000. The additional ₹6,00,000 has been revalidated against D1, where ₹80,00,000 is available."*

**Worked example, downward with a floor.** The same line at ₹20,00,000 with ₹12,00,000 billed and ₹20,00,000 received. An attempt to amend to ₹10,00,000 is rejected: the floor is `max(₹12,00,000, ₹20,00,000) = ₹20,00,000`. Amending to ₹18,00,000 is likewise rejected. The user's next action is to raise a vendor credit for the over-received quantity, or reverse the receipt, before reducing the order.

**Provenance.** `CLIENT-PDF`, REQ-PO-008; the floor rule is `DERIVED-RECOMMENDATION`.

#### BR-23 — Quantity-based and value-based lines

**Statement.** Material lines are tracked on quantity times rate. Service lines are tracked on value only, because a service receipt has no meaningful quantity to net.

**Consequence for received-but-unbilled.** A service line has no reconstructable receipt, so its received-but-unbilled is always zero and its whole open commitment is `ordered_not_received`. SCR-16 marks such lines `service — receipt not tracked` rather than showing a misleading zero.

**Corroboration.** SAP monitors purchase orders for services on the basis of value, not quantity, unlike material purchase orders `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/1b7cd0531d8b4208e10000000a174cb4.html — verified 2026-08-05]` (SAP S/4HANA on-premise, Project System).

**Provenance.** `MASTER-PROMPT` (service procurement, material procurement).

#### BR-24 — Freight and landed cost inside the commitment

**Statement.** Freight, duty, insurance, packing and other landed-cost lines carried on the same purchase order are part of the commitment for that control object, coded to the same budget head as the goods they relate to unless explicitly coded otherwise.

**Worked example.** Purchase order with a goods line of ₹20,00,000 and a freight line of ₹1,50,000, both coded to D1. Commitment ₹21,50,000, exposure ₹21,50,000, available ₹78,50,000.

**Corroboration.** SAP includes anticipated delivery costs in the purchase order commitment and displays them individually by origin such as freight, duty and packaging `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/157cd0531d8b4208e10000000a174cb4.html — verified 2026-08-05]`, and its own worked example commits 3 pieces at 1500.00 plus 150.00 freight as 4650.00 `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/5e23dc8fe9be4fd496f8ab556667ea05/2a7cd0531d8b4208e10000000a174cb4.html — verified 2026-08-05]` (both SAP S/4HANA on-premise, Project System).

**The harder case.** Freight billed separately by a third-party forwarder, with no purchase order, is BR-12: it increases actual with no commitment to relieve and therefore raises exposure at posting. §22.9 case T16 works it through.

**Provenance.** `MASTER-PROMPT` (freight and duty); the client PDF never mentions freight (CONF-15).

### 21.10 Group G — Tax treatment

#### BR-25 — The tax policy switch

**Statement.** A single organisation-level configuration, `capex_budget_tax_basis`, takes one of two values and determines the value on which every commitment, actual and availability figure is computed.

| Value | Meaning | Commitment and actual are measured at |
|---|---|---|
| `NET_OF_RECOVERABLE_TAX` | Approved budgets are stated exclusive of recoverable input tax | Line net value + non-creditable tax + landed cost |
| `GROSS_OF_TAX` | Approved budgets are stated inclusive of all tax | Line gross value including all tax |

**This is a blocking clarification, not a design choice we may make.** The client document never states whether approved CAPEX budgets are inclusive or exclusive of tax, and this single answer changes the value of every figure in its own sections 6, 7 and 12 (CONF-15). The blueprint models both and takes no tax position. No legal or tax conclusion is drawn anywhere in this document.

**Provenance.** `MASTER-PROMPT`; unresolved, CONF-15.

#### BR-26 — Three-column storage

**Statement.** Every Commitment Ledger and Actual Ledger row stores `gross_amount`, `tax_amount` and `net_amount` separately, plus `non_creditable_tax_amount`. The control value is derived from these by BR-25, so switching policy is a configuration change, not a schema change or a data migration.

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-27 — Non-creditable tax

**Statement.** Non-creditable tax is capitalisable and is included in the control value under both policies. Recoverable input tax is included only under `GROSS_OF_TAX`.

**Worked example, all three columns side by side.** Purchase order line, net ₹20,00,000, tax at 18% = ₹3,60,000, gross ₹23,60,000.

| Input tax recoverability | Non-creditable tax | Control value under `NET_OF_RECOVERABLE_TAX` | Control value under `GROSS_OF_TAX` |
|---|---:|---:|---:|
| Fully recoverable | ₹0 | ₹20,00,000 | ₹23,60,000 |
| 50% blocked | ₹1,80,000 | ₹21,80,000 | ₹23,60,000 |
| Fully blocked | ₹3,60,000 | ₹23,60,000 | ₹23,60,000 |

Available on D1 after committing the fully-blocked case under `NET_OF_RECOVERABLE_TAX`: ₹1,00,00,000 − ₹23,60,000 = ₹76,40,000.

**Provenance.** `MASTER-PROMPT`. The recoverability determination itself is the client's tax position and is **UNVERIFIED - REQUIRES CONFIRMATION**.

#### BR-28 — Tax deducted at source does not reduce cost

**Statement.** Tax withheld from a vendor payment is a payment-side deduction and never reduces Actual CWIP. The bill's capitalisable value is unaffected by withholding.

**Worked example.** Bill of ₹12,00,000 with ₹24,000 withheld. Actual CWIP ₹12,00,000. Cash paid to the vendor ₹11,76,000. Exposure and availability are computed from ₹12,00,000.

**Provenance.** `DERIVED-RECOMMENDATION`; the client PDF never mentions withholding (CONF-15). Treatment remains subject to client policy and professional validation.

### 21.11 Group H — Foreign currency

#### BR-29 — The budget register is single-currency

**Statement.** Budgets, commitments, actuals, exposure and availability are held and controlled in one base currency, INR. Foreign-currency purchase orders and bills are translated on ingestion; the foreign amount and rate are retained on the ledger row for audit and for the variance report.

**Provenance.** `DERIVED-RECOMMENDATION`; the client PDF never mentions currency other than the rupee symbol (CONF-15).

#### BR-30 — Which rate applies to which measure

**Statement.**

| Measure | Rate | Rationale |
|---|---|---|
| Commitment at purchase order approval | The rate on the purchase order approval date | The commitment is what was promised, at the rate then known |
| Actual at billing | The rate on the bill date, as posted by Zoho ERP | The actual is what was booked |
| Remaining open commitment after a bill | Revalued to the rate used on the most recent bill for that line, or the period-end rate if later | Otherwise remaining exposure is stale and understates a depreciating rupee |
| Exchange variance | The difference between translated exposure and the exposure that would have arisen at the original rate | Reported, not hidden inside the commitment figure |

The revaluation basis is a configuration, `fx_commitment_revaluation`, with values `PO_RATE` (hold at the original rate) and `LATEST_RATE` (the default above).

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-31 — Worked example of an exchange-rate variance

Head D1, Current Approved Budget ₹1,00,00,000.

| Step | Event | Foreign | Rate | INR | Open commitment | Actual CWIP | Exposure | Available |
|---|---|---|---:|---:|---:|---:|---:|---:|
| 1 | Baseline | — | — | — | ₹0 | ₹0 | ₹0 | ₹1,00,00,000 |
| 2 | PO approved, USD 25,000 | USD 25,000 | 80.00 | ₹20,00,000 | ₹20,00,000 | ₹0 | ₹20,00,000 | ₹80,00,000 |
| 3 | Bill for USD 15,000 at 84.00 | USD 15,000 | 84.00 | ₹12,60,000 | ₹8,40,000 | ₹12,60,000 | ₹21,00,000 | ₹79,00,000 |

At step 3 the remaining USD 10,000 is revalued at 84.00 to ₹8,40,000. Exposure rises from ₹20,00,000 to ₹21,00,000 without any new order being placed. The ₹1,00,000 increase is the exchange variance and is reported as its own line on SCR-15 and SCR-25, not buried in the commitment column.

Under `PO_RATE` the remaining commitment would stay at ₹8,00,000, exposure would be ₹20,60,000 and available ₹79,40,000 — and the ₹40,000 of real exposure would be invisible until the second bill posted. That is why `LATEST_RATE` is the recommended default.

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-32 — Capitalisation of exchange differences

**Statement.** Whether an exchange difference on a foreign-currency capital acquisition is capitalised into the asset cost or taken to profit and loss is an accounting-policy determination. The application records the difference separately and applies whichever treatment is configured. It does not decide.

Marked **UNVERIFIED - REQUIRES CONFIRMATION**. No legal or tax conclusion is drawn.

**Provenance.** `MASTER-PROMPT`; CONF-15.

### 21.12 Group I — Partial billing

#### BR-33 — Partial billing moves the split, never the total

**Statement.** A bill against a purchase order line reduces open commitment and increases actual by the same value. Exposure is unchanged. Available budget is unchanged.

**Worked example, the client's own anchor, quoted verbatim from the frozen registry:**

> po 20L; actual_bill 12L; open_commitment 8L; budget_exposure 20L

On head D1 that is: open commitment ₹8,00,000, actual ₹12,00,000, exposure ₹20,00,000, available ₹80,00,000 — the same ₹80,00,000 as before the bill posted.

**Provenance.** `CLIENT-PDF`, REQ-PO-005, REQ-BILL-002.

#### BR-34 — Over-billing against a line

**Statement.** A bill line exceeding the purchase order line it references relieves commitment only down to zero. The excess becomes actual with no commitment relief and therefore increases exposure. The excess is revalidated against available budget before the row is accepted.

**Worked example.** Purchase order line ₹20,00,000, nothing billed. A bill arrives for ₹22,00,000. Open commitment `max(0, 20,00,000 − 22,00,000) = ₹0`. Actual ₹22,00,000. Exposure ₹22,00,000, up ₹2,00,000. Available on D1 ₹78,00,000. MSG-PRC-004 on SCR-17: *"Bill BILL-2026-0331 line 1 is ₹22,00,000 against purchase order line PO-2026-0114/1 of ₹20,00,000, an excess of ₹2,00,000. Confirm this is intended, or correct the bill before it is posted to CWIP."*

**Two defensible treatments, presented rather than chosen.** (a) Accept the excess as actual and let exposure rise, which is the arithmetic above and preserves the invariant. (b) Block the bill until the purchase order is amended upward, which forces the incremental value through BR-22. Option (a) is recommended because the bill already exists in Zoho ERP and blocking a posted document is not something the Control Hub can do; option (b) is available where the client wants the amendment discipline enforced. Mark for client and auditor confirmation (CONF-12).

**Provenance.** `MASTER-PROMPT`; the client PDF has no row for this position.

#### BR-35 — Multi-line and multi-head bills

**Statement.** A bill spanning several budget heads is decomposed line by line. Each line is checked, matched and posted against its own control object. There is no header-level control value.

**Worked example.** One bill with three lines: ₹8,00,000 to Civil, ₹5,00,000 to Electrical, ₹1,20,000 freight to Civil. Three Actual Ledger rows are written against two control objects: Civil ₹9,20,000 and Electrical ₹5,00,000. If Electrical has only ₹4,00,000 available, only that line raises MSG-PRC-004-style review; the Civil lines post cleanly.

**Provenance.** `DERIVED-RECOMMENDATION`. The client PDF does not state behaviour for a multi-line document spanning several budget heads.

### 21.13 Group J — Advance payment

#### BR-36 — A vendor advance is not Actual CWIP

**Statement.** A payment made to a vendor before a bill exists is a capital advance, not project cost. It does not increase Actual CWIP, does not reduce open commitment and does not change exposure or availability.

**Worked example.** Head D1 with one purchase order of ₹20,00,000, nothing received or billed. A 20 percent advance of ₹4,00,000 is paid.

| Measure | Before | After |
|---|---:|---:|
| Open PO Commitment | ₹20,00,000 | ₹20,00,000 |
| Actual CWIP | ₹0 | ₹0 |
| Exposure | ₹20,00,000 | ₹20,00,000 |
| Available Budget | ₹80,00,000 | ₹80,00,000 |
| Capital advance outstanding (memo) | ₹0 | ₹4,00,000 |

**Provenance.** `CLIENT-PDF` by implication and `DERIVED-RECOMMENDATION` explicitly, from the frozen anti-double-count rule: vendor advances are NOT actual CWIP unless the accounting policy and a source transaction support it.

#### BR-37 — Identifying an advance in Zoho ERP

**Statement.** Zoho ERP has no advance flag. An advance is a vendor payment whose bill allocation array is empty (OAS-11) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. The Control Hub therefore derives the classification.

**Derivation rule.** A vendor payment is a **candidate capital advance** when all of the following hold: the allocated amount is zero or less than the payment amount; the vendor has at least one open capital purchase order coded to a CAPEX project; and the payment date precedes the first bill on that purchase order. Candidates are listed on SCR-17 for confirmation by Finance. An unconfirmed candidate is reported but never posted as actual.

**Provenance.** `DERIVED-RECOMMENDATION` from OAS-11.

#### BR-38 — Advance adjustment against a bill

**Statement.** When a bill is posted and the advance is adjusted against it, actual increases by the **full bill value**, not by the net cash paid. The advance balance reduces by the adjusted amount. Exposure and availability follow the bill, not the cash.

**Worked example.** Continuing BR-36: a bill of ₹12,00,000 posts and ₹4,00,000 of advance is adjusted, so ₹8,00,000 is paid in cash. Actual CWIP ₹12,00,000. Open commitment ₹8,00,000. Exposure ₹20,00,000. Available ₹80,00,000. Capital advance outstanding ₹0.

**Corroboration for the netting discipline.** SAP requires that a down payment and its clearing be settled together under the same settlement rule so that they net to zero `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/a6bcb3e6679b4a31a9441939ec9430db/8ca1c6535e601e4be10000000a174cb4.html — verified 2026-08-05]` (SAP S/4HANA on-premise, Project System).

**Provenance.** `DERIVED-RECOMMENDATION`; CONF-15.

### 21.14 Group K — Retention

#### BR-39 — Retention is a payment deferral, not a cost reduction

**Statement.** Where a contract permits the buyer to withhold a percentage of each bill until a defect-liability period expires, the withheld amount is a payment deferral. Actual CWIP is recognised at the **full** bill value. Retention is tracked as a separate payable, not as a reduction of project cost.

**Worked example.** Bill of ₹12,00,000 with 5 percent retention.

| Measure | Value |
|---|---:|
| Bill value | ₹12,00,000 |
| Retention withheld (5%) | ₹60,000 |
| Cash payable now | ₹11,40,000 |
| **Actual CWIP recognised** | **₹12,00,000** |
| Open commitment relieved | ₹12,00,000 |
| Retention payable (memo) | ₹60,000 |

Exposure and available budget are computed on ₹12,00,000.

**Provenance.** `MASTER-PROMPT`; the client PDF never mentions retention (CONF-15).

#### BR-40 — Retention release

**Statement.** Releasing retention at the end of the defect-liability period is a payment event only. It does not change Actual CWIP, exposure or availability, and it does not reopen a capitalised project.

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-41 — The alternative treatment, flagged not chosen

**Statement.** Where the contract makes retention a conditional **price reduction** rather than a deferred payment — for example where unremedied defects permanently forfeit the retention — the accounting treatment differs and the retained amount should not be recognised as cost until the condition lapses. The application supports both through a per-contract flag `retention_is_price_reduction`, default false.

Marked **UNVERIFIED - REQUIRES CONFIRMATION**. This is an accounting-policy determination for Atha Group and its auditor.

**Provenance.** `MASTER-PROMPT`; CONF-15.

### 21.15 Group L — Cancellation

#### BR-42 — Cancellation before any billing

**Statement.** Cancelling a purchase order line that has never been billed and never been received releases the whole commitment and reduces that line's exposure to zero.

**Worked example, the client's own anchor position:** PO Value ₹20,00,000; Actual Bill ₹0; Open Commitment ₹0; Budget Exposure ₹0. On head D1, available returns to ₹1,00,00,000.

MSG-PRC-002 on SCR-15: *"PO-2026-0114 has been cancelled. Commitment of ₹20,00,000 has been released back to D1. Available budget is now ₹1,00,00,000."*

**Provenance.** `CLIENT-PDF`, REQ-PO-007, REQ-PO-009.

#### BR-43 — Cancellation where goods have been received

**Statement.** Cancelling a line that carries received-but-unbilled value does **not** release that portion. The commitment base switches from ordered value to received value, so the received-but-unbilled amount remains inside open commitment until it is billed or the receipt is reversed.

**Worked example.** Line ordered ₹20,00,000, received ₹12,00,000, billed ₹0. On cancellation: `commitment_base = received_value = ₹12,00,000`; `open_commitment = max(0, 12,00,000 − 0) = ₹12,00,000`. Exposure ₹12,00,000, not ₹0. Available on D1 ₹88,00,000, not ₹1,00,00,000.

**Why this matters.** Releasing the full ₹20,00,000 would drop ₹12,00,000 of goods already in the plant out of every control figure. That is exactly the under-count the design exists to prevent.

**Provenance.** `DERIVED-RECOMMENDATION`, from the `commitment_reduction_gates` ruling.

#### BR-44 — Cancellation after billing is not cancellation

**Statement.** A line that has been billed cannot be cancelled. It can only be **closed** (BR-45), or the bill must be reversed first (BR-48). Attempting to cancel a billed line is rejected with a message naming the billed value and offering both alternatives.

**Provenance.** `DERIVED-RECOMMENDATION`.

### 21.16 Group M — Closure

#### BR-45 — Closing a purchase order with a residual

**Statement.** Closing a purchase order line short releases only the unbilled residual **that is not covered by receipts**.

**Formula.**

```
released_on_closure = max(0, ordered_value - max(billed_value, received_value))
```

**Worked example A, no outstanding receipts.** Ordered ₹20,00,000, received ₹12,00,000, billed ₹12,00,000. Released = `max(0, 20,00,000 − max(12,00,000, 12,00,000)) = ₹8,00,000`. Open commitment ₹0, actual ₹12,00,000, exposure ₹12,00,000, available on D1 ₹88,00,000.

MSG-PRC-003 on SCR-15: *"PO-2026-0114 has been closed with ₹12,00,000 billed against an ordered value of ₹20,00,000. The unbilled residual of ₹8,00,000 has been released back to D1."*

**Worked example B, receipts outstanding.** Ordered ₹20,00,000, received ₹20,00,000, billed ₹12,00,000. Released = `max(0, 20,00,000 − 20,00,000) = ₹0`. Open commitment stays at ₹8,00,000, all of it received-but-unbilled. Exposure ₹20,00,000, available ₹80,00,000. When the vendor eventually bills the remaining ₹8,00,000, commitment goes to ₹0 and actual to ₹20,00,000 — exposure still ₹20,00,000.

**Provenance.** `CLIENT-PDF` for the control (REQ-PO-009); the receipts-outstanding arithmetic is `DERIVED-RECOMMENDATION`, and CONF-12 records that the client stated the control without stating the arithmetic.

#### BR-46 — Project closure has two gates, not one

**Statement.** Technical completion and financial completion are separate transitions with separate effects, and the gap between them is where the client's own step 9 review happens.

| Transition | Effect | Precondition |
|---|---|---|
| → Technically Completed | `allow_procurement = false` on the project and all descendants. New Purchase Requests and new commitments blocked. Postings still permitted | Project Manager declaration plus Plant Head approval |
| → Financially Completed | `allow_posting = false`. No further actual, no further journal | Open commitment ₹0 and received-but-unbilled ₹0, **or** an approved write-off for the remainder |
| → Closed | Terminal. Procurement and posting blocked | Financially Completed and either Capitalised or an approved abandonment |

**Provenance.** `CLIENT-PDF` for closure and the completion review (REQ-PRJ-004); the two-gate split is `DERIVED-RECOMMENDATION` resolving CONF-11.

#### BR-47 — What "resolved" means at closure

**Statement.** The client's requirement that open commitments and pending bills be "resolved" before closure has exactly three permitted resolutions per line, and one must be chosen explicitly.

| Resolution | Effect on commitment | Effect on actual | Approval |
|---|---|---|---|
| Bill received and posted | Relieved by the billed value | Increased | None beyond normal |
| Purchase order closed short | Residual released per BR-45 | None | Procurement |
| Written off | Released | Increased by the write-off if goods were received and will not be billed | Project Finance Controller plus CFO |

A line left unresolved blocks financial completion. MSG-CAP-001 lists what is outstanding.

**Provenance.** `DERIVED-RECOMMENDATION`. The client PDF does not define "resolved".

### 21.17 Group N — Reversal

#### BR-48 — Vendor credit and bill reversal

**Statement.** A vendor credit note or a bill reversal reduces Actual CWIP and restores available budget. Whether it also restores commitment depends on the state of the purchase order line.

| Purchase order line state at reversal | Commitment effect | Actual effect | Exposure effect |
|---|---|---|---|
| Live (open) | Restored automatically — `open_commitment = max(0, ordered − billed)` recomputes with the lower billed value | Reduced | **Unchanged** |
| Closed or cancelled | Not restored. `commitment_base` is the received value, so commitment restores only up to received-but-unbilled | Reduced | Reduced by the uncovered portion |
| No purchase order (direct bill) | No commitment exists | Reduced | Reduced by the full credit |

**Worked example, live line.** Ordered ₹20,00,000, billed ₹20,00,000, open commitment ₹0, actual ₹20,00,000, exposure ₹20,00,000. The bill is voided. Billed becomes ₹0, so open commitment recomputes to ₹20,00,000 and actual to ₹0. Exposure stays ₹20,00,000. Available on D1 stays ₹80,00,000. Nothing moved except the split — which is the same property partial billing has, run backwards.

**Worked example, direct bill.** Actual ₹3,00,000 from an unmatched bill, exposure ₹23,00,000. A vendor credit of ₹3,00,000 posts. Actual ₹0, exposure ₹20,00,000, available ₹80,00,000.

**Provenance.** `DERIVED-RECOMMENDATION`, from the frozen anti-double-count rule that credit notes and bill reversals reduce actual and restore available budget. CONF-12 records that the client PDF has no row for these positions.

#### BR-49 — Debit notes raised on the vendor

**Statement.** A debit note raised by Atha Group on a vendor is recorded in Zoho ERP as a vendor credit. Its effect on Actual CWIP depends on what it recovers.

| What the debit note recovers | Effect on Actual CWIP | Rationale |
|---|---|---|
| Overcharge, short supply, rejected material, rate correction | Reduces Actual CWIP | It corrects the cost of the asset |
| Liquidated damages or penalty for delay | Policy-dependent — either reduces the capitalisable cost or is recognised as other income | Depends on whether the recovery is attributable to the asset's cost |
| Recovery of a cost the vendor incurred on Atha Group's behalf and re-billed | Reduces Actual CWIP | It is a reimbursement of the same cost |

The penalty row is marked **UNVERIFIED - REQUIRES CONFIRMATION** and is configured by `debit_note_penalty_treatment`, default `REDUCE_CWIP`.

**Endpoint note.** The vendor-side credit document in the Zoho ERP specification is `vendorcredits`, and its scope family is `ERP.debitnotes` — `GET /vendorcredits` requires `ERP.debitnotes.READ` and `POST /vendorcredits` requires `ERP.debitnotes.CREATE` `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. The naming mismatch between the path and the scope is real and is catalogued in §15.4; a coding agent must not assume the scope name matches the path name.

**Worked example.** Actual ₹20,00,000 on a fully billed line. A debit note of ₹1,50,000 for short supply is raised. Actual ₹18,50,000, open commitment ₹0 (the line is closed), exposure ₹18,50,000, available on D1 ₹81,50,000.

**Provenance.** `MASTER-PROMPT`; the client PDF has no debit-note row.

#### BR-50 — Goods receipt reversal

**Statement.** Reversing a goods receipt reduces received value and therefore reduces received-but-unbilled. It does not change open commitment on a live line, does not change actual, and does not change exposure.

**Worked example.** Line ordered ₹20,00,000, received ₹12,00,000, billed ₹0. Open commitment ₹20,00,000, of which received-but-unbilled ₹12,00,000. The receipt is reversed. Open commitment stays ₹20,00,000, received-but-unbilled becomes ₹0, ordered-not-received becomes ₹20,00,000. Exposure ₹20,00,000. Available ₹80,00,000 throughout.

**Ordering rule.** A receipt may not be reversed below the billed quantity. Reverse the bill first (BR-48), then the receipt. Attempting the reverse order is rejected with the billed value named.

**Provenance.** `MASTER-PROMPT`; the client PDF has no goods-receipt-reversal row (CONF-12).

### 21.18 Group O — Budget transfer, supplement and return

#### BR-51 — Three signed revision types over one ledger

**Statement.** Supplement, return and transfer are three signed revision types written to one versioned Budget Ledger. The client's own formula continues to hold, with returns and transfers-out negative.

```
Current Approved Budget = Original Budget + Approved Supplements - Approved Returns +/- Approved Transfers
```

**The client's immutability rule is preserved exactly.** The Original Budget is never overwritten. Every revision is a separate record carrying requestor, approver, date, reason and approval reference (REQ-SEC-003, REQ-SEC-004).

**Corroboration.** SAP composes the current budget the same way — original budget together with budget supplements, budget returns and budget transfers `[source: https://learning.sap.com/courses/project-financials-control-in-sap-s-4hana/performing-budgeting-functions — verified 2026-08-05]` (SAP S/4HANA, vendor learning) — and once the original budget is locked by user status it can only be changed through supplements, returns and transfers, each of which is documented `[source: https://learning.sap.com/courses/exploring-investment-projects-in-sap-s-4hana/budgeting-projects — verified 2026-08-05]` (SAP S/4HANA, vendor learning).

**Provenance.** `CLIENT-PDF` for supplement and versioning; `MASTER-PROMPT` for return and transfer, which the client formula as written cannot express (CONF-13).

#### BR-52 — Revision record contents

**Statement.** Every Budget Revision record carries, without exception: revision number, revision type (`SUPPLEMENT`, `RETURN`, `TRANSFER_IN`, `TRANSFER_OUT`), source control object where applicable, target control object, amount, reason, requestor, approver, approval date, approval reference, effective date and version number.

**Worked example of the resulting version history on SCR-10.**

| Version | Type | Head | Amount | Current Approved Budget after | Approved by | Date |
|---|---|---|---:|---:|---|---|
| V1 | Original | D1 | ₹1,00,00,000 | ₹1,00,00,000 | CAPEX Committee | 20-Apr-2026 |
| V2 | Supplement | D1 | ₹10,00,000 | ₹1,10,00,000 | CFO | 12-Aug-2026 |
| V3 | Transfer out | D1 | (₹5,00,000) | ₹1,05,00,000 | CAPEX Committee | 03-Oct-2026 |
| V4 | Return | D1 | (₹2,00,000) | ₹1,03,00,000 | CFO | 15-Jan-2027 |

Original Budget still reads ₹1,00,00,000 at every version. That is the client's own control (REQ-SEC-003) rendered as a table.

**Provenance.** `CLIENT-PDF` and `MASTER-PROMPT` combined.

#### BR-53 — The transfer guard

**Statement.** A transfer out of a control object may not exceed that object's available budget. A transfer that would drive availability negative is rejected with the maximum transferable amount stated.

**Formula.**

```
max_transferable(source) = max(0, current_approved_budget - exposure)
```

**Worked example.** Head D1: Current Approved Budget ₹1,00,00,000, open commitment ₹60,00,000, actual ₹25,00,000, exposure ₹85,00,000, available ₹15,00,000. A transfer of ₹20,00,000 to Electrical is requested. It is rejected. MSG-BUD-006 on SCR-12: *"Transferring ₹20,00,000 from D1 would leave it with negative availability of (₹5,00,000), because ₹85,00,000 is already committed. Reduce the transfer to at most ₹15,00,000."*

**Provenance.** `MASTER-PROMPT`; CONF-13 records "budget transfer after commitment" as an edge case the client must confirm.

#### BR-54 — Transfers are net-zero at the level above

**Statement.** Every transfer writes two rows — `TRANSFER_OUT` on the source and `TRANSFER_IN` on the target — of equal magnitude and opposite sign, both carrying the same approval reference. A transfer between two heads of the same project leaves the project's Current Approved Budget unchanged. A transfer between projects changes both project totals and requires CFO approval.

**Provenance.** `MASTER-PROMPT`. Whether Atha Group permits inter-project transfers at all is an open question (CONF-13).

### 21.19 Group P — Reclassification

#### BR-55 — Budget-head reclassification of posted actual

**Statement.** Moving a posted actual from one budget head to another is a reclassification, not a budget change. It writes two Actual Ledger rows — a negative on the source and a positive on the target — with the same reclassification reference, and posts a corresponding journal in Zoho ERP coded at line level. The budget on neither head changes.

**Availability rule.** The **receiving** head is revalidated. The sending head is not, because its availability can only improve. If the receiving head cannot absorb the value, the reclassification routes to exception approval exactly like any other over-budget transaction.

**Worked example.** ₹6,00,000 of civil work was miscoded to Electrical. Electrical: budget ₹20,00,000, commitment ₹6,00,000, actual ₹8,00,000, available ₹6,00,000. Civil: budget ₹25,00,000, commitment ₹5,00,000, actual ₹12,00,000, available ₹8,00,000.

| Head | Before actual | After actual | Before available | After available |
|---|---:|---:|---:|---:|
| Electrical | ₹8,00,000 | ₹2,00,000 | ₹6,00,000 | ₹12,00,000 |
| Civil | ₹12,00,000 | ₹18,00,000 | ₹8,00,000 | ₹2,00,000 |

Civil absorbs ₹6,00,000 against ₹8,00,000 available → `PASS`. Had Civil held only ₹4,00,000 available, the reclassification would fail with MSG-BUD-001 naming a shortfall of ₹2,00,000, and the user's next action would be a transfer or a revision.

**Zoho mechanics.** The correcting journal is posted with `POST /journals` carrying `project_id` and `tags` on each line; journal lines carry `project_id` and `tags` while bill headers do not (OAS-10) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`.

**Provenance.** `MASTER-PROMPT`.

#### BR-56 — WBS reclassification

**Statement.** Moving a transaction from one WBS element to another follows BR-55 exactly, one level down. Where both elements roll up to the same budget-carrying ancestor and neither carries its own budget, no availability check is needed because no control object changes; the move is presentational and is recorded as such.

**Provenance.** `MASTER-PROMPT`; CONF-02 applies.

#### BR-57 — Reclassification of commitment

**Statement.** An open commitment may be reclassified only by amending the coding on the Zoho ERP purchase order line, never by a Control Hub-only adjustment. The Control Hub writes an outbound update, waits for the change to appear on the next poll, and only then moves the Commitment Ledger rows. Until it does, the commitment remains on the original control object.

**Why.** A Control Hub-only move would put our commitment figure and Zoho's purchase order coding permanently out of agreement, and the nightly reconciliation would raise MSG-INT-006 every night thereafter.

**Provenance.** `DERIVED-RECOMMENDATION`.

### 21.20 Group Q — Reopening a closed project

#### BR-58 — Reopening is an approved, reasoned, audited act

**Statement.** A project in status Capitalised or Closed blocks all procurement and all posting. Reopening requires an approval from the CAPEX Committee or CFO band per the approval matrix, a mandatory free-text reason, and sets status Reopened.

**Message.** MSG-PRC-006 on the blocked attempt: *"CAPEX-2026-001 is Closed. Procurement is not permitted. Request a controlled reopening, which requires CAPEX Committee approval and a recorded reason."* MSG-SEC-003 on the override itself: *"You are overriding project closure for CAPEX-2026-001. A reason is mandatory and will be stored in the audit trail with your name and the current time."*

**Provenance.** `CLIENT-PDF`, REQ-CAP-002. The status `Reopened` itself is a `MASTER-PROMPT` addition, since the client requires reopening but lists no such status (CONF-11).

#### BR-59 — What reopening restores

**Statement.** On transition to Reopened: `allow_procurement` and `allow_posting` are set true; the budget register is re-armed at its last approved version, not at the original; all exposure thresholds are re-armed so alerts can fire again; and any capitalisation already posted is **not** reversed.

**Worked example.** CAPEX-2026-001 was capitalised at ₹1,42,00,000 against a Current Approved Budget of ₹1,50,00,000. It is reopened to book a ₹3,00,000 commissioning bill that arrived late. On reopening: budget ₹1,50,00,000, actual ₹1,42,00,000, exposure ₹1,42,00,000, available ₹8,00,000. The bill posts, actual becomes ₹1,45,00,000, available ₹5,00,000. A second capitalisation request then transfers the incremental ₹3,00,000 to the same asset.

**Provenance.** `DERIVED-RECOMMENDATION`.

#### BR-60 — Reopening is time-boxed and reported

**Statement.** A reopened project carries a mandatory target re-closure date. Reopened projects appear on SCR-25 until closed again, and the audit trail records who reopened, when, why and how long it stayed open.

**Provenance.** `DERIVED-RECOMMENDATION`.

### 21.21 Group R — Capitalisation

#### BR-61 — What is capitalisable

**Statement.** The CWIP balance at capitalisation is split into a capitalisable portion, which becomes fixed-asset cost, and a non-capitalisable portion, which is expensed. The split is driven by a per-budget-head capitalisation rule, overridable per capitalisation request with a reason.

**The qualifier that must not be dropped.** With no capitalisation key, the system settles all debits **not assigned to CO receivers** to the asset under construction during periodic settlement. Asserting that 100 percent of debits reach the asset would model CWIP as a total-cost sink and erase the non-capitalisable and pre-operative-expense write-off path entirely. Both paths are modelled: capitalisable debits to the asset, and debits routed to cost-centre receivers by a prior rule which never reach the asset.

**Corroboration.** SAP specifies the capitalisable percentage of each cost element or activity type in a capitalisation key `[source: https://help.sap.com/doc/saphelp_me60/6.0.4/en-US/56/a1c6535e601e4be10000000a174cb4/content.htm?no_cache=true — verified 2026-08-05]`, defined at company code level `[source: https://help.sap.com/doc/saphelp_me60/6.0.4/en-US/56/a1c6535e601e4be10000000a174cb4/content.htm?no_cache=true — verified 2026-08-05]` (SAP classic on-premise Investment Management). Settlement credits reduce assigned value only when the receiving object is itself budget-controlled, so settling to a cost centre does not free budget `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/f711d553088f4308e10000000a174cb4.html — verified 2026-08-05]` (SAP S/4HANA on-premise, Project System).

**Provenance.** `CLIENT-PDF` for "eligible CWIP" (REQ-CAP-001); the eligibility criteria themselves are undefined in the client document and the two-path model is `DERIVED-RECOMMENDATION`.

#### BR-62 — Capitalisation does not restore budget

**Statement.** Transferring value from CWIP to a fixed asset does not increase available budget. The budget was consumed when the cost was incurred.

**Worked example.** Head D1: budget ₹1,00,00,000, commitment ₹0, actual ₹92,00,000, exposure ₹92,00,000, available ₹8,00,000. ₹92,00,000 is capitalised. After capitalisation: actual ₹92,00,000 (the ledger is not cleared, it is marked capitalised), exposure ₹92,00,000, available ₹8,00,000 — **identical**. The CWIP GL balance falls to ₹0; the control figures do not move.

**Provenance.** `DERIVED-RECOMMENDATION`. This is the single most common misunderstanding in CAPEX control systems and is stated explicitly for that reason.

#### BR-63 — The allocation must total the balance

**Statement.** The sum of all Asset Allocation lines plus any recorded write-off must equal the CWIP balance being capitalised, to the paisa. A shortfall or excess blocks submission.

**Worked example.** CWIP balance ₹1,42,00,000. Allocation: Building ₹38,00,000; Plant and machinery ₹86,00,000; Electrical installations ₹11,50,000; write-off to pre-operative expense ₹6,50,000. Total ₹1,42,00,000 → accepted.

Had the write-off line been omitted, MSG-CAP-002 on SCR-22: *"The allocation totals ₹1,35,50,000 against a CWIP balance of ₹1,42,00,000, a difference of ₹6,50,000. Allocate the full balance across assets, or record the remainder as a write-off with a reason."*

**Provenance.** `DERIVED-RECOMMENDATION`; the client PDF does not define partial capitalisation or componentisation.

#### BR-64 — Capitalising with open items

**Statement.** Capitalisation while open commitment or received-but-unbilled value remains is permitted but warned, because blocking it would strand assets already in use.

**Message.** MSG-CAP-001 on SCR-21: *"CAPEX-2026-001 has ₹4,00,000 in open commitments and ₹1,20,000 received but unbilled. Resolve or explicitly write off these before capitalising, or the asset value will be understated."*

**Completion message.** MSG-CAP-003: *"CAPEX-2026-001 capitalised on 20-Mar-2027. ₹1,42,00,000 transferred from CWIP to 3 fixed asset(s). The project is now Capitalised and closed to further procurement."*

**Traceability constraint.** Fixed assets carry no link to a source project, purchase order or bill, and the asset list endpoint offers no last-modified filter (OAS-09) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. Traceability is therefore anchored on the Control Hub's own Capitalisation Request and Asset Allocation records, which hold the returned `fixed_asset_id` for each allocation line.

**Provenance.** `CLIENT-PDF` for the completion review (REQ-PRJ-004); the warn-not-block rule is `DERIVED-RECOMMENDATION`.

### 21.22 Group S — Abandoned project

#### BR-65 — An abandoned project never capitalises

**Statement.** Where a capital project is abandoned, no asset is created. Open commitments are cancelled, received-but-unbilled value is either billed or written off, and the accumulated CWIP balance is written off to profit and loss under approval.

**Sequence.**

1. Project status → Technically Completed with reason `ABANDONED`. Procurement blocks immediately.
2. Every open purchase order line is cancelled (BR-42) or closed (BR-45). Received-but-unbilled is settled per BR-47.
3. A write-off request is raised for the full remaining CWIP balance, approved by CFO.
4. The write-off journal posts, WBS-coded at line level.
5. Project status → Financially Completed, then Closed. Status **never** passes through Capitalised.
6. The residual budget is returned (BR-51, type `RETURN`) so the project's Current Approved Budget reflects what was actually authorised to be lost.

**Worked example.** CAPEX-2026-004, Current Approved Budget ₹40,00,000, open commitment ₹6,00,000, actual CWIP ₹18,00,000, exposure ₹24,00,000, available ₹16,00,000.

| Step | Open commitment | Actual CWIP | Exposure | Available | Current Approved Budget |
|---|---:|---:|---:|---:|---:|
| Abandonment declared | ₹6,00,000 | ₹18,00,000 | ₹24,00,000 | ₹16,00,000 | ₹40,00,000 |
| Purchase orders cancelled, no receipts | ₹0 | ₹18,00,000 | ₹18,00,000 | ₹22,00,000 | ₹40,00,000 |
| CWIP ₹18,00,000 written off to profit and loss | ₹0 | ₹0 | ₹0 | ₹40,00,000 | ₹40,00,000 |
| Budget return of ₹40,00,000 approved | ₹0 | ₹0 | ₹0 | ₹0 | ₹0 |

The final row is the point: after the return, the project carries no budget and no exposure, so it cannot be quietly restarted without a new approval.

**Provenance.** `MASTER-PROMPT`; the client PDF has no abandonment path at all.

#### BR-66 — Partial abandonment

**Statement.** Where part of a project is abandoned and part is completed, the abandonment is scoped to WBS elements or budget heads. The completed portion capitalises normally; the abandoned portion follows BR-65 at its own control objects.

**Provenance.** `MASTER-PROMPT`.

#### BR-67 — The write-off is not silent

**Statement.** A CWIP write-off requires MSG-SEC-003 with a mandatory reason, appears on SCR-25 until approved, and is listed permanently in the audit trail with the approving CFO named. It is one of the two irreversible acts in the application, the other being capitalisation, and both use the dialog placement rule with the consequence stated explicitly (MSG-GEN-001).

**Provenance.** `DERIVED-RECOMMENDATION`.

### 21.23 Group T — Data reconciliation

#### BR-68 — Three reconciliations, not one

**Statement.** Reconciliation runs on three independent axes. Each has its own frequency, tolerance and breach action, and each writes a Reconciliation Log row whether it passes or fails.

| # | Reconciliation | Our side | Zoho side | Frequency | Tolerance | Breach |
|---|---|---|---|---|---|---|
| RC-A | Commitment | Commitment Ledger open balance per purchase order line | `GET /purchaseorders` line values and statuses | Nightly, plus on demand | ₹0.00 on value; ±1 status-transition lag | Reconciliation Pending; MSG-INT-006 |
| RC-B | Actual | Actual Ledger per `(bill_id, line_item_id)` | `GET /bills` filtered on `last_modified_time` | Nightly, plus on demand | ₹0.00 on value | Reconciliation Pending; MSG-INT-006 |
| RC-C | CWIP balance | Sum of Actual Ledger not yet capitalised, per CWIP control account | Zoho ERP CWIP account balance | Monthly, at period close | ₹1.00 per document for tax rounding, ₹0.00 in aggregate | Escalate to Finance; block capitalisation until cleared |

**Provenance.** `MASTER-PROMPT` for the reconciliation requirement; the three-axis split is `DERIVED-RECOMMENDATION`.

#### BR-69 — Line-level reconciliation of purchase order, receipt and bill

**Statement.** For each purchase order line the reconciliation asserts:

```
ordered_qty  >= received_qty                        unless over-receipt is flagged
ordered_value >= billed_value                       unless over-billing is flagged (BR-34)
open_commitment + billed_value == commitment_base   always, no exception
received_but_unbilled + ordered_not_received == open_commitment   always, no exception
```

The last two are invariants, not tolerances. A breach is a defect in our own arithmetic, not a data difference, and raises a system alert rather than a reconciliation exception.

**The receipt leg is weaker than the other two, and the report says so.** Receipt lines carry no purchase order line link (OAS-03), so the receipt-to-order match is reconstructed and carries a confidence flag. SCR-27 shows `MATCH: EXACT`, `MATCH: INFERRED` or `MATCH: AMBIGUOUS — MANUAL ASSIGNMENT REQUIRED`. An ambiguous row is never silently resolved.

**Provenance.** `MASTER-PROMPT`, POC step 36.

#### BR-70 — What happens on a difference

**Statement.** A difference beyond tolerance sets the affected object's status to Reconciliation Pending, raises MSG-INT-006, and marks every report containing that object. It does **not** auto-correct.

**Message.** *"Purchase Order PO-2026-0114: our value ₹20,00,000 differs from Zoho's ₹22,00,000 by ₹2,00,000, beyond the tolerance of ₹0.00. Investigate before relying on the affected report."*

**Provenance.** `MASTER-PROMPT`; MSG-INT-006.

#### BR-71 — Reconciliation is Zoho-authoritative for the four mirrored entities

**Statement.** Where the Control Hub and Zoho ERP disagree on a Purchase Order Reference, PO Line, GRN Reference or Vendor Bill Reference, **Zoho ERP wins**. Our row is corrected to match and the correction is logged. For every other entity the Control Hub is authoritative and no correction is applied from Zoho.

**Why this asymmetry is safe.** Those four entities are procurement and accounting records that Zoho owns by design. Budget, WBS, Purchase Request and every control decision are ours and are never overwritten by an inbound sync.

**Provenance.** `DERIVED-RECOMMENDATION`, consistent with §13 Source-of-Truth Matrix.

#### BR-72 — Reconciliation before capitalisation is a hard gate

**Statement.** A capitalisation request cannot be submitted while any object on that project carries status Reconciliation Pending. This is the only place reconciliation blocks rather than warns, because capitalisation is irreversible and a wrong CWIP balance becomes a wrong asset value that depreciates for years.

**Provenance.** `DERIVED-RECOMMENDATION`.
