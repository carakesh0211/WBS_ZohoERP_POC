## 15. OAuth, Credential and Scope Management

### 15.1 The headline: the real scope surface is 163 scopes, not 16

Zoho's published OAuth documentation page for the ERP API lists **16 scope families**. The vendor's own machine-readable specification declares **44 scope families and 163 distinct scopes** across 869 operations. Any least-privilege design built from the documentation page will be wrong in both directions: it will omit scopes the connector actually needs, and it will over-grant where the page's coarse families hide narrower ones.

| Source | Scope families | Distinct scopes | Evidence |
|---|---|---|---|
| Published OAuth documentation page | 16 | not enumerated as CRUD variants | Regex extraction over the rendered page returns exactly 16 families, in this order: contacts, settings, manufacturing, estimates, invoices, customerpayments, creditnotes, projects, expenses, salesorders, purchaseorders, bills, debitnotes, vendorpayments, banking, accountants `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Official OpenAPI bundle | **44** | **163** | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` |

28 of the 44 families are absent from the published page altogether — including `ERP.fixedasset.*`, without which capitalisation cannot read or write assets, and `ERP.department.*`, without which the plant/department dimension cannot be synced. The engagement's mechanical verification recorded this as finding **OAS-07**: least-privilege scope design must be driven from the specification, not from the documentation page.

**Binding rule for implementers.** The `required_scopes` generator (wizard step 7, §14.8) reads the API Endpoint Catalogue, which is seeded from the endpoint inventory in §17 Zoho ERP Endpoint Inventory. It never reads a documentation page and never accepts a hand-typed scope. A scope string that does not appear in the 163-scope inventory is a build-blocking defect, not a runtime warning.

### 15.2 Scope grammar

*"The format to define a scope is"* / *"scope = service_name.scope_name.operation_type"* `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`.

| Element | Values in the ERP surface | Notes |
|---|---|---|
| `service_name` | `ERP` | Every one of the 163 scopes begins `ERP.` |
| `scope_name` | 44 distinct values | Not the same as the module name and not the same as the path segment — see §15.4 |
| `operation_type` | `CREATE`, `READ`, `UPDATE`, `DELETE`, `ALL` | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |

Requested scopes are transmitted as a comma-separated list on the authorisation request. The mandatory authorisation parameters printed by the vendor are `client_id`, `response_type` (value must be `code`), `redirect_uri` and `scope`, with `access_type` and `prompt` described as the offline/consent controls `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`.

**Specification anomaly worth recording.** The OpenAPI bundle declares its security scheme `Zoho_Auth` as OAuth 2.0 with an **implicit** flow, while the ERP OAuth documentation describes an authorisation-code exchange producing a refresh token `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. This design implements the **authorisation-code** flow described in the documentation, because it is the only flow that yields a refresh token and the only one suitable for a server-side connector. The implicit declaration in the specification is treated as a specification artefact and is recorded as an open question for Zoho in §44 Open Questions. No part of this design uses an implicit-flow token.

### 15.4 Naming inconsistencies — a register, not a complaint

Scope strings in this surface do not follow one rule. Every inconsistency below is a real source of runtime failure, because a scope is a literal string and a plausible-looking guess simply does not authorise anything. Implementers must copy scope strings from the endpoint inventory, never derive them from a module name, a path segment or a documentation heading.

The scope request is assembled deterministically:

```
function required_scopes(profile):
    scopes = {}
    for module in profile.selected_modules:
        for operation in catalogue.operations_for(module, profile.direction):
            scopes.add(catalogue.scope_for(operation))       # literal string from the inventory
    assert every s in scopes exists in SPEC_SCOPES_163        # build-blocking otherwise
    assert no s ends with ".ALL" unless no narrower variant exists for that family
    assert no write scope present when profile.direction == "Inbound"
    return sorted(scopes)
```

The two assertions are the least-privilege enforcement. They run at build time against the seeded catalogue and again at wizard step 7 against the live profile.

### 15.6 Scope-elevation traps

Four places where the granularity of the scope model is coarser than the granularity of the action, so that requesting what you need necessarily grants more than you need. Each must be disclosed to the client's security reviewer rather than discovered by them.

| # | Trap | Mechanism | Mitigation |
|---|---|---|---|
| T1 | **Approval is CREATE.** `POST /purchaseorders/{purchaseorder_id}/approve`, `/submit`, `/status/open`, `/status/billed` and `/status/cancelled` all require `ERP.purchaseorders.CREATE`. There is no approve-only scope, and `ERP.approval.CREATE` covers only expense reports and trips (N7). The same pattern holds for bills (`POST /bills/{bill_id}/approve` → `ERP.bills.CREATE`) and journals (`POST /journals/{journal_id}/approve` → `ERP.accountants.CREATE`) | Zoho's scope model treats resource actions as creations | Do not request `ERP.purchaseorders.CREATE` unless the client chooses PO creation from this application. Approval of a Zoho purchase order stays a Zoho-side act by default. Recorded as a design decision in §13 Source-of-Truth Matrix |
| T2 | **Journal write implies chart-of-accounts write.** `ERP.accountants.CREATE` is required to post a journal and simultaneously authorises `POST /chartofaccounts`, `POST /chartofaccounts/{account_id}/active` and `/inactive` | One family, many resources (N4) | Compensating control, not a scope control: the connector's own outbound allow-list permits exactly the journal operations in §23 Accounting Design and rejects any other `ERP.accountants.CREATE` call at the HTTP client layer, logging the attempt as a security event. Disclose the residual risk |
| T3 | **`ERP.settings.READ` is unavoidably broad.** It is required simply to discover the organisation, and it also grants read on users, items, locations, reporting tags, taxes, currencies and tasks (N8) | The organisation-discovery operation is scoped to the settings family | Accept for READ; **never** request `ERP.settings.CREATE/UPDATE/DELETE`. Manual creation of reporting tags (prerequisite P3, §14.5) exists precisely to avoid requesting settings-write |
| T4 | **`ERP.custommodules.ALL` has no narrower form.** If the Purchase Request fallback is implemented as a Zoho custom module rather than in this application, the only available scope grants create, read, update and delete on **every** custom module in the organisation | Only `ALL` is declared (N6) | This is a material argument for the recommended CONF-01 resolution: **Purchase Request is owned by this application**, so `ERP.custommodules.ALL` is never requested. If the client insists on a Zoho custom module, the scope consequence must be put in writing before the decision |

The setup completion report (§14.8.2) prints an **over-grant list**: every scope present in `granted_scopes` but absent from `required_scopes`. A non-empty over-grant list is not an error — an administrator may have consented to a broader set on a shared OAuth client — but it is shown on SCR-38 permanently, so the gap between what was granted and what is used never becomes invisible.

Screen behaviour:

- Grouped by severity, `Blocking` first. A `Blocking` row present anywhere prevents the profile leaving `Draft`.
- Rows are generated, never authored. The screen has no create action.
- A **Re-authorise** action rebuilds the scope request from the current `required_scopes` and re-runs wizard steps 8–11 without disturbing organisation mapping or field mappings.
- An **Export** action produces the same grid as CSV for the client's security review, with no token material of any kind.
- Business-impact text is stored on the OAuth Scope Requirement entity as seeded content, so it is reviewed once and reads consistently rather than being composed at runtime.

Message raised per missing scope, `MSG-INT-001` (error): *"The connected Zoho organisation is missing the scope {scope}, required for {module}. {impact} Re-authorise the connection and grant this scope."*

Worked instance: *"The connected Zoho organisation is missing the scope `ERP.fixedasset.READ`, required for Capitalisation. Fixed assets cannot be read, so a capitalisation request cannot be matched to an existing asset and every capitalisation must be completed manually in Zoho. Re-authorise the connection and grant this scope."*

### 15.8 Missing-scope detection

This is harder than it looks, because the vendor documents **no scope-specific error**. The documented status codes are exactly 200, 201, 400, 401, 404, 405, 429 and 500 — `403`, `409` and `422` do not appear — and 401 is documented as *"Unauthorized (Invalid AuthToken)"*, with no "insufficient scope" status anywhere `[source: https://www.zoho.com/erp/api/v3/errors/ — verified 2026-08-05]`. A 401 therefore cannot, by itself, distinguish *expired token* from *revoked token* from *missing scope*.

Detection is consequently layered, and proactive detection is the primary mechanism:

| Layer | Mechanism | When it runs | Detects |
|---|---|---|---|
| L1 — Declarative | Compare `granted_scopes` (from the token response) with `required_scopes` | At token exchange, at every refresh, and on every health check | Missing scope, over-grant, consent change |
| L2 — Probe | Connectivity Test Console (§14.10): one cheap read per required scope | Wizard steps 15–17, on demand, and on a daily schedule in production | Scope that was granted but has since been withdrawn, and module access lost because the connector's Zoho user lost a role |
| L3 — Reactive | 401 classification on any operational call | Continuously | Distinguishes the three 401 causes using the decision procedure below |
| L4 — Behavioural | Empty result set from an operation that has previously returned data, with no filter change | On every incremental sync | Silent permission loss that manifests as no rows rather than an error |

The 401 classification procedure — this is the part an implementer will otherwise get wrong:

```
on HTTP 401 for operation OP with scope S:
    # 1. Is the access token merely stale?
    if access_token_expiry <= now + skew:
        refresh_access_token()                    # §15.10, single-flight
        retry OP once
        if success: classify = "EXPIRED_TOKEN"; return

    # 2. Refresh succeeded but the call still fails - probe the cheapest
    #    operation governed by a scope we are certain of.
    probe = GET /organizations                    # ERP.settings.READ, no org id, no params
    if probe fails with 401:
        classify = "TOKEN_REVOKED_OR_CONSENT_WITHDRAWN"
        set oauth_grant_status = "Revoked"
        set connection_status  = "Integration Failed"
        raise MSG-INT-002
        pause scheduler; retain queued work
        return

    # 3. Probe succeeded, so the token is alive; the failure is scope-specific.
    if S not in granted_scopes:
        classify = "MISSING_SCOPE"                # declarative confirmation
    else:
        classify = "SCOPE_GRANTED_BUT_INEFFECTIVE"
        # granted at consent, but the connector's Zoho user has lost module access
    mark OP row on SCR-34 as failing with the classification
    raise MSG-INT-001 for scope S
    disable only the affected sync object; the rest of the connector keeps running
```

Two properties of this procedure are deliberate. First, **failure is partitioned**: a missing `ERP.fixedasset.READ` stops capitalisation sync and nothing else; it does not take the connector down. Second, **no automatic re-consent** is ever attempted — re-authorisation always requires a human administrator, because a silent re-consent would defeat the audit trail.

The five conditions the brief requires the application to detect, mapped to layers:

| Condition | Detected by | Status set | Message |
|---|---|---|---|
| A required scope is missing | L1 at exchange/refresh; L3 confirms at call time | `Draft` (pre-live) or per-object disable (live) | `MSG-INT-001` |
| A token has been revoked | L3 step 2 probe; also L1 when a refresh returns an error | `Integration Failed`, `oauth_grant_status = Revoked` | `MSG-INT-002` |
| Consent has changed | L1 — `granted_scopes` differs from the previously recorded set | Recorded on Connector Audit Log; `Draft` if a required scope was lost | `MSG-INT-001` per lost scope |
| An administrator has connected the wrong Zoho organisation | Health check compares `organization_id`, `name`, `currency_code` and `fiscal_year_start_month` against the stored snapshot | Blocked before any sync runs | `MSG-INT-005` |
| A connector user no longer has access to a required module | L2 probe fails or L4 detects an unexplained empty set, while the L3 probe succeeds ⇒ `SCOPE_GRANTED_BUT_INEFFECTIVE` | Per-object disable | `MSG-INT-001` with remediation naming the Zoho role, not the scope |

The last row is the one that scope comparison alone cannot catch: consent is granted to an *application* but data access is governed by the *Zoho user's* role. A scope can be present and still authorise nothing. Only a probe distinguishes the two.

### 15.9 Token lifecycle facts

Every value in this table is vendor-documented. None of it may be adjusted by configuration, and no design in this blueprint depends on a longer lifetime than is documented here.

| Token / artefact | Lifetime | Where it lives in this design | Evidence |
|---|---|---|---|
| Authorisation code (grant code) | **2 minutes** — *"this code will be valid for 2 minutes"* | In memory only, for the duration of the exchange. Never logged, never persisted | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Access token | **1 hour** — *"Each access token is valid only for an hour and can be used only for the operations that are specified in the scope."* | Encrypted short-lived cache keyed on `connection_profile_id`; never written to the connection-profile row | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Refresh token | **Does not expire** — *"A refresh token does not expire."* and *"This token has an unlimited lifetime until it is revoked by the end-user."* | Secret store, referenced by handle (`refresh_token_ref`) | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Refresh-token count per user | **Maximum 20.** *"Note: Each time a re-consent is accepted, a new refresh token is generated. The maximum limit is 20 refresh tokens per user. If this limit is crossed, the first refresh token is automatically deleted to accommodate the latest one. This is done irrespective of whether the first refresh token is in use or not."* | Governs the re-consent policy in §15.10.3 | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Authorisation endpoint | `{Accounts_URL}/oauth/v2/auth` | Built from `accounts_domain` (§14.6) | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Token endpoint | `{Accounts_URL}/oauth/v2/token` | Built from `accounts_domain` | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| `api_domain` | Returned in the token response | Written to connection-profile field 8; never typed | `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| Revocation endpoint | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** | See §15.12 | No citable evidence for a revocation path was found in this engagement's evidence set |

**The 20-token eviction hazard, stated plainly.** Because a new refresh token is minted on every re-consent, and the oldest is deleted once 20 exist *irrespective of whether it is in use*, an organisation that re-authorises repeatedly — during a setup workshop, or across development, test and production profiles that share one Zoho user — can silently destroy a production refresh token. The connector's first symptom is a refresh failure with a live-looking configuration.

Design responses, all mandatory:

1. **One Zoho authorising user per environment.** Production consent is never granted by the same Zoho user that development and test use. This is the single most effective mitigation and it is a client-side operational rule, recorded in §45 Client Clarification Questionnaire.
2. **Re-consent counter.** The connector records every consent event per (Zoho authorising user, environment) on the Connector Audit Log and shows the running count on SCR-38. At 15 the dashboard raises an advisory; at 18 it raises a warning naming the eviction rule.
3. **Never re-consent automatically.** Re-authorisation is always an explicit administrator act (§15.8).
4. **Refresh failure is treated as possible eviction, not only as revocation.** The `Integration Failed` remediation text names both causes so the administrator checks the right thing first.

### 15.10 Refresh, and the concurrency problem

#### 15.10.1 The documented refresh call

The vendor's own refresh example places the refresh token, client id and client secret **in the URL query string**, and sets `Content-Type: application/data`:

```
POST https://accounts.zoho.in/oauth/v2/token?refresh_token=…&client_id=…&client_secret=…&redirect_uri=…
```

`[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`

**This design does not reproduce that shape without compensating controls, and the reason is a security one.** Secrets in a query string are logged by proxies, reverse proxies, load balancers and browser-adjacent tooling by default; they appear in access logs and in error reports. §26 Integration Security and Secret Management specifies the compensating controls: form-encoded body preferred where the endpoint accepts it, mandatory URL redaction in every logging sink, and outbound HTTP logging that records method, host, path and status but never the query string for the accounts domain. Where Zoho's endpoint accepts only the documented query-string form, the call is made through a dedicated client whose logging is disabled at the transport layer and whose URLs are never passed to the shared logger.

Whether the token endpoint also accepts a standard `application/x-www-form-urlencoded` request body is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**; the documented example uses the query string and `application/data`. The implementation attempts the body form first and falls back to the documented form, recording which form succeeded on the connection profile so the behaviour is observable rather than assumed.

#### 15.10.2 Refresh algorithm

```
function get_access_token(profile):
    token = cache.get(profile.id)
    if token and token.expires_at > now + SKEW:            # SKEW = 120 s
        return token

    # Single-flight: exactly one refresh per profile at a time, cluster-wide.
    lease = distributed_lock.acquire("refresh:" + profile.id, ttl = 30 s)
    if not lease:
        wait_for_refresh(profile.id, timeout = 30 s)       # follower path
        return cache.get(profile.id) or fail("REFRESH_TIMEOUT")

    try:
        refresh_token = secret_store.resolve(profile.refresh_token_ref)
        client_id     = secret_store.resolve(profile.client_id_ref)
        client_secret = secret_store.resolve(profile.client_secret_ref)

        response = accounts_client.post_token(
            accounts_domain = profile.accounts_domain,
            grant_type      = "refresh_token",
            refresh_token   = refresh_token,
            client_id       = client_id,
            client_secret   = client_secret,
            redirect_uri    = profile.redirect_uri)        # logging disabled on this client

        if response.ok:
            cache.put(profile.id, response.access_token,
                      expires_at = now + 3600 s)           # documented one-hour lifetime
            profile.access_token_expiry     = now + 3600 s
            profile.token_last_refreshed_at = now
            profile.api_domain              = response.api_domain or profile.api_domain
            profile.granted_scopes          = parse_scopes(response.scope)
            reconcile_scopes(profile)                      # §15.8 layer L1
            profile.oauth_grant_status      = "Granted"
            audit("TOKEN_REFRESHED", profile, actor = "system")
        else:
            profile.oauth_grant_status = "Refresh failing"
            increment_consecutive_refresh_failures(profile)
            if consecutive_refresh_failures(profile) >= 3:
                profile.oauth_grant_status = "Revoked"
                profile.connection_status  = "Integration Failed"
                pause_scheduler(profile)                   # queued work retained
                raise MSG_INT_002(organisation_name = profile.zoho_organisation_name,
                                  since = first_failure_at(profile))
            audit("TOKEN_REFRESH_FAILED", profile, code = response.code)
    finally:
        distributed_lock.release(lease)
```

Properties an implementer must preserve:

- **Single-flight.** Without the lease, a burst of 8 concurrent workers all seeing an expired token would fire 8 refreshes. Beyond wasting rate-limit budget, repeated refresh is exactly the behaviour that interacts badly with the 20-token rule.
- **Skew of 120 seconds.** A token is refreshed before it expires, not after it fails. This removes the 401-classification path from the normal case entirely.
- **Scope reconciliation on every refresh.** The refresh response carries the granted scope set, which makes L1 detection free and catches a consent change within one hour rather than at the next manual check.
- **`api_domain` is re-read on every refresh** and a change is treated as a configuration event, logged, and surfaced on SCR-38.
- **Three consecutive failures, not one, before declaring revocation.** A single failure may be a transient accounts-service error; three is a pattern.

#### 15.10.3 Re-consent policy

| Situation | Action | Re-consent? |
|---|---|---|
| Access token expired | Refresh | No |
| Refresh returns a transient error | Retry with backoff, up to 3 | No |
| Refresh fails 3 consecutive times | `Integration Failed`; administrator alerted | Yes — human-initiated only |
| A required scope was added to `required_scopes` (new module enabled) | Re-authorisation required to widen consent | Yes — human-initiated, and the re-consent counter increments |
| Client secret rotated | See §15.11 | Depends on rotation type |
| Organisation re-mapped | Existing grant still valid; mapping change controlled separately (§14.9.3) | No |

### 15.11 Credential rotation

Two rotations exist and they have different blast radii. Confusing them is a common operational error.

| Rotation | What changes | Consent needed? | Downtime | Procedure |
|---|---|---|---|---|
| **Refresh-token rotation** | A new refresh token replaces the current one | Yes — a new grant produces a new refresh token | None if performed as described below | R1–R7 |
| **Client-secret rotation** | The OAuth client's secret changes in Zoho | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** whether an existing refresh token survives a client-secret change | Potentially total until re-consent | C1–C6, with a re-consent contingency |

**R — Refresh-token rotation runbook**

| Step | Action | Control |
|---|---|---|
| R1 | Administrator raises a rotation request on SCR-40 with a reason | Maker recorded |
| R2 | In `Production`, a second `System Administrator` approves | Maker-checker, §26.11 |
| R3 | Connector enters a rotation window: scheduler paused, in-flight calls allowed to drain, queue retained | `connection_status` unchanged; a rotation banner shows on SCR-38 |
| R4 | Wizard steps 8–11 are re-run for the same profile, producing a new refresh token | Re-consent counter increments (§15.9) |
| R5 | New refresh token written to a **new** secret-store version; the profile handle is repointed atomically | Old version retained for the rollback window |
| R6 | A verification call (`GET /organizations`) must succeed on the new token before the window closes | Failure rolls the handle back to the previous version |
| R7 | Old secret version destroyed after the rollback window (default 24 hours); `credential_rotated_at` set | Connector Audit Log records both events |

**C — Client-secret rotation runbook**

| Step | Action |
|---|---|
| C1 | Rotate the secret in Zoho's developer console (manual; see prerequisite P1, §14.5) |
| C2 | Write the new secret to a new secret-store version; repoint `client_secret_ref` |
| C3 | Force a refresh (§15.10.2) and observe the result |
| C4 | If the refresh succeeds, the existing refresh token survived the change — record that observation against the connection profile, since it is otherwise unverified |
| C5 | If the refresh fails, treat as revocation: `Integration Failed`, then re-run wizard steps 8–11 |
| C6 | Destroy the old secret version after the rollback window |

**Rotation policy defaults** (recommendations, not client-confirmed requirements): client secret rotated annually or on any suspicion of exposure; refresh token rotated on administrator change, on offboarding of the Zoho authorising user, and on any security event; the SCR-38 rotation-due alert fires at 335 days since `credential_rotated_at`. Atha Group's own credential policy takes precedence and is a §45 Client Clarification Questionnaire item.

### 15.12 Revocation and disconnection

| Requirement | Design |
|---|---|
| Revoke Zoho's grant | The vendor states a refresh token has *"an unlimited lifetime until it is revoked by the end-user"* `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`, which establishes that end-user revocation exists. **The revocation API path is UNVERIFIED - REQUIRES ZOHO CONFIRMATION** — no citable evidence for a revoke endpoint was found. The disconnection procedure therefore does **not** depend on calling one |
| Disconnect from our side | Deterministic and complete without any Zoho call: destroy every secret-store version for the profile, purge the access-token cache, set `oauth_grant_status = Revoked`, set `connection_status = Closed` with a mandatory `disable_reason`, pause the scheduler, retain all historical data |
| Confirm revocation took effect | A verification probe (`GET /organizations`) must fail after disconnection; if it succeeds, the grant still exists on Zoho's side and the administrator is instructed to revoke it in the Zoho account UI. The dashboard shows `Revocation unconfirmed` until the probe fails |
| Emergency disconnect | A single **Disconnect now** action performs the full sequence with no maker-checker, on the principle that stopping access must never be harder than starting it. The action is heavily audited and notifies every `System Administrator` |
| Data retention on disconnect | Nothing is deleted except secret material. Sync Log, Integration Event, Reconciliation Log, Connector Audit Log and every business record are retained (§14.13) |

Because our-side disconnection cannot by itself terminate the grant on Zoho's side, the disconnection checklist explicitly instructs the administrator to revoke the connected application in the Zoho account's connected-apps interface, and the connector records that instruction as an outstanding action until the verification probe fails.
