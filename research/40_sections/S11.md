## 11. Architecture Options

Four options are compared. The comparison is run genuinely, on one rubric, with the client's own proposal scored on the same criteria as the others. **The client's document proposed Option D** — its cover states an approach using Zoho ERP with controlled customization, and its section 10 classifies every gap as Standard, Configuration or Customization, that is, work done inside Zoho (CONF-05). Where the recommendation in §12 Recommended Architecture departs from that, it is justified against named constraints, not against preference.

### 11.1 The four options, defined precisely

Vague option definitions produce meaningless scores. Each option below is defined by where four specific things live: the budget register, the availability check, the Purchase Request, and the user interface.

| | Option A — Standalone custom web application integrated with Zoho ERP | Option B — Zoho Creator-based control layer | Option C — Hybrid architecture | Option D — Configuration-only inside Zoho ERP |
|---|---|---|---|---|
| Budget register (project, WBS, budget head, versions, revisions) | Own relational schema in the Control Hub | Zoho Creator forms and reports | Own relational schema in the Control Hub | Zoho ERP custom modules and custom fields |
| Availability check | Control Hub service, synchronous, pessimistic-locked against a serialised budget ledger | Deluge script in Zoho Creator | Control Hub service | Zoho ERP custom function or workflow rule |
| Purchase Request | Owned by the Control Hub end to end | Owned by Zoho Creator | Owned by the Control Hub; optionally mirrored into a Zoho ERP custom module so procurement staff see it in their own tool | Zoho ERP Purchase Request product feature, driven through the user interface only |
| User interface | Purpose-built SAP-familiar web application; all 40 screens in scope | Zoho Creator pages, within Creator's layout system | Purpose-built web application for control screens; native Zoho ERP screens for procurement and accounting documents | Native Zoho ERP screens plus custom module layouts |
| Integration to Zoho ERP | REST, OAuth 2.0, polling, from the Control Hub | Creator connections plus Deluge invokeUrl | REST polling from the Control Hub, plus UI-configured workflow webhooks in Zoho ERP as a latency accelerator | None required — same platform |
| Accounting and procurement system of record | Zoho ERP | Zoho ERP | Zoho ERP | Zoho ERP |

Every option keeps Zoho ERP as the accounting and procurement system of record. That constraint is binding and is not a differentiator.

**Evidence status of Option B.** This engagement's verified evidence base contains **no verified claim about Zoho Creator at all** — not its data model, not its scripting limits, not its API quotas, not its licensing. Every Option B capability statement in this section is therefore marked **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** and its scores are conditional. This is stated rather than papered over, because scoring an option on assumed capability is exactly the failure mode the evidence rules exist to prevent.

### 11.2 Scoring rubric

Eight criteria, the eight named in the engagement brief. Scores run 1 to 5, where 5 is always the better outcome for the client. For effort, cost, lock-in and time to POC a score of 5 means low effort, low cost, low lock-in and short time. Weights are stated so a reviewer can re-derive every total.

| Criterion | Weight | 5 means | 3 means | 1 means |
|---|---|---|---|---|
| C1 Control fidelity | 20 | Availability control is synchronous, serialised, line-level, and cannot be bypassed by any route into the transaction | Control exists but can be bypassed by one documented route, or is asynchronous | Control is advisory only, or is evaluated after the commitment already exists |
| C2 Multi-level WBS support | 15 | Arbitrary-depth WBS with budget, commitment, actual and available at every node, rolling up | Fixed shallow depth, or budget at only some levels | No hierarchy below project and budget head |
| C3 Auditability | 15 | Immutable append-only audit of every field change, approval, override and integration event, with who, when, before, after and why; queryable and exportable | Audit exists for approvals but not for all field changes or integration events | Platform-level activity log only, not tied to the control values |
| C4 Resilience to the discovered API constraints | 20 | Every one of the four hard constraints is absorbed inside the architecture with a designed answer, not a workaround | Constraints are absorbed but at least one leaves a manual step or a blind spot | At least one constraint is load-bearing and unanswered |
| C5 Build effort | 10 | Smallest engineering effort to production quality | Moderate | Largest |
| C6 Cost | 5 | Lowest total cost of ownership including licences, hosting and maintenance | Moderate | Highest |
| C7 Lock-in | 5 | Control logic and data are portable; a change of ERP or platform is a connector change | Portable data, non-portable logic | Both logic and data are captive to one vendor platform |
| C8 Time to POC | 10 | Full POC scope demonstrable fastest | Moderate | Slowest |

### 11.3 Criterion-by-criterion comparison

#### C1 Control fidelity — weight 20

| Option | Assessment | Score |
|---|---|---|
| A | The availability check is a synchronous service call inside the same transaction that creates the Purchase Request, against a serialised budget ledger with pessimistic locking. Because the Purchase Request itself is owned here, there is no route into a capital commitment that bypasses the check. The one residual gap is a purchase order raised directly in Zoho ERP without a Purchase Request, which the reconciliation job at stage L18 detects but does not prevent. | 5 |
| B | Same logical placement as A — the Purchase Request would be owned in Creator, so the check is in front of the commitment. Whether Deluge can express a serialised, pessimistically-locked budget ledger with the concurrency behaviour CONF-10 requires is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. Scored conditionally on that being possible. | 4 |
| C | Identical to A for the control path. The Zoho-side additions are read accelerators and coding conveniences, not control points, so they cannot weaken the check. | 5 |
| D | The Purchase Request lives in the Zoho ERP product feature, which has no API (OAS-02). A custom function or workflow rule fires on the record, but the client PDF's own control formula requires reading open PO commitment across the whole project or budget head, which Zoho ERP does not compute (C2 glossary). The check would have to be reconstructed inside a custom function on every evaluation, and no evidence in this engagement establishes that a Zoho ERP custom function can block a Purchase Request submission synchronously. **UNVERIFIED - REQUIRES ZOHO CONFIRMATION.** | 2 |

#### C2 Multi-level WBS support — weight 15

WBS is a **SCOPE ADDITION** throughout — the client document contains no WBS hierarchy anywhere, only project plus budget head (CONF-02). This criterion scores each option's ability to carry the addition if the client accepts it.

| Option | Assessment | Score |
|---|---|---|
| A | Arbitrary depth in the Control Hub's own schema, with budget, commitment, actual and available at every node and roll-up to project plus budget head totals identical to the client's section 6 table. A project with zero WBS elements behaves exactly as the client document describes. | 5 |
| B | Self-referencing hierarchy in Creator is plausible but the depth, roll-up query behaviour and report performance are **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. | 3 |
| C | Identical to A. | 5 |
| D | Zoho ERP Projects are flat. Hierarchy exists only under Tasks via `parent_id`, and Project carries only scalar `budget_amount`, `budget_type` and `cost_budget_amount` with no budget-by-head object (OAS-05) `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. A custom module could be given a `parent_module_id`, but the budget register and its roll-up arithmetic would still have to be written by hand in custom functions. | 1 |

#### C3 Auditability — weight 15

REQ-SEC-001 requires an unbroken trail from budget approval through procurement, accounting and final capitalisation. REQ-SEC-004 requires every revision to retain requestor, approver, date, reason and approval reference.

| Option | Assessment | Score |
|---|---|---|
| A | Append-only Audit Log, Approval Instance, Connector Audit Log, Sync Log and Reconciliation Log are first-class entities in the data model. Retention, immutability and export are design choices the Control Hub owns. | 5 |
| B | Creator provides platform-level record history; whether it yields an immutable, exportable, field-level trail across the whole control cycle including integration events is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. | 3 |
| C | Identical to A, plus the Zoho-side documents keep their own native history, which is additive. | 5 |
| D | The trail would be split across Zoho ERP's own record history and whatever a custom module records. Critically, the capitalisation leg cannot be traced from asset back to the CWIP that funded it using documented fields (OAS-09), so the trail breaks at the last step of the client's own workflow. | 2 |

#### C4 Resilience to the discovered API constraints — weight 20

This is the criterion that separates the options. Each constraint is a mechanically verified finding from the vendor's own specification, not an opinion.

| Constraint | Evidence | Option A | Option B | Option C | Option D |
|---|---|---|---|---|---|
| **No Purchase Request API anywhere in the specification** — zero matching paths, modules or scopes across all 78 modules, 561 paths and 163 scopes (OAS-02) | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` | Absorbed. The PR is owned by the Control Hub, so no API is needed. | Absorbed if Creator owns the PR. **UNVERIFIED** whether Creator can drive the downstream Zoho ERP purchase order creation. | Absorbed, same as A. Optional mirror into a Zoho custom module gives procurement visibility without moving ownership. | **Load-bearing and unanswered.** The PR is the record the whole control cycle hangs from, and it would be unreachable programmatically. Approval routing, budget checks and reporting would all be confined to what the product's user interface exposes. |
| **No API to create a custom field definition** — custom-field endpoints set values on an existing record only (OAS-06) | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` | Absorbed. Field definitions are a documented manual prerequisite performed once per organisation in the Zoho ERP user interface, then discovered by the connector. | Same manual prerequisite. | Same manual prerequisite, but it is fewer fields because the Control Hub holds the register and Zoho only carries the reference codes. | **Worst position.** The entire control model lives in Zoho custom fields and custom modules, so provisioning a second organisation is a large manual configuration exercise that cannot be scripted, versioned or diffed. |
| **No list endpoint for purchase receives, and receipt lines carry no purchase-order link** — receipt lines expose only description, item id, item order, line item id, name, quantity and unit; paths are `POST /purchasereceives`, `GET /purchasereceives/{purchasereceive_id}`, `PUT /purchasereceives/{purchasereceive_id}`, `DELETE /purchasereceives/{purchasereceive_id}` (OAS-03) | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` | Absorbed. Received-but-unbilled exposure is reconstructed in the Control Hub from PR-to-PO-to-receipt linkage the Control Hub itself created, and carried as an explicit exposure bucket. | Same reconstruction required, in Deluge. **UNVERIFIED** whether Creator can hold the reconstruction at the volumes involved. | Absorbed, same as A, and improved: a UI-configured workflow webhook on the receipt event can push the receipt id to the Control Hub, removing the discovery problem the missing list endpoint creates. | **Load-bearing and unanswered.** Zoho ERP has the receipt document but computes no received-but-unbilled exposure, and the missing linkage means it cannot. The anti-under-count control in the formula registry could not be implemented. |
| **The API is not uniformly `/erp/v3`** — 14 of 78 modules are served from `/erp/v1`, including `departments` and `receipts` (OAS-01) | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` | Absorbed. The connection profile resolves base path per module rather than per connection; the API Endpoint Catalogue entity carries the version. | Absorbed if Creator connections can vary base URL per call. **UNVERIFIED.** | Absorbed, same as A. | Not applicable — no cross-API calls. This is the one constraint Option D genuinely does not face. |
| *Additional:* **No webhook framework in the ERP REST API**; webhooks exist only as a workflow action configured in the user interface | `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`; `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]` | Absorbed by polling on `last_modified_time`. | Same. | Absorbed by polling, with the UI-configured webhook as an accelerator. | Not applicable in-platform. |
| *Additional:* **Fixed assets carry no link to source project, PO or bill, and no last-modified filter** (OAS-09) | `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` | Absorbed. Capitalisation reconciliation is anchored on the Control Hub's own Capitalisation Request and Asset Allocation; asset sync is full-refresh. | Same anchor required. **UNVERIFIED** whether full-refresh asset sync is practical in Creator. | Absorbed, same as A. | **Unanswered.** With no external anchor record, there is nothing to reconcile the asset back to. |

| Option | Score |
|---|---|
| A | 5 — all four named constraints absorbed with a designed answer; one documented manual prerequisite remains |
| B | 3 — the same answers are structurally available but every one of them is unevidenced on this platform |
| C | 5 — identical to A, and the webhook accelerator improves the receipt-discovery position |
| D | 1 — three of the constraints are load-bearing and unanswered |

#### C5 Build effort — weight 10

Effort figures are a **DERIVED-RECOMMENDATION** estimate for planning only. No effort benchmark from the client or from Zoho exists in this engagement's evidence base.

| Option | POC effort | Production effort | What drives it | Score |
|---|---|---|---|---|
| A | 6 to 8 person-weeks | 26 to 34 person-weeks | 40 screens, own schema, own auth, own connector, own audit subsystem | 2 |
| B | 4 to 6 person-weeks | 18 to 26 person-weeks | Platform supplies persistence, auth and basic UI; effort concentrates in Deluge control logic and in fighting layout limits for the SAP-familiar interface | 3 |
| C | 6 to 8 person-weeks | 28 to 36 person-weeks | As A, plus Zoho-side workflow and custom-module configuration and its per-organisation repetition | 2 |
| D | 3 to 5 person-weeks | 16 to 24 person-weeks *for a materially reduced control model* | Least code — but the reduction is capability, not efficiency. It cannot deliver C1, C2 or C4. | 4 |

The effort ranking must be read against C1 to C4. Option D is cheapest because it does less, not because it does the same thing faster.

#### C7 Lock-in — weight 5

| Option | Assessment | Score |
|---|---|---|
| A | Control logic and control data are in a system the client owns. Replacing Zoho ERP is a connector rewrite, not a control rewrite. This directly supports the roadmap's eventual multi-ERP or group-wide phase. | 5 |
| B | Control logic is written in a proprietary scripting language and control data lives in a proprietary store. Migration means rewriting the control layer. | 2 |

#### C8 Time to POC — weight 10

The POC must demonstrate 36 steps, including three-level WBS, partial GRN, partial bill, PO amendment, PO cancellation, budget revision with version history, capitalisation to multiple assets, OAuth authorisation, organisation discovery, scope validation, token refresh, rate-limit handling, retry and dead-letter processing, and line-level PO-receipt-bill reconciliation.

| Option | Assessment | Score |
|---|---|---|
| A | Fastest credible route to the *full* POC step list, because every step that Zoho cannot do is done locally by design and because the connector module is buildable against a controlled mock where live credentials are unavailable. | 4 |
| B | Fast to a first screen, slow to the full list, and every connector step carries unevidenced platform risk. | 3 |
| C | Same as A for the POC, because the Zoho-side accelerators are deferred to production. | 4 |
| D | Cannot demonstrate three-level WBS, cannot demonstrate received-but-unbilled reconstruction, cannot demonstrate line-level PO-receipt-bill reconciliation. It reaches a partial POC quickly and a complete POC never. | 2 |

| # | Requirement of every option | Basis |

| I2 | CAPEX code, WBS code and budget head are carried at **line** level on purchase orders, bills and journals, never header level | OAS-04, OAS-10 |
| I3 | Custom-field definitions are created manually in the Zoho ERP user interface as a documented prerequisite, then discovered | OAS-06 |
