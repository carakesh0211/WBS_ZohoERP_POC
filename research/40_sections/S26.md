## 26. Integration Security and Secret Management

### 26.1 Scope of this section

This section governs the security of the integration boundary between the CAPEX & WBS Control Hub and Zoho ERP: how connector secrets are stored, how the OAuth exchange is protected, what may and may not appear in a log, and which connection changes require a second pair of eyes. Application-level security — user authentication, role-based access, segregation of duties across the CAPEX lifecycle, and the business audit trail — is specified in §32 Security and Internal Controls. Where the two meet, §32 governs the user and this section governs the machine identity.

The controls here are stated as **binding requirements on the POC build**, not as aspirations for a later hardening pass. Two of them — "no plain-text secret" and "no secret in any log" — are architectural, and retrofitting them after a POC has been demonstrated is expensive and usually incomplete.

Client-stated requirement served: `REQ-SEC-001` (audit trail from budget approval through procurement, accounting and final capitalisation) — the connector audit trail in §26.13 is the integration segment of that trail. Everything else in this section is `provenance=MASTER-PROMPT` under CONF-07 and must be sized as engagement-added scope in §41 Implementation Roadmap.

### 26.2 What is being protected, and from whom

| Asset | Why it matters | Realistic loss scenario |
|---|---|---|
| OAuth **client secret** | Combined with the client ID and a refresh token, it mints access tokens indefinitely — a refresh token *"does not expire"* `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` | Committed to a repository, or printed in an outbound HTTP log line because the vendor's documented refresh call puts it in a query string (§26.9) |
| OAuth **refresh token** | The long-lived credential. Possession is equivalent to standing access at the granted scopes | Copied out of a database backup, or read from a `.env` file on a shared build server |
| **Access token** | One hour of API access at the granted scopes `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` | Captured from a browser local-storage entry, or from an error report that echoed the `Authorization` header |
| **Authorisation code** | Two-minute window `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`; exchangeable for both tokens by anyone who intercepts it before the legitimate exchange | Delivered to an attacker-controlled redirect URI, or replayed from a browser history entry |
| **`organization_id`** | Not secret, but it is the tenancy key. A wrong value silently writes CAPEX references into another company's books | Typed by hand rather than selected from `GET /organizations` (§14.9) |
| **Synced vendor master data** | Contains contact-person names, e-mail addresses and phone numbers — personal data under India's DPDP regime | Exported from a connector log or a failed-sync payload dump |
| **CAPEX and budget figures in transit** | Commercially sensitive; the client's own budget structure | Unencrypted transport, or over-broad log retention |

Threat actors assumed: an insider with application-database read access but no secret-store access; an insider with source-repository access; an external attacker who obtains a database backup; an attacker who can induce an administrator to click a crafted link during setup; and an operator who accidentally pastes a secret into a support ticket. The design is intended to make each of these non-fatal on its own.

Two things are explicitly **out of scope of the design's guarantees** and must be stated rather than implied: this design cannot protect against an attacker who holds both the application database *and* the key-management key material; and it cannot revoke a Zoho grant unilaterally, because no revocation endpoint is evidenced (§15.12).

### 26.3 Secret inventory

Every secret the connector handles, with its permitted resting place. Any location not named here is a violation.

| Secret | Created by | Permitted storage | Permitted display | Lifetime | Blast radius if leaked |
|---|---|---|---|---|---|
| OAuth client ID | Administrator (from the Zoho developer console) | Secret store, referenced by `client_id_ref` | Last 4 characters only | Until rotated | Low alone; high in combination |
| OAuth client secret | Administrator | Secret store, referenced by `client_secret_ref` | **Never** — not even masked-with-reveal | Until rotated | Full standing access when combined with a refresh token |
| Authorisation code | Zoho Accounts | **Process memory only.** Never persisted, never logged, never placed in a database column or a cache | Never | 2 minutes | Full grant if replayed inside the window |
| Refresh token | Zoho Accounts | Secret store, referenced by `refresh_token_ref` | **Never** | Until revoked or evicted (§15.9) | Full standing access at the granted scopes |
| Access token | Zoho Accounts | Encrypted short-lived cache, keyed on `connection_profile_id`, TTL ≤ 3600 s | **Never** | 1 hour | One hour of access at the granted scopes |
| OAuth `state` nonce | This application | Server-side session store, single-use, TTL 10 minutes | Never | 10 minutes | CSRF / code-injection if predictable |
| PKCE code verifier | This application | Server-side session store, paired with the `state` | Never | 10 minutes | Code interception becomes exploitable if lost |
| Webhook shared secret (conditional) | Administrator, in the Zoho ERP UI | Secret store | **Never** — *"cannot be edited or viewed once the webhook is created"* on the Zoho side either `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]` | Until re-created | Forged inbound events (§26.14) |
| Data-encryption key (DEK) | This application | Wrapped by the KEK, stored alongside the ciphertext | Never | Per secret version | Ciphertext for that one secret |
| Key-encryption key (KEK) | Key manager / HSM / deployment secret | **Never in the application database**, never in source, never in an image layer | Never | Per rotation period | Every secret in the store |

**The rule, stated once and without exception: no secret in this table is ever written to the application database as readable plain text.** The connection-profile master (§14.3) stores handles in fields 11, 12 and 15, never values.

### 26.4 Storage design

#### 26.4.1 Options assessed

| Option | Key custody | Operational cost | Resistance to a database-only compromise | Resistance to a full-host compromise | Auditability | Verdict |
|---|---|---|---|---|---|---|
| Plain text in the application database | None | None | **None** | None | None | **Prohibited.** Not offered as a configuration option anywhere in the product |
| Reversible field encryption with a key in application configuration | Key sits beside the data | Very low | Weak — a configuration file usually travels with the backup | None | Poor | **Rejected** |
| **Application-level envelope encryption** (per-secret DEK, wrapped by a KEK held outside the database) | KEK in the deployment's key material, injected at runtime | Low | **Strong** — the database alone yields nothing | Weak | Good — versioned, audited | **POC minimum** |
| **Managed cloud secret manager** | Provider-managed KMS; the application never sees the key | Moderate | Strong | Moderate — depends on workload identity | Strong — provider access logs plus ours | **Production recommendation** |
| **HSM-backed key management** | Hardware key custody, non-exportable | High | Strong | Strong | Strongest | Recommended where Atha Group's own policy or a lender/auditor requirement demands it |

#### 26.4.2 Recommendation

| Deployment | Recommendation | Why |
|---|---|---|
| **POC** | Application-level **envelope encryption**, per §26.5, with the KEK injected as a runtime secret and never present in source, in an image layer or in a configuration file committed anywhere | The brief names envelope encryption as the minimum fallback. It is achievable inside a POC timebox, it removes the database-only compromise entirely, and it forces the correct interface — `secret_store.resolve(handle)` — so that swapping in a managed secret manager for production is a configuration change, not a redesign |
| **Production** | **Managed cloud secret manager**, with **HSM-backed key management where Atha Group's policy requires it**, behind the same `SecretStore` interface | Removes key custody from the application entirely; gives an independent access log; supports versioning and staged rotation natively (§15.11) |

This is a **recommendation, not a client-confirmed requirement.** Atha Group's hosting decision (§40 Deployment Recommendation) and its own information-security policy govern the final choice, and the choice is recorded on the connection profile as `secret_store_backend` so that the deployed reality is visible on SCR-38 rather than assumed.

The interface both backends implement:

```
interface SecretStore:
    put(namespace, name, value) -> handle          # returns "sm://<ns>/<name>#<version>"
    resolve(handle)             -> value           # audited on every call
    versions(namespace, name)   -> [handle]
    destroy(handle)                                # irreversible; audited
    # There is deliberately no list_values() and no export(). Bulk read of secret
    # VALUES is not an operation this interface offers to any caller.
```

`resolve()` is the only path from a handle to a value, it is callable only from the connector's server-side runtime, and every call writes a Connector Audit Log row carrying caller, handle, purpose and correlation ID — never the value.

### 26.5 Envelope encryption specification (the POC minimum)

| Element | Specification |
|---|---|
| Data-encryption key (DEK) | 256-bit, generated by a CSPRNG, **unique per secret version** — never reused across secrets or versions |
| Symmetric algorithm | AES-256-GCM (authenticated encryption). A 96-bit nonce, unique per encryption operation, never reused with the same DEK |
| Additional authenticated data (AAD) | `connection_profile_id ‖ secret_name ‖ version` — binds the ciphertext to its intended profile and slot, so a ciphertext moved between rows fails to decrypt rather than silently decrypting into the wrong context |
| Key-encryption key (KEK) | Held outside the application database: a KMS key in production, or a runtime-injected key for the POC. **Never** in source, in a repository file, in an image layer, in an environment file committed to any store, or in the database |
| DEK wrapping | The DEK is encrypted under the KEK and stored beside the ciphertext. The plaintext DEK exists only in process memory, for the duration of one operation, and is zeroised afterwards |
| Stored record | `{ version, kek_id, wrapped_dek, nonce, ciphertext, auth_tag, algorithm, created_at, created_by }` — no field of this record is a plaintext secret |
| Integrity failure | A GCM authentication failure is a **security event**, not a data error: the operation aborts, the connector does not retry, and `System Administrator` is alerted |
| KEK rotation | Re-wrap every DEK under the new KEK; ciphertexts are untouched, so rotation is fast and does not require re-consent. `kek_id` on each record identifies which KEK is in force |
| DEK rotation | Occurs naturally on every secret rotation (§15.11), because each new version gets a new DEK |
| Destruction | `destroy(handle)` overwrites the wrapped DEK and the ciphertext and marks the version destroyed. Because the DEK is per-version, destroying the wrapped DEK renders that ciphertext unrecoverable even if a backup of the ciphertext survives |

```
function put_secret(profile_id, name, value):
    version      = next_version(profile_id, name)
    dek          = csprng(32)                                  # 256-bit
    nonce        = csprng(12)                                  # 96-bit, never reused
    aad          = profile_id || name || version
    ct, tag      = aes_256_gcm_encrypt(key = dek, nonce = nonce, aad = aad, pt = value)
    wrapped_dek  = kms.wrap(kek_id, dek)                       # KEK never enters this process in the clear
    store_row(profile_id, name, version, kek_id, wrapped_dek, nonce, ct, tag)
    zeroise(dek); zeroise(value)
    audit("SECRET_WRITTEN", profile_id, name, version)         # never the value
    return handle(profile_id, name, version)

function resolve(handle):
    row  = load_row(handle)
    dek  = kms.unwrap(row.kek_id, row.wrapped_dek)
    aad  = row.profile_id || row.name || row.version
    pt   = aes_256_gcm_decrypt(dek, row.nonce, aad, row.ciphertext, row.auth_tag)
                                                               # raises on tag mismatch
    zeroise(dek)
    audit("SECRET_RESOLVED", row.profile_id, row.name, row.version, caller, correlation_id)
    return pt                                                  # caller must not persist or log this
```

Callers of `resolve()` are restricted to three code paths: the token-exchange client, the token-refresh client, and the rotation runbook. Any fourth caller is a review-blocking finding, and a static check enforces it (§26.11).

### 26.6 OAuth `state` validation

The `state` parameter is the only defence against an attacker inducing an administrator's browser to complete an OAuth callback that the administrator did not initiate. It is mandatory, and its properties are prescriptive.

| Property | Requirement |
|---|---|
| Generation | Cryptographically secure random, at least 128 bits, base64url-encoded |
| Binding | Bound server-side to: the administrator's authenticated session, the `connection_profile_id`, the `redirect_uri`, and the exact `required_scopes` set being requested |
| Storage | Server-side session store only. **Never** in a cookie readable by script, never in local storage, never in the URL beyond the outbound authorisation request |
| Lifetime | 10 minutes. Expiry ends the wizard step; the profile stays `Draft` |
| Single use | Consumed atomically on first presentation. A second presentation of the same value is rejected and logged as a security event |
| Validation on callback | All of: value exists, not expired, not consumed, session matches, `connection_profile_id` matches, `redirect_uri` matches the registered value |
| Failure behaviour | Reject the callback, discard any `code` present without exchanging it, write a security event naming the source IP and the authenticated user, show a page-level error. **Never retry automatically**, and never offer a "continue anyway" action |

**PKCE is additionally recommended** (RFC 7636, S256 challenge method), on the principle that an authorisation code should be useless to anyone who did not initiate the request. The code verifier is generated with the `state`, stored beside it server-side, and presented at exchange. **Whether Zoho's ERP token endpoint accepts and enforces `code_challenge` / `code_verifier` is UNVERIFIED - REQUIRES ZOHO CONFIRMATION** — the documented mandatory authorisation parameters are `client_id`, `response_type`, `redirect_uri` and `scope`, with `access_type` and `prompt` as the offline/consent controls `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`, and PKCE is not among them. The implementation therefore sends PKCE parameters, records whether the exchange succeeded with them, and falls back to a non-PKCE exchange only after logging that fallback as a recorded security posture reduction on the connection profile. It never silently drops PKCE.

### 26.7 CSRF protection on the callback

The OAuth callback is a state-changing GET issued by a third party's redirect. It needs protection that ordinary form CSRF tokens do not provide.

| Control | Requirement |
|---|---|
| `state` as the primary CSRF defence | As §26.6. A callback with no `state`, an unknown `state` or a consumed `state` is rejected before any parameter is parsed |
| Authenticated session required | The callback endpoint requires an authenticated `System Administrator` session. An unauthenticated callback is rejected outright — it is not a login mechanism |
| Session cookie attributes | `SameSite=Lax` (the callback is a top-level cross-site GET, which `Lax` permits and `Strict` would break), `Secure`, `HttpOnly`, `__Host-` prefix |
| Idempotent handling | The callback exchanges the code **exactly once**. A repeat with the same `state` is rejected, not re-exchanged — this closes browser-back and history-replay routes |
| No side effect before validation | The handler validates `state` before it reads `code`, before it writes anything, and before it emits any log line containing request parameters |
| Referrer and error hygiene | `Referrer-Policy: no-referrer` on the callback route; the error page carries no request parameters in its URL or body |
| Rate limiting | Callback route limited per session and per source IP; exceeding the limit is a security event |

Response security headers on every connector route: `Strict-Transport-Security` with a long max-age, `Content-Security-Policy` with no inline script, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (the setup wizard is never framed), `Cache-Control: no-store` on every route that can render configuration.

### 26.8 Redirect-URI validation

| Rule | Detail |
|---|---|
| Exact-match allow-list | The redirect URI is validated by **exact string comparison** against a per-environment allow-list held in deployment configuration. No prefix matching, no suffix matching, no regular expression |
| No wildcards | Neither host nor path wildcards are accepted in the allow-list |
| HTTPS only in `Test` and `Production` | `http://localhost` is permitted **only** when `environment = Development`, and only on the loopback host |
| No query string, no fragment | A candidate URI carrying either is rejected at profile save (wizard step 5), not at callback time |
| One URI per (environment, connection profile) | Prevents a Development URI being registered on a Production OAuth client |
| Registered value must match | The value stored in connection-profile field 13 must be exactly the value registered in Zoho's developer console. The wizard displays the exact string for copying rather than asking the administrator to retype it |
| Open-redirect prohibition | The callback route never redirects to a URL taken from a request parameter. Post-callback navigation targets are chosen from a fixed server-side map keyed on the outcome |
| Change control | Changing field 13 on a `Production` profile is a maker-checker change (§26.11) and invalidates the current grant, because the registered URI must be changed in Zoho too |

### 26.9 The documented query-string credential hazard

Zoho's own refresh example places the refresh token, client ID and client secret in the URL query string and sets `Content-Type: application/data` `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`. Query strings are, by default, recorded by reverse proxies, load balancers, CDNs, application access logs and error-reporting agents. Following the example naively places long-lived credentials into several log sinks at once.

Compensating controls, all mandatory:

| # | Control |
|---|---|
| C1 | A **dedicated accounts-domain HTTP client**, separate from the ERP API client, with request/response logging disabled at the transport layer — not merely filtered downstream |
| C2 | The accounts client attempts a form-encoded request body first; it falls back to the documented query-string form only on rejection, and records which form succeeded on the connection profile so the deployed behaviour is observable |
| C3 | The accounts domain is added to the **URL-redaction deny-list** in every logging sink: for that host, only method, host, path and status code may be recorded. The query string is never emitted |
| C4 | Reverse-proxy and load-balancer access-log formats for the egress path are configured to drop query strings; this is a deployment checklist item in §40 Deployment Recommendation, verified by a test that asserts no credential material appears in any collected log after a refresh |
| C5 | Error-reporting and APM agents are configured to scrub URLs for the accounts host, and the scrubbing is asserted by an automated test rather than trusted |
| C6 | Refresh calls are never made from a browser, from a client-side script, or from any process whose outbound requests transit a shared logging proxy |

### 26.10 No secrets in logs, browser storage, source or repository

#### 26.10.1 Logging policy

| Rule | Requirement |
|---|---|
| Structured logging only | Free-form string interpolation of request or response objects is prohibited in connector code, because it is how secrets escape |
| Field allow-list | Integration Request and Integration Response records persist: method, resolved base path, path template (not the interpolated path where it contains identifiers that are secret), status code, Zoho `code`, Zoho `message`, response time, record count, correlation ID, profile ID, organisation ID, retry attempt. **Nothing else from the wire is persisted by default** |
| Header deny-list | `Authorization`, `Cookie`, `Set-Cookie`, and any header whose name contains `token`, `secret`, `key`, `credential` or `auth` (case-insensitive) is replaced with `[REDACTED]` before the record is constructed |
| Body handling | Request and response bodies are **not** logged by default. Where a failed record must be inspected, the payload is captured to the Dead-Letter Record with the redactor applied, and access to that payload is itself an audited read |
| Redaction at serialisation | Redaction happens where the log record is **built**, never at render time. A redactor applied only in the UI leaves the secret in the store |
| Pattern redaction | Any value matching a credential shape — long base64url or hex runs on a field whose name matches the deny-list, `refresh_token=`, `client_secret=`, `code=`, `Zoho-oauthtoken ` — is replaced with `[REDACTED]` as a defence in depth. Pattern redaction is the **second** line; the allow-list is the first |
| Token display | Where an access token must be referenced operationally, only a non-reversible fingerprint (first 6 characters of a salted hash) is shown, so two log lines can be correlated without the token being reconstructable |
| Test enforcement | An automated test drives a full wizard run and a refresh against a recording proxy and **fails the build** if any known secret value appears in any log sink, any exported file, any error page or any audit record |
| Log retention and access | Connector logs are access-controlled to `System Administrator` and `Internal Auditor`. Where a log line contains personal data — vendor contact person names, e-mail addresses, phone numbers synced from Zoho — the DPDP position in §26.12 applies |

#### 26.10.2 Browser storage policy

| Rule | Requirement |
|---|---|
| No token in `localStorage` or `sessionStorage` | Neither the access token nor the refresh token nor the authorisation code is ever placed in browser storage. The browser never holds a Zoho credential at all |
| No token in the DOM | Setup screens render masked placeholders. There is no hidden input, no data attribute and no inline script variable carrying credential material |
| Server-side session only | The `state`, the PKCE verifier and the in-flight wizard context live server-side, keyed by the session cookie |
| All Zoho calls are server-side | The browser never calls `zohoapis.in` or `accounts.zoho.in` directly. Every ERP call originates from the application server, which also makes the outbound IP allow-list in §26.12 possible |
| Secret input fields | Write-only: `autocomplete="off"`, no reveal control, no copy-to-clipboard, cleared from memory on submit, and never re-populated on re-render |

#### 26.10.3 Source and repository policy

| Rule | Requirement |
|---|---|
| No secret in source | No client ID, client secret, refresh token, organisation ID or KEK appears in application source, in a test fixture, in a seed script, in an infrastructure template or in documentation examples. Illustrative values in this blueprint (`10234695`, `Zylker Inc`) are the vendor's own documentation samples, not credentials |
| No secret in repository files | No `.env`, no committed configuration file and no CI variable file carries a live secret |
| Pre-commit and CI scanning | A secret scanner runs pre-commit and in CI, blocking on detection; a positive hit is treated as an exposure event, requiring rotation under §15.11 even if the commit never reached a shared branch |
| Image hygiene | Container images carry no secret in any layer, including build-time layers; the KEK and every secret handle are injected at runtime |
| Fixtures | Test fixtures use clearly non-functional values with an obvious marker, and the recorded-response fixtures used by the POC mock strategy carry redacted headers |
| Environment separation | Development, Test and Production use **separate Zoho organisations, separate OAuth clients, separate secrets and separate KEKs**. Zoho ERP has no sandbox (§14.4), so this separation is entirely the deployer's responsibility. A shared credential across environments is prohibited, and it is also the fastest route to the 20-refresh-token eviction hazard in §15.9 |

### 26.11 Maker-checker on production connection changes

**Rule.** In `environment = Production`, no change to a connection's identity, credentials, scopes, mappings or schedule takes effect on the maker's action alone. The change is staged, a second `System Administrator` reviews the exact before/after, and only the checker's approval commits it. The maker may not approve their own change; the system rejects the attempt and logs it. In `Development` and `Test`, maker-checker is disabled by configuration and the fact that it is disabled is displayed on SCR-38.

| Change | Maker-checker in Production | Effect on `connection_status` while pending | Rationale |
|---|---|---|---|
| Create a connection profile | Yes | `Draft` | A profile is the trust boundary |
| Run OAuth consent / re-authorise | Yes | `Submitted` → `Under Review` | Consent is the act that grants standing access |
| Change the mapped Zoho organisation | Yes (§14.9.3) | `Under Review` | Re-points every synced record |
| Change `redirect_uri` | Yes | `Under Review` | Invalidates the grant; must be matched in Zoho |
| Rotate the refresh token | Yes | Unchanged; rotation banner shown | Standing-access credential |
| Rotate the client secret | Yes | Unchanged | Standing-access credential |
| Change `required_scopes` (enable/disable a module) | Yes | `Under Review` | Widens or narrows machine authority |
| Change field or dimension mappings | Yes | Unchanged; mapping version staged | A wrong mapping mis-states CWIP silently |
| Change sync direction to include outbound | Yes | Unchanged | First time the connector may write to Zoho |
| Change the sync schedule or polling interval | Yes | Unchanged | Can exhaust the daily call quota |
| Disable the connector | Yes | → `Closed` | Stops the control data feed |
| **Emergency disconnect** | **No** | → `Closed` | Stopping access must never be harder than starting it. Heavily audited, notifies every `System Administrator` |
| Force a full resync | No | Unchanged | Read-only, but the projected call count is recorded |
| Replay a dead-letter record | No | Unchanged | Recorded on the Dead-Letter Record disposition |
| Run connectivity tests | No | Unchanged | Read-only |

Checker view requirements: the checker sees a field-level diff (before, after, changed-by, changed-at, reason), the maker's stated reason, and — for scope changes — the specific business impact text from SCR-34 for every scope added or removed. A checker cannot approve a change whose diff they have not expanded; the approval control is disabled until every changed field is acknowledged.

`MSG-SEC-003` applies to every maker submission: *"You are overriding {control} for {object}. A reason is mandatory and will be stored in the audit trail with your name and the current time."* `MSG-SEC-001` applies to any user without `System Administrator` attempting any of these actions.

### 26.12 Transport, network, environment and data-protection controls

| Control | Requirement |
|---|---|
| Transport | TLS 1.2 or higher on every outbound call to `accounts_domain` and `api_domain`; certificate validation never disabled, in any environment, for any reason |
| Inbound transport | HTTPS only for every connector route including the callback; HSTS enabled |
| Egress control | Outbound calls restricted to the accounts and API hosts of the configured data centre. A call to any other host from the connector runtime is blocked and logged as a security event — this also detects a mis-configured `api_domain` |
| Ingress control | The Zoho ERP web UI is the only place a webhook can be configured (§26.14); if webhooks are adopted, the receiving endpoint is restricted at the network edge as far as the deployment permits. **Zoho's source IP ranges are UNVERIFIED - REQUIRES ZOHO CONFIRMATION**, so IP allow-listing is offered as a hardening option and never as the primary authentication of an inbound event |
| Database access | The connector's database role has no access to the secret-store tables; the secret store is reachable only through the `SecretStore` interface (§26.4.2) running under a distinct workload identity |
| Encryption at rest | Application database and backups encrypted at rest. This is defence in depth **in addition to** envelope encryption of secrets, never instead of it — disk encryption protects a stolen disk, not a compromised query |
| Backups | Backups inherit the same rule: a backup that contains a plain-text secret is a design failure, and because secrets are stored only as ciphertext with the KEK held outside the database, a backup alone yields nothing |
| Multi-factor authentication | Required for every `System Administrator` session that touches this module. Enforced by the application's identity provider; specified in §32 Security and Internal Controls |
| Session controls | Re-authentication required before consent, rotation and disconnect actions, regardless of session age. `MSG-SEC-002` warns of impending expiry |
| Correlation | Every outbound call carries a correlation ID, persisted on Integration Request / Integration Response, so a business record can be traced to the exact HTTP exchange without the payload being retained |

**Personal data in the synced set.** The connector pulls vendor master data, which includes contact-person names, e-mail addresses and phone numbers. Under India's data-protection regime this is personal data, and the following are directly applicable obligations, not general good practice:

- The controller must *"protect personal data in its possession or under its control, including in respect of processing undertaken on its behalf by a Data Processor, by taking reasonable security safeguards to prevent personal data breach"* `[source: https://www.meity.gov.in/static/uploads/2024/06/2bf1f0e9f04e6fb4f8fef35e82c42aa5.pdf — verified 2026-08-05]`, and remains responsible for processing undertaken on its behalf `[source: https://www.meity.gov.in/static/uploads/2024/06/2bf1f0e9f04e6fb4f8fef35e82c42aa5.pdf — verified 2026-08-05]`.
- The itemised minimum safeguards include *"securing of personal data through encryption, obfuscation, masking or the use of virtual tokens mapped to that personal data"* `[source: https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf — verified 2026-08-05]`, and *"visibility on the accessing of such personal data, through appropriate logs, monitoring and review"* `[source: https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf — verified 2026-08-05]`.
- Logs and personal data are to be retained *"for a period of one year, unless compliance with any law for the time being in force requires otherwise"* `[source: https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf — verified 2026-08-05]` — which sets the default retention for connector logs containing personal data at one year and makes an "indefinite log retention" default incorrect.
- Where processing is performed by a processor, there must be *"appropriate provision in the contract entered into between such Data Fiduciary and such a Data Processor"* for reasonable security safeguards `[source: https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf — verified 2026-08-05]` — relevant to the hosting and support arrangement chosen in §40 Deployment Recommendation.
- Breach notification to the regulator carries a deadline of *"within seventy-two hours of becoming aware of the breach, or within such longer period as the Board may allow"* `[source: https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf — verified 2026-08-05]`, which is why §26.15 requires a rehearsed exposure procedure rather than an ad-hoc response.

Design consequences: connector log retention defaults to 12 months for records that may contain personal data and is configurable only upward where another law requires it; every `resolve()` and every payload inspection is logged as an access event; and vendor contact fields are excluded from the default persisted field set in §26.10.1. Whether Atha Group is a Significant Data Fiduciary, and the applicability of specific rules to this processing, requires the client's own legal assessment — **UNVERIFIED - REQUIRES CONFIRMATION**, and §32 Security and Internal Controls carries the jurisdictional caveat in full.

### 26.13 Connector audit log (SCR-40)

The Connector Audit Log is append-only and is the evidence base for every control in this section. It is distinct from the business Audit Log in §32 and is joined to it by correlation ID.

| Field | Content |
|---|---|
| `event_id` | Immutable identifier |
| `event_type` | `PROFILE_CREATED`, `CONSENT_LAUNCHED`, `CONSENT_COMPLETED`, `STATE_VALIDATION_FAILED`, `TOKEN_EXCHANGED`, `TOKEN_REFRESHED`, `TOKEN_REFRESH_FAILED`, `SECRET_WRITTEN`, `SECRET_RESOLVED`, `SECRET_DESTROYED`, `SECRET_REVEAL_ATTEMPTED`, `ROTATION_STARTED`, `ROTATION_COMPLETED`, `ROTATION_ROLLED_BACK`, `ORG_MAPPED`, `ORG_REMAPPED`, `SCOPE_SET_CHANGED`, `SCOPE_MISSING_DETECTED`, `MAPPING_CHANGED`, `SCHEDULE_CHANGED`, `CONNECTOR_DISABLED`, `CONNECTOR_REENABLED`, `EMERGENCY_DISCONNECT`, `EGRESS_BLOCKED`, `MAKER_SUBMITTED`, `CHECKER_APPROVED`, `CHECKER_REJECTED`, `SELF_APPROVAL_BLOCKED`, `LOG_EXPORTED` |
| `connection_profile_id` | Which connection |
| `zoho_organisation_id` | Which Zoho organisation |
| `environment` | `Development` / `Test` / `Production` |
| `actor_user_id`, `actor_role` | Human actor, or `system` for machine events |
| `checker_user_id` | Populated on maker-checker events |
| `before_value`, `after_value` | Field-level diff, **with the secret redactor applied** — for a secret change these record the handle and version, never the value |

| `source_ip`, `user_agent` | For human-initiated events |

| `occurred_at` | ISO 8601 UTC in the record; displayed in the organisation time zone with the zone labelled |
| `outcome` | `Success` / `Failure` / `Blocked`, with the failure reason |

Properties: append-only with no update or delete path exposed anywhere in the application; export permitted to `System Administrator` and `Internal Auditor` with the export itself logged including row count and filter criteria; retention at least as long as the business audit trail, and never shorter than the 12-month floor in §26.12 for records that may contain personal data.

### 26.14 Webhook security — conditional, and currently not adopted

No webhook, event, notification, subscription or callback path exists anywhere in the ERP API: the 84-page documentation index contains no such page, direct URL probes returned 404, and a case-insensitive scan of the 78-module bundle for hook, event, trigger, subscribe, automation, workflow, function, notification, push and callback returned nothing in any path name `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`. Webhooks exist only as a **workflow action configured through the Zoho ERP web UI** — *"Webhooks are user-defined HTTP & HTTPS callbacks that are triggered when a particular event occurs at the source site."* `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`.

Polling is therefore the primary ingestion mechanism (CONF-16, §25 API and Event Architecture), and this application adopts **no webhook** in the POC. Should webhooks be adopted later, the following controls are mandatory, and the first row explains why the adoption bar is high.

| Control | Requirement and its limitation |
|---|---|
| Authentication of the inbound event | Zoho's documented mechanism is a **shared secret token**, not an HMAC signature over the body: *"You can also secure the webhook with a secret token, which cannot be edited or viewed once the webhook is created… It should be alphanumeric and range between 12 - 50 characters."* `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`. A shared secret proves the sender knew the secret; it does **not** prove the body was not modified in transit, and it is replayable |
| Replay protection | **No replay protection is documented.** The receiver must therefore implement its own: a persisted idempotency key derived from the event payload, a receipt window, and rejection of duplicates. Every inbound event is treated as at-least-once |
| Trust level | An inbound event is treated as a **hint to re-read**, never as data. On receipt the connector fetches the authoritative record by id from the ERP API and processes that. This makes body tampering irrelevant to correctness |
| Secret storage | The shared secret is a secret under §26.3 and is stored accordingly. Note it cannot be read back from Zoho once created, so loss requires re-creating the webhook |
| Transport and method | HTTPS only. The vendor documents *"Select the type of API method: PUT, POST, or DELETE. By default, the system selects the POST method."* `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`; the receiver accepts POST only and rejects PUT and DELETE |
| Payload format | Three formats are offered — *"You can choose from Default Payload, x-www-form-urlencoded, and Raw body parameters."* `[source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05]`. The schema of "Default Payload" is not documented, which is a further reason the receiver must not depend on body contents |
| Configuration drift | Webhooks are configured per organisation in the Zoho UI and cannot be listed, verified or created by API. A configuration that is silently deleted in Zoho produces silence, not an error. **Polling must remain enabled as the backstop even if webhooks are adopted** |
| Rate and size limits | Receiver enforces its own body-size cap, per-source rate limit and 200-response-then-process pattern, so a burst cannot become a denial of service |

### 26.15 Credential exposure procedure

A rehearsed procedure, because the 72-hour regulatory clock in §26.12 begins on awareness, not on convenience.

| Step | Action | Owner | Target |
|---|---|---|---|
| 1 | Emergency disconnect on every affected connection profile (no maker-checker; §26.11) | `System Administrator` | Immediate |
| 2 | Destroy every affected secret version (`destroy(handle)`; §26.5) | `System Administrator` | Immediate |
| 3 | Revoke the connected application in the Zoho account UI, since no revocation endpoint is evidenced (§15.12) | `System Administrator` | Immediate |
| 4 | Rotate the client secret in the Zoho developer console (runbook C, §15.11) | `System Administrator` | Same day |
| 5 | Determine the exposure window from Connector Audit Log and API Usage Record: which calls, which organisation, which scopes, what data could have been read or written | `System Administrator`, `Internal Auditor` | Same day |
| 6 | Assess whether personal data was in scope; if so, invoke the client's breach procedure against the deadlines in §26.12 | Client legal / Data Protection Officer | Per statute |
| 7 | Re-establish the connection through wizard steps 8–20 with new credentials | `System Administrator` | After containment |
| 8 | Record a Connector Audit Log entry and a §42 Risk Register review of the root cause | `System Administrator` | Within 5 working days |

### 26.16 Security acceptance tests

These are pass/fail and belong in the POC acceptance run (§37 Acceptance Criteria, §39 Test Scenarios).

| # | Test | Pass criterion |
|---|---|---|
| SEC-01 | Dump every application-database table after a complete wizard run | No client secret, refresh token, access token or authorisation code appears in any column, in any encoding |
| SEC-02 | Attempt to reveal a stored secret through the UI and through every API route | No route returns a secret value to any role, including `System Administrator`. The attempt is logged as `SECRET_REVEAL_ATTEMPTED` |
| SEC-03 | Collect every log sink during a wizard run and a token refresh, and grep for the known secret values | Zero occurrences in application logs, proxy access logs, error reports and exported files. The build fails otherwise (§26.10.1) |
| SEC-04 | Replay an OAuth callback with a valid but already-consumed `state` | Rejected; no token exchange; security event written |
| SEC-05 | Submit a callback with a `state` from a different session | Rejected; security event written |
| SEC-06 | Submit a callback with a `redirect_uri` that differs from the registered value by one character | Rejected at exchange |
| SEC-07 | Attempt to save a redirect URI with a wildcard, a query string, a fragment, or `http://` in `Production` | Rejected at profile save with a field-level message |
| SEC-08 | Inspect browser `localStorage`, `sessionStorage`, cookies and the DOM after setup | No Zoho credential material of any kind |
| SEC-09 | Tamper with one byte of a stored ciphertext and attempt `resolve()` | GCM authentication failure; operation aborts; no retry; security event written |
| SEC-10 | Move a ciphertext row to a different `connection_profile_id` and attempt `resolve()` | Fails on AAD mismatch — it does not decrypt into the wrong context |
| SEC-11 | Maker attempts to approve their own production change | Blocked; `SELF_APPROVAL_BLOCKED` logged |
| SEC-12 | Non-`System Administrator` attempts every action in §14.14 | All refused with `MSG-SEC-001`; each attempt logged |
| SEC-13 | Force the connector runtime to call a host outside the configured data centre | Blocked at egress; `EGRESS_BLOCKED` logged |
| SEC-14 | Run the repository secret scanner over the full history | No finding |
| SEC-15 | Destroy a secret version and attempt to read it from a restored database backup | Unrecoverable — the wrapped DEK for that version no longer exists |
| SEC-16 | Emergency disconnect, then probe `GET /organizations` | Probe fails; if it succeeds, the dashboard shows `Revocation unconfirmed` and instructs revocation in the Zoho account UI |
| SEC-17 | Export a connectivity-test run and an audit log to CSV and PDF | Redaction applied at serialisation; no header, token or body material present |
