## 28. Data Model

This section defines the physical data model of the CAPEX & CWIP control application for all 44 entities in `C4_entities.json`. It is written to be implemented without further business interpretation: every entity carries an explicit field list with data type, mandatory flag, unique key, foreign key, status field, audit fields, source system ID, sync status, version field, effective date and soft-delete flag.

The application owns its own relational store. It does not read or write Zoho ERP tables directly; every Zoho-sourced row arrives through the integration layer described in §25 API and Event Architecture and lands in a mirror entity in this model.

### 28.1 Modelling conventions

| Convention | Rule |
|---|---|
| Target engine | PostgreSQL 15 or later. Types below are PostgreSQL types. `UNVERIFIED - REQUIRES CONFIRMATION` — the client document states no database platform. |
| Table naming | Singular `snake_case`. The registry entity name is the documented name; the table name is given in each entity heading. |
| Primary key | `id UUID` (UUID v7, application-generated, monotonic by creation time). Never a Zoho identifier, never a business code. |
| Business codes | Held in a separate `*_code` column with a partial unique index that excludes soft-deleted rows. |
| Money | `NUMERIC(18,2)`. Never `FLOAT`. Stored in the entity's `currency_code`; reporting converts to the organisation base currency. |
| Percentages | `NUMERIC(6,3)`, stored as a percentage value (76.700), rendered to one decimal per §28.10. |
| Quantities | `NUMERIC(18,4)`. |
| Dates and times | `DATE` for business dates, `TIMESTAMPTZ` (UTC) for system instants. All API payloads, exports and audit records use ISO-8601; screens render `dd-MMM-yyyy`. |
| Enumerations | `VARCHAR(n)` with a `CHECK` constraint, not a native PostgreSQL `ENUM` type — new values must be addable without an exclusive table lock. |
| Status columns | Every value is a `code` from `C3_statuses.json`. No entity may introduce a status label outside those 21. |
| Semi-structured | `JSONB` only for vendor payloads, tag arrays and mapping expressions. Never for a value that participates in a control calculation. |
| Derived amounts | Control figures (exposure, available budget, utilisation) are **calculated**, not authored. Where they are stored, they are stored as snapshots with a `computed_at` stamp and are always reproducible from the ledgers. See §22 Budget and Commitment Calculation Logic. |
| Referential integrity | Enforced by foreign keys with `ON DELETE RESTRICT`. Deletion is logical only (see §28.2.4). |
| Row-level scope | Every table except `organisation` carries `tenant_org_id` and every query is scoped by it. |

### 28.2 The common column envelope

Every entity carries the envelope below unless its entity block states an exception. Field numbering inside each entity block starts after the envelope, so envelope columns are not repeated 44 times.

#### 28.2.1 Identity and scope

| Column | Type | Mandatory | Key | Rule |
|---|---|---|---|---|
| `id` | UUID | Y | PK | UUID v7, generated by the application before insert. |
| `tenant_org_id` | UUID | Y | FK → `organisation.id` | Row-level security predicate. On `organisation` this column equals `id`. |

#### 28.2.2 Audit fields

| Column | Type | Mandatory | Rule |
|---|---|---|---|
| `created_at` | TIMESTAMPTZ | Y | Set once. Immutable. |
| `created_by` | VARCHAR(120) | Y | Principal identifier of the acting user or the service account (`svc.connector`, `svc.scheduler`). |
| `created_by_role` | VARCHAR(40) | Y | Role from `C9_roles.json` in force at the time of the action. |
| `updated_at` | TIMESTAMPTZ | Y | Refreshed on every successful `UPDATE`. |
| `updated_by` | VARCHAR(120) | Y | As above. |
| `updated_by_role` | VARCHAR(40) | Y | As above. |
| `correlation_id` | UUID | N | Ties a row to the request, batch or integration event that produced it. |

Field-level history is **not** kept in the entity row. Every `INSERT`, `UPDATE`, `DELETE`, status change and control override writes to `audit_log` (§28.9.1), which satisfies REQ-SEC-001 (audit trail from budget approval through procurement, accounting and final capitalisation) and REQ-SEC-005.

#### 28.2.3 Version field

| Column | Type | Mandatory | Rule |
|---|---|---|---|
| `row_version` | INTEGER | Y | Default 1. Incremented by trigger on every `UPDATE`. Every `PUT`/`PATCH` API call must send the `row_version` it read; a mismatch returns HTTP 409 and the caller re-reads before retrying. |

`row_version` is technical optimistic locking. It is distinct from **business** version numbers (`budget_version.version_no`, `budget_revision.revision_no`, `approval_matrix.version_no`, `field_mapping.version_no`, `transformation_rule.version_no`), which are user-visible and appear on screens.

#### 28.2.4 Soft-delete flag

| Column | Type | Mandatory | Rule |
|---|---|---|---|
| `is_deleted` | BOOLEAN | Y | Default `false`. No physical `DELETE` is issued by application code against any table in this model. |
| `deleted_at` | TIMESTAMPTZ | N | Mandatory when `is_deleted = true`. |
| `deleted_by` | VARCHAR(120) | N | Mandatory when `is_deleted = true`. |
| `delete_reason` | VARCHAR(500) | N | Mandatory when `is_deleted = true`. Surfaced by `MSG-GEN-001` (irreversible-action confirmation). |

All unique indexes are partial: `WHERE is_deleted = false`. All read models filter `is_deleted = false` by default; the Internal Auditor role can query with deleted rows included.

On the five append-only ledgers and logs (`commitment_ledger`, `actual_ledger`, `budget_ledger`, `audit_log`, `connector_audit_log`) the column is present for envelope uniformity but constrained `CHECK (is_deleted = false)`. Correction is by contra entry only, never by deletion.

#### 28.2.5 Effective date

| Column | Type | Mandatory | Rule |
|---|---|---|---|
| `effective_from` | DATE | Y | Date from which the row is valid for control purposes. |
| `effective_to` | DATE | N | `NULL` means open-ended. `CHECK (effective_to IS NULL OR effective_to >= effective_from)`. |

Master entities (organisation, plant, department, budget head, approval matrix, field mapping, transformation rule) are **effective-dated**: a change closes the current row and opens a successor, so a historical availability check can be replayed against the rules that were in force. Transactional entities set `effective_from` to the governing business date (`po_date`, `bill_date`, `posting_date`) and leave `effective_to` `NULL`.

#### 28.2.6 Source system ID and sync status

| Column | Type | Mandatory | Rule |
|---|---|---|---|
| `source_system` | VARCHAR(20) | Y | `APP`, `ZOHO_ERP`, or `MANUAL_IMPORT`. |
| `source_system_id` | VARCHAR(64) | N | The Zoho record identifier (`purchaseorder_id`, `bill_id`, `project_id`, `fixed_asset_id`, …). Mandatory when `source_system = 'ZOHO_ERP'`. |
| `source_org_id` | VARCHAR(32) | N | The Zoho `organization_id` the record belongs to. Mandatory when `source_system_id` is present. |
| `source_last_modified` | TIMESTAMPTZ | N | The vendor's last-modified stamp where the module exposes one. `NULL` where it does not — fixed assets expose no `created_time` or `last_modified_time`, so their sync is full-refresh (OAS-09). |
| `sync_status` | VARCHAR(28) | Y | Domain in §28.2.7. |
| `last_synced_at` | TIMESTAMPTZ | N | Last successful exchange for this row. |
| `sync_attempt_count` | INTEGER | Y | Default 0. Reset on success. |

`UNIQUE (source_org_id, source_system_id) WHERE is_deleted = false` on every mirror entity. This is the idempotency key that makes replayed integration events safe.

#### 28.2.7 The `sync_status` domain

| Value | Origin | Meaning |
|---|---|---|
| `NOT_APPLICABLE` | Technical value — **no equivalent exists in `C3_statuses.json`** | Row never crosses the Zoho boundary (for example `approval_matrix`). |
| `SYNC_PENDING` | Technical value — **no equivalent exists in `C3_statuses.json`** | Change queued, exchange not yet attempted or in flight. |
| `IN_SYNC` | Technical value — **no equivalent exists in `C3_statuses.json`** | Last exchange succeeded and no local change is outstanding. |
| `INTEGRATION_FAILED` | `C3_statuses.json` | Outbound or inbound sync failed; retry or dead-letter. Drives `MSG-INT-004`. |
| `RECONCILIATION_PENDING` | `C3_statuses.json` | Source and target values differ beyond tolerance. Drives `MSG-INT-006`. |

The three technical values are recorded as a contract gap: `C3_statuses.json` provides negative and warning sync outcomes but no neutral or positive one, and a sync-status column cannot be built from the negative labels alone. They are deliberately **not** presented as business statuses, are never shown in a status chip on a business screen, and appear only in the connector monitoring screens.

### 28.6 Procurement mirrors

### 28.11 Cross-entity integrity rules

| # | Rule | Enforced by |
|---|---|---|
| DM-01 | A commitment or actual ledger entry may only reference a WBS element whose `is_account_assignment = true`. | Check trigger. |
| DM-02 | A ledger entry may not be posted against a project whose `workflow_status` is `FINANCIALLY_COMPLETED`, `CAPITALISED` or `CLOSED`. Blocked with `MSG-PRC-006`. | Check trigger. |
| DM-03 | A purchase order line may not post commitment while `coding_resolution_status <> 'RESOLVED'`. Raises `MSG-BUD-004`. | Application service. |
| DM-04 | `SUM(commitment_ledger.base_amount_signed)` for a purchase order line may never be negative. | Check trigger. |
| DM-05 | `open_commitment_amount` on any line equals `line_amount - billed_amount`, floored at zero, and is never reduced by a goods receipt. | Materialised view test, run nightly. |
| DM-06 | Exactly one `budget_version.is_current = true` per project. | Partial unique index. |
| DM-07 | Budget-version 1 rows are immutable once `RELEASED`. REQ-SEC-003. | Row-level trigger rejecting `UPDATE`. |
| DM-08 | Transfer pairs in `budget_ledger` net to zero at the common ancestor. | Deferred constraint trigger, checked at commit. |
| DM-09 | Every mirror row has a unique `(source_org_id, source_system_id)`. | Partial unique index. |
| DM-10 | Every outbound call resolves to an `api_endpoint_catalogue` row; unlisted paths are refused. | Application service, verified by contract test. |
| DM-11 | `field_mapping` rows targeting a control dimension must have `zoho_object_level = 'LINE'`. | Check constraint. |
| DM-12 | Deleting a master row referenced by any ledger entry is rejected; closure is offered instead. | `ON DELETE RESTRICT` plus service guard. |
| DM-13 | Every status value written to any `*_status` column that is declared as a business status must exist in `C3_statuses.json`. | Check constraint generated from the registry at build time. |
| DM-14 | `audit_log` and `connector_audit_log` hash chains verify end to end. | Nightly verification job; failure raises an internal control incident. |

### 28.13 Worked reference values

The frozen worked examples in `C5_formulas.json` are the acceptance data for this model. Quoted verbatim:

| Context | Budget | Commitment | Actual | Available |
|---|---|---|---|---|
| Budget head - Civil | 25,00,000 | 5,00,000 | 12,00,000 | 8,00,000 |
| Budget head - Plant & Machinery | 80,00,000 | 30,00,000 | 35,00,000 | 15,00,000 |

Commitment-to-actual, part billed: po `20L`, actual_bill `12L`, open_commitment `8L`, budget_exposure `20L`.

PDF section 7 over-budget example: "80L Budget - 35L Actual CWIP - 30L Open PO Commitment = 15L Available. A new PO of 20L exceeds available budget by 5L and must route to exception approval or budget revision."

A seeded database must reproduce every one of these rows from `budget_ledger`, `commitment_ledger` and `actual_ledger` aggregation alone, with no manual snapshot values. That is the acceptance test for §28.
