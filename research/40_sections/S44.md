### 44.2 The questions

#### OQ-01 — Who owns the Purchase Request

**The question.** The Purchase Request has no public API in Zoho ERP. Does Atha Group accept that the Purchase Request is created, approved and held in the new CAPEX and CWIP control application, with the approved request converted into a Zoho ERP Purchase Order?

**Why research cannot resolve it.** The API half of this question *has* been resolved, mechanically: Purchase Request does not exist anywhere in Zoho's own specification — no path, no module, no scope, across all 78 modules, 561 paths and 163 scopes `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`. What research cannot decide is the business consequence. The client's own solution mapping classifies Purchase Request as Zoho ERP **Standard**, and that classification may well be correct at product level: a module can exist in the Zoho ERP user interface and still have no documented public API. The two statements are not the same proposition, and the resolution may be "both true" rather than "one wrong". Whether Atha Group is willing to move PR creation out of Zoho ERP is a business decision.

| Option | What it means | Consequence |
|---|---|---|
| A | Purchase Request owned by the control application; approved PR converted to a Zoho ERP Purchase Order | Full budget control at PR. Users raise PRs outside Zoho ERP. Requires PR-to-PO creation via the documented purchase-order endpoints. |
| B | Purchase Request stays in the Zoho ERP user interface; no API integration | PR data is invisible to the control layer. The PR-stage budget check cannot be automated at all, and the client's workflow step 4 becomes manual. |
| C | Purchase Request stays in Zoho ERP, bridged by custom functions or workflow callbacks | Depends entirely on a bridge capability that is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. Cannot be committed to without a Zoho answer. |

**Recommended default (advisory): Option A.** It is the only option that delivers the client's own workflow step 4 without depending on an unverified capability. The client's "Standard" classification is recorded as correct at product level but not sufficient for an API-first architecture — it is not silently re-classified.

**What changes if the answer differs.** Under B, the PR module in §20 becomes a manual process with no automated check, and POC steps 5 to 8 are demonstrated without integration. Under C, the design cannot be finalised until Zoho confirms the bridge.

#### OQ-10 — Should an approved Purchase Request block budget

**The question.** Should an approved Purchase Request reserve — that is, block — budget before a Purchase Order is raised?

**Why this matters, in the client's own arithmetic.** The client document requires a budget availability check at the Purchase Request stage in three separate places: workflow step 4, section 7 ("At PR/PO approval, the system should read the CAPEX Code and Budget Head and calculate the remaining budget"), and section 9, where an exception is raised when a "PO/PR exceeds available project or budget-head limit". But the document's core control formula counts only Actual CWIP and Open PO Commitments:

> Available Budget = Current Approved Budget − Actual CWIP − Open PO Commitments

An approved Purchase Request therefore reserves nothing. The consequence is concrete and it is a real control weakness: **two Purchase Requests of ₹10L each can both pass a check against ₹15L available, and both can then become Purchase Orders.** The same rupee clears twice. Neither PR is wrong at the moment it is checked; the failure is that the check has no memory.

**Why research cannot resolve it.** It is a client control decision, not a fact. Adding reservation strengthens control and complicates the process — reservations must expire, be released when the PO is raised, and be visible to approvers. Not adding it keeps the client's formula literally true and leaves the race open.

| Option | Behaviour at PR | Consequence |
|---|---|---|
| A — Soft check (the client's stated formula) | Advisory. Availability is displayed to the approver; nothing is reserved | The client's formula holds exactly as written. The two-concurrent-PR race exists. |
| B — Hard reservation | An approved PR creates a reservation that consumes available budget until it converts to a PO or expires | The race is eliminated. The client's stated formula must be extended to subtract PR reservations, so the formula in the client's own section 1 no longer matches the system. |
| C — Configurable per entity or per project | Default soft; hard where the client chooses | Both behaviours are supported. Requires both to be modelled, tested and documented. |

**Recommended default (advisory): Option C, defaulting to Option A.** The client's behaviour is the default so that the system matches the document Atha Group signed off. Hard reservation is a switch, off unless enabled.

**Mandatory regardless of the answer.** The race must not be reachable through a concurrency defect on top of the design decision. The budget check and the resulting consumption are executed against a serialised budget ledger with pessimistic locking on the project-and-budget-head key, so that the only race that exists is the one Atha Group has explicitly chosen by selecting soft checking. Both variants are modelled in §21 with worked examples of the two-concurrent-PR case, and the failure mode is covered by a test scenario in §39.

#### OQ-13 — May budget be reduced or transferred

**The question.** May approved budget be returned (reduced), or transferred between budget heads or between projects? If transfers are permitted, may budget be transferred out of a head that already carries commitment?

**Why research cannot resolve it.** It is a governance decision. The client's revision model is one-directional: the user submits an *additional* budget requirement, the authority approves *additional* CAPEX, and the formula is Original Budget + Approved Revisions = Current Approved Budget. There is no return, no reduction, no transfer between heads and no transfer between projects. The formula as written cannot express a decrease unless revisions are permitted to be negative, which the document never states.

**Recommended default (advisory).** Supplement, return and transfer are implemented as three signed revision types over the same versioned ledger, so that the client's formula continues to hold literally: Current Approved Budget = Original Budget + sum of approved revisions, where returns and transfers-out are negative. The client's immutability rule is preserved exactly — the original budget is never overwritten, and every revision is separately recorded with requestor, approver, date, reason and approval reference.

**The specific hazard to put to the client.** A transfer out of a budget head that already carries commitment can drive that head's available budget negative. Atha Group must state whether transfer after commitment is permitted, and if so whether it requires a higher approval.

#### OQ-15 — Are budgets tax-inclusive or tax-exclusive

**This is the blocking question.**

Exposure is defined explicitly as (Open PO Commitment + Actual CWIP) ÷ Current Approved Budget — the definition that the client's own section 12 data satisfies at all three rows. The threshold is configurable per entity, evaluated at both project and budget-head level by default, one-shot on crossing, and re-armed on budget revision. Recipients are put to the client in §45.

**Related fact the client should know.** Their own three dashboard rows sit at 76.7%, 78.8% and 70.0% — all below their own first threshold. Their sample data never demonstrates the alert their own section recommends. The POC dataset therefore includes at least one project above 80% and one above 90% so the control is demonstrable.

#### OQ-18 — Are "utilisation" and "exposure" one measure or two

**The question.** In the dashboard column headed "Utilisation / Exposure", are utilisation and exposure the same measure? If Atha Group also wants a spend-only measure, what should it be called?

**Why research cannot resolve it.** The client's data settles what the column *is*, but not what Atha Group *means*. Empirically the column is (Open Commitment + Actual CWIP) ÷ Current Budget: all three rows match at one decimal place, and an actual-only reading would give 56.7%, 60.0% and 50.0%, none of which match the printed figures. But the document nowhere states this formula in words, so the equivalence is inferred from the data, not asserted by the document.

**Recommended default (advisory).** Adopt one definition and state it: Exposure = Open PO Commitment + Actual CWIP; Utilisation % = Exposure ÷ Current Approved Budget. If a spend-only measure is also required, it is named distinctly — Actual Utilisation % = Actual CWIP ÷ Current Approved Budget — and never presented under the same label. Two different percentages never appear under one name. The blueprint records that the equivalence was inferred from the data because the client document states no formula for this column.

#### OQ-19 — Is the project-level limit an independent ceiling

**The question.** Is a project-level budget an independent ceiling, or only the sum of its budget heads? May a project hold an unallocated reserve, and if so which authority may allocate it?

**Why research cannot resolve it.** The client document asserts both levels but its own data makes only one of them operative. Section 2 requires budgets at both levels and section 9 raises an exception when a transaction exceeds "available project or budget-head limit", implying two independent ceilings. But in section 6 the project budget is exactly the sum of the five head budgets — ₹25,00,000 + ₹80,00,000 + ₹20,00,000 + ₹15,00,000 + ₹10,00,000 = ₹1,50,00,000 — so a head-level check always binds first and the project-level check can never fire independently. The document never states whether heads must sum to the project budget, whether an unallocated reserve is permitted, or which check takes precedence.

**Recommended default (advisory).** Head-level availability is the binding check. A project-level check also runs, and becomes meaningful only where an unallocated project reserve exists — that is, where the project budget exceeds the sum of head budgets. A validation prevents the sum of head budgets from exceeding the project budget, and any unallocated remainder is exposed as a visible "Unallocated" line so that it cannot be spent invisibly. If WBS is adopted under OQ-02, the same question recurs one level down and must be answered once for all levels.

#### OQ-20 — Does a draft purchase order consume budget

**The question.** Should a draft purchase order — one created in Zoho ERP but not yet approved — consume budget?

**Why research cannot resolve it.** Part of it is researchable: whether Zoho ERP purchase orders carry a draft and approval status model, and what filtering is available for incremental pull, is answerable from the specification. But whether a draft *should* consume budget is a client control decision. The client document conflates creation and approval — workflow step 6 says "Approved PO is created in Zoho ERP and reserves/commits the budget" — while section 8's first row is labelled "PO approved" and section 7 places validation at "PR/PO approval".

**The compounding constraint.** Because webhook availability is **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**, the moment of commitment may be detected only at the next poll. There is therefore a window in which budget is consumed in Zoho ERP but not yet visible in the control layer.

**Recommended default (advisory).** Commitment is recognised when a purchase order's status becomes approved or open in Zoho ERP, detected by incremental polling with a look-back window. The pre-approval budget check is performed in the control layer *before* the purchase order is raised, so the check does not depend on the polling latency. The detection latency is documented explicitly in §27 as a stated control limitation, with the exposure window quantified, and it is paired with a failed-sync-after-PO-approval test case in §39.

#### OQ-21 — Which definition of assigned value governs the control

**The question.** Does Atha Group ratify their own availability formula as sufficient, in the knowledge that it corresponds to a narrower definition of consumption than the authoritative SAP definition and will therefore permit more spend?

**Why research cannot resolve it.** Research has already established the facts; what remains is a control-appetite decision for Atha Group and their auditor. Two non-equivalent SAP definitions of assigned value exist. The compact definition is the total of commitment and actual postings, shown only when availability control is active `[source: https://help.sap.com/doc/acd8b65334e6b54ce10000000a174cb4/3.6/en-US/0213d553088f4308e10000000a174cb4.html — verified 2026-08-05]` (SAP Project System; variant: S/4HANA on-premise documentation set). The authoritative definition is a nine-component calculated aggregate, not a single stored field, which additionally includes statistical actual costs, settlement debits, settlement credits to budget-controlled objects, statistical actual costs of subordinate WBS elements that do not carry budget, and the **maximum** of plan versus actual-plus-commitment for assigned networks and orders `[source: https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/4dd8cb7b1c484b4b93af84d00f60fdb8/f711d553088f4308e10000000a174cb4.html — verified 2026-08-05]` (variant: S/4HANA on-premise).

Atha Group's formula resembles the **compact** definition. Building availability control on it will therefore **systematically understate consumption and permit overspend relative to SAP behaviour** wherever the additional components carry value.

| Option | What it means |
|---|---|
| A | Ratify the client formula as the control | Simple, matches the signed-off document. Understates consumption; the understatement must be visible. |
| B | Adopt the broader definition as the control | Stronger control. The client's own worked examples cease to reproduce, and the control model must be re-baselined with Atha Group. |
| C | Client formula as the control, broader components reported alongside | Control behaviour unchanged; the gap is measurable and auditable. |

**Recommended default (advisory): Option C.** The client formula is implemented as the primary control exactly as stated, and the additional components are exposed as an explicit, separately reported **"other assigned value"** line, so that the understatement is visible rather than silent. This is the position recorded in ASM-38. It requires Atha Group's ratification before it can be treated as settled.
