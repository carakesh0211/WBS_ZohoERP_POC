### 1.4 Evidence method

This blueprint was produced under a three-stage evidence method. No stage is optional and no claim reaches the document without passing all three.

**Stage 1 — Fifteen research lanes.** Fifteen independent research lanes (R01–R15) collected primary-source material on SAP Project System and work breakdown structures, SAP budgeting and availability control, SAP settlement and asset-under-construction handling, manufacturing CAPEX practice, Zoho ERP API surface, OAuth and data-centre behaviour, integration patterns, and enterprise UI conventions. Each lane recorded discrete claims with a source URL, a source tier and a verbatim evidence quote. The corpus is 1,527 claims.

**Stage 2 — Adversarial verification.** Ten verifier passes (V01–V10) re-fetched each source and tested each claim against the retrieved text rather than against the researcher's summary of it. The verifier could return CONFIRMED, CONFIRMED-REPLACED-QUOTE, OVERSTATED (with a mandatory `narrower_true_statement` replacing the original), UNVERIFIED - REQUIRES CONFIRMATION, CONTRADICTED, or NOT-YET-VERIFIED.

| Verdict | Count |
|---|---|
| CONFIRMED | 894 |
| CONFIRMED-BY-VENDOR-SPECIFICATION | 204 |
| OVERSTATED (narrowed, original discarded) | 45 |
| CONFIRMED-REPLACED-QUOTE | 14 |
| UNVERIFIED - REQUIRES CONFIRMATION | 22 |
| CONTRADICTED | 3 |
| NOT-YET-VERIFIED | 345 |
| **Total claims** | **1,527** |

Verification found 45 claims that were true only in a narrower form than originally written, and 3 that were false. It also found 18 records that stated rules specific to S/4HANA Cloud Public Edition as though they were general SAP rules. That is why every SAP statement in this blueprint names the SAP variant its source documents. Where a source did not make the variant clear, the blueprint says so rather than guessing.

**Stage 3 — Mechanical verification against the vendor's own specification.** Zoho's official OpenAPI bundle for the ERP API was downloaded and parsed mechanically. Every Zoho endpoint, path, HTTP method, request field, response field and OAuth scope in this document is taken from that parse, not from documentation pages and not from recollection.

`[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

The mechanical parse produced eleven findings (OAS-01 to OAS-11) that constrain the design. Four of them are hard negatives — statements about what the API does **not** provide — and they are load-bearing for the architecture:

1. Purchase Request does not exist anywhere in the specification: no path, no module, no scope, across all 78 modules, 561 paths and 163 scopes. This is a proven clean negative, not a failed search. Purchase Request must therefore be owned by our application.
2. Purchase Receive lines carry no link to a purchase order line, no project, tag or custom-field coding, and the module exposes no list endpoint. Received-but-unbilled exposure must be reconstructed by our application. Bill lines *do* carry `purchaseorder_item_id`, so purchase-order-to-bill line matching works — the two legs must not be confused.
3. There is no API to create a custom field *definition*; only to set values on a record. The CAPEX and WBS custom-field layout is a manual prerequisite in the Zoho ERP user interface, per organisation.
4. Fixed assets carry no link to a source project, purchase order or bill, and expose no last-modified field, so asset synchronisation must be full-refresh and capitalisation traceability must be anchored on our own capitalisation record.

**Rule for anything not evidenced.** Any statement about Zoho that could not be evidenced from the specification or from a verified citable claim is written verbatim as **UNVERIFIED - REQUIRES ZOHO CONFIRMATION**. Any other unevidenced statement is written verbatim as **UNVERIFIED - REQUIRES CONFIRMATION**. These markers are never softened, never omitted and never replaced by a plausible guess. A page that could not be fetched is recorded as inaccessible; inaccessibility is never treated as confirmation.

**Citation format.** Source-backed statements carry `[source: <url> — verified 2026-08-05]`. Statements derived from the vendor specification carry `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`.

### 1.6 Provenance discipline

The client requirement document contains **no work breakdown structure of any kind** — its budget structure is exactly two levels, CAPEX/CWIP project code and budget head. Multi-level WBS, WBS-level budgeting, Purchase Request budget reservation, the dedicated connector setup module, webhook handling, the SAP-familiar interface mandate and the multi-entity/multi-organisation scope all originate in the engagement brief or are derived recommendations. Every such item is tagged `provenance=MASTER-PROMPT` or `provenance=DERIVED-RECOMMENDATION` wherever it appears, and is never presented as a confirmed client requirement. §3 states the split explicitly; §4 carries it into the traceability matrix.

### 1.7 Intellectual property and SAP references

This document describes enterprise interface patterns associated with SAP in its own words. It contains no SAP logos, marks, theme colour values, screenshots or asset references, and no verbatim SAP text exceeding 15 words. It does not state or imply SAP endorsement, certification or partnership. Design tokens come from the frozen token registry only. Every SAP behavioural claim names the SAP variant its source documents — classic on-premise, S/4HANA on-premise, or S/4HANA Cloud Public Edition — because those variants differ materially on budgeting, availability control and settlement.

### 1.8 Status of the research directory

The `research/` directory holds the supporting evidence for this blueprint: the intake material, the fifteen research lanes, the ten verifier outputs, the parsed Zoho specification, the endpoint inventory, the frozen contract registries and the quality-assurance gates.

**`research/` is not part of the deliverable.** It is the working evidence base. The deliverable is the single Markdown document `SAP_WBS_Zoho_ERP_POC_Blueprint.md`. The blueprint must be complete and implementable on its own: a coding agent given only the blueprint must be able to build the POC without opening any file under `research/`. References to research artefacts appear in this document only as citations establishing provenance, never as a dependency the reader is required to resolve. If the blueprint appears to require a research file in order to be actionable, that is a defect in the blueprint, not an instruction to ship the research directory.
