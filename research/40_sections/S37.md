## 37. Acceptance Criteria

### 37.1 How to read this section

One acceptance criterion per user story, in given/when/then form, numbered so that `AC-nn` corresponds to `US-nn` in §36 User Stories. Every figure is drawn either from the frozen worked examples in the formula registry — quoted verbatim, never recomputed — or from the seeded dataset in §38 Sample Data. Nothing here is illustrative; a build that produces a different number has failed.

**Identifier note.** `AC-nn` is a sequence authored in this section, as `RISK-nn` is authored in §42 Risk Register. The frozen identifier table defines no scheme for acceptance criteria.

**Conventions in force throughout.**

| Item | Rule |
|---|---|
| Currency | Rupee symbol prefixed, no space. Indian digit grouping, e.g. ₹1,50,00,000. Two decimals on transaction screens, none on dashboard tiles, one decimal on percentages. Negatives in parentheses. |
| Lakh and crore | Permitted only on dashboard tiles and chart axes. Full grouped figures everywhere else. Where a frozen worked example uses `L` or `Cr`, it is quoted in its original notation. |
| Dates | `dd-MMM-yyyy` in prose and on screen; ISO-8601 in payloads, exports and audit records. |
| Formula | Exposure = Open PO Commitment + Actual CWIP. Available Budget = Current Approved Budget - Exposure. Utilisation % = Exposure / Current Approved Budget. Current Approved Budget = Original Budget + Approved Supplements - Approved Returns +/- Approved Transfers. |
| Statuses | Only the 21 frozen labels. Every status must be distinguishable without colour — icon plus text. |
| Messages | Only the frozen message identifiers, and every message must name the object, the numbers and at least one next action. |

**The four acceptance criteria that outrank the rest.** If AC-16, AC-31, AC-28 and AC-36 pass and everything else fails, the control model is sound. If any one of those four fails, the POC has not demonstrated CAPEX control regardless of what else works.

### 37.2 E1 — Project and WBS structure

#### AC-01 — Create a CAPEX Project (US-01)
- **Given** a **Project Manager** is signed in and no project exists with the code `CAPEX-2026-004`.
- **When** they complete SCR-05 with code `CAPEX-2026-004`, name *Effluent Treatment Upgrade*, entity `ENT-01`, plant `PLT-02`, department *Projects and Engineering*, owner *R. Venkataraman*, asset category *Plant and Machinery*, timeline `2026-09-01` to `2027-06-30`, CWIP GL `1803 CWIP - Plant & Machinery`, and save.
- **Then** the project is created with status **Draft**, appears on SCR-04, and the audit trail carries a creation record with the actor and an ISO-8601 timestamp.
- **And** procurement against it is refused until a budget version is **Released**, with `MSG-PRC-006` naming the status.

#### AC-02 — Duplicate CAPEX code refused (US-02)
- **Given** `CAPEX-2026-001` already exists as *New Production Line*.
- **When** a **Project Manager** attempts to save a second project with code `CAPEX-2026-001`.
- **Then** the save is refused at field level beneath the code field, focus moves to that field, and the message names the existing project *New Production Line* rather than saying only that the value is in use.
- **And** no partial project record is written.

#### AC-03 — Entity and plant recorded (US-03)
- **Given** two entities (`ENT-01`, `ENT-02`) and two plants (`PLT-01`, `PLT-02`) exist, with `PLT-01` belonging to `ENT-01` and `PLT-02` to `ENT-02`.
- **When** a **System Administrator** assigns plant `PLT-01` to a project whose entity is `ENT-02`.
- **Then** the save is refused because the plant does not belong to the selected entity, and the message names both.
- **And** with a valid pairing, SCR-01 can filter to a single entity and the totals shown equal the sum of that entity's projects only.

#### AC-04 — Three-level WBS (US-04)
- **Given** project `CAPEX-2026-002` *New Manufacturing Plant - Phase 1* exists.
- **When** a **Project Manager** opens SCR-07.
- **Then** the tree table shows 3 level-1 nodes, 11 level-2 nodes and 6 level-3 nodes, each row collapsible, each row showing WBS code, description, Current Approved Budget, Open PO Commitment, Actual CWIP, Available Budget and Utilisation %.
- **And** the level-2 node `CAPEX-2026-002.2.1` *Plant and machinery* shows Current Approved Budget **₹4,15,00,000**, being the sum of its three level-3 children ₹1,80,00,000 + ₹1,75,00,000 + ₹60,00,000, with no figure enterable directly at level 2.
- **And** an attempt to create a level-4 node is refused, naming the configured maximum depth of 3.

#### AC-05 — A project with no WBS behaves as project plus budget head (US-05)
- **Given** project `CAPEX-2026-001` has zero WBS elements.
- **When** any user opens SCR-05, raises a Purchase Request, or runs an availability check against it.
- **Then** every screen, check and message operates on (project, budget head) alone, the WBS column is absent rather than empty, and no WBS reporting tag is written to any outbound Zoho document for this project.
- **And** the budget-head register for `CAPEX-2026-001` reproduces the frozen figures exactly: **Civil** budget 25,00,000, commitment 5,00,000, actual 12,00,000, available 8,00,000; **Plant & Machinery** budget 80,00,000, commitment 30,00,000, actual 35,00,000, available 15,00,000.

### 37.3 E2 — Budget definition and release

#### AC-08 — Unallocated project reserve visible (US-08)

#### AC-10 — Original Budget immutable (US-10)

#### AC-11 — Roll-up from (WBS element, budget head) (US-11)
- **Given** budget lines exist at (WBS element, budget head) granularity for `CAPEX-2026-002`.

### 37.4 E3 — Purchase Request and the availability check

- **Given** a **Requestor** is signed in and project `CAPEX-2026-002` has a released budget.

- **Then** the Purchase Request moves **Draft** → **Submitted**, and the Integration Event log for this transaction shows **zero** outbound Zoho calls.
- **And** the connector never attempts a Purchase Request endpoint, because none exists in the Zoho ERP API specification. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]`

#### AC-14 — Budget head mandatory on every line (US-14)
- **Given** `PR-2026-0021` is in **Draft** with line 2 carrying a CAPEX code but no budget head.
- **When** the **Requestor** submits.
- **Then** submission is refused, an error summary appears at the top of the form linking to the failing field, and `MSG-BUD-004` is shown: *A CAPEX code and budget head are mandatory on capital procurement. Select a budget head for line 2 before submitting.*
- **And** line 1, which is correctly coded, is not lost.

#### AC-15 — Available Budget visible before submission (US-15)
- **Given** budget head **Consultancy & Other** on `CAPEX-2026-002` has Current Approved Budget ₹15,00,000, Open PO Commitment ₹0 and Actual CWIP ₹4,50,000.
- **When** a **Requestor** selects that head on a Purchase Request line.
- **Then** the line panel shows Current Approved Budget **₹15,00,000.00**, Open PO Commitment **₹0.00**, Actual CWIP **₹4,50,000.00**, Exposure **₹4,50,000.00** and Available Budget **₹10,50,000.00**, refreshed on every change of head.
- **And** the figures shown are computed from the ledgers at request time, not cached from page load.

#### AC-16 — The availability check (US-16) — **load-bearing**
- **Given** budget head **Plant & Machinery** on `CAPEX-2026-001` carries the frozen position: Approved Budget 80,00,000, PO Commitment 30,00,000, Actual CWIP 35,00,000, Available 15,00,000.
- **When** a **Project Finance Controller** opens SCR-13 for that budget head.
- **Then** the screen reproduces the frozen worked example exactly: *80L Budget - 35L Actual CWIP - 30L Open PO Commitment = 15L Available.*
- **And** the screen shows Available Budget **₹15,00,000.00** in full Indian grouping, with the lakh notation appearing only where the frozen example is quoted.
- **And** the same check run at project level for `CAPEX-2026-001` returns Current Approved Budget **₹1,50,00,000**, Open PO Commitment **₹47,00,000**, Actual CWIP **₹63,00,000**, Available Budget **₹40,00,000** — the frozen TOTAL row, derived by summation and not stored.
- **And** the check names which level is binding: budget-head availability binds; project-level availability becomes meaningful only where an Unallocated reserve exists.

#### AC-17 — Serialised availability under concurrency (US-17)
- **Given** budget head **Testing and Commissioning** on `CAPEX-2026-002` has Current Approved Budget **₹10,00,000**, zero commitment and zero actual, and hard reservation is switched on for the entity.
- **When** two **Requestor** sessions submit `PR-2026-0014` and `PR-2026-0015`, each for **₹8,00,000.00**, within the same second.
- **Then** exactly one is accepted and one is refused with `MSG-BUD-001` naming a shortfall of **₹6,00,000**.
- **And** the Budget Ledger contains exactly one reservation row of ₹8,00,000, never two, and never one of ₹16,00,000.
- **And** with hard reservation switched off — the client document's own default behaviour — both are accepted and the exposure gap is surfaced on SCR-25 as a known consequence of soft checking, not hidden.

#### AC-18 — Within-budget normal approval route (US-18)
- **Given** `PR-2026-0021` line 1 for **₹9,00,000.00** is submitted against Available Budget **₹10,50,000.00**.
- **When** the availability check completes.
- **Then** the request is routed to the normal approval route and appears in the **Department Head** inbox on SCR-03, with the availability figure that was current at routing time stored on the Approval Instance.
- **And** on approval the status becomes **Approved** and the stored availability figure is displayed alongside the decision, so a later change of availability does not rewrite history.

#### AC-19 — Over-budget exception route (US-19) — **load-bearing counterpart**
- **Given** budget head **Plant & Machinery** on `CAPEX-2026-001` has Available Budget ₹15,00,000, per the frozen example.
- **When** a **Requestor** submits `PR-2026-0007` for **₹20,00,000.00** against that head.
- **Then** the transaction is not offered the normal approval route at all, the check result is **Budget Exceeded** and the request becomes **Exception Pending**.
- **And** the frozen consequence is reproduced: *A new PO of 20L exceeds available budget by 5L and must route to exception approval or budget revision.*
- **And** two routes are presented — exception approval, and budget revision — with neither pre-selected and neither auto-executed.

#### AC-20 — The over-budget message (US-20)
- **Given** the conditions of AC-19.
- **When** the check fails.
- **Then** a page-level message strip below the header shows `MSG-BUD-001` populated as: *The proposed Purchase Request value of ₹20,00,000 exceeds the available budget of ₹15,00,000 for CAPEX-2026-001 (Plant & Machinery) by ₹5,00,000. Submit a budget revision or request exception approval.*
- **And** the message is not a toast, because the user must act on it.
- **And** it contains no bare error code and no technical exception text.

### 37.5 E4 — Commitment

#### AC-21 — Approved request becomes a coded purchase order (US-21)
- **Given** `PR-2026-0021` line 1 is **Approved**.
- **When** **Procurement** converts it to a purchase order.
- **Then** the connector issues `POST {BASE_V3}/purchaseorders` with scope `ERP.purchaseorders.CREATE`, then `POST {BASE_V3}/purchaseorders/{purchaseorder_id}/submit` and `POST {BASE_V3}/purchaseorders/{purchaseorder_id}/approve`, both with scope `ERP.purchaseorders.CREATE`.
- **And** the created line carries `project_id` for the CAPEX code, a `tags[]` entry whose `tag_option_id` is the WBS element, `account_id` for the budget head and an `item_custom_fields[]` entry echoing the Control Hub line key.
- **And** a line that cannot be fully coded is refused before the call is made; no partially coded purchase order is created in Zoho.

#### AC-22 — Approved and open purchase orders consume budget (US-22)
- **Given** purchase order `PO-2026-2002` for **₹3,50,00,000.00** is approved and open with **₹1,20,00,000.00** billed.
- **When** the availability check runs for budget head **Plant & Machinery** on `CAPEX-2026-002`.
- **Then** Open PO Commitment is **₹2,30,00,000.00**, being the unbilled balance only, and Actual CWIP is **₹1,20,00,000.00**.
- **And** Exposure is **₹3,50,00,000.00** and Available Budget is **₹65,00,000.00** against a Current Approved Budget of ₹4,15,00,000.
- **And** the unbilled portion still consumes budget even though no vendor bill exists for it.

#### AC-23 — Commitment recognised on approval, with stated latency (US-23)
- **Given** a purchase order is approved directly in Zoho ERP at 10:14 on 03-Jul-2026 and the poll interval is five minutes with a fifteen-minute look-back window.
- **When** the next incremental poll of `GET {BASE_V3}/purchaseorders` filtered on `last_modified_time` runs.
- **Then** the commitment appears in the Commitment Ledger, and SCR-15 shows a *last synchronised* timestamp and the configured detection window.
- **And** the detection latency is stated on the screen as a control limitation rather than being invisible, because commitment may be consumed in Zoho before the control layer sees it.
- **And** a record whose `last_modified_time` falls inside the look-back window but which was already ingested is deduplicated on its idempotency key, not ingested twice.

#### AC-24 — Upward amendment revalidates only the delta (US-24)
- **Given** `PO-2026-2002` is **₹3,50,00,000.00** and budget head **Plant & Machinery** has Available Budget **₹65,00,000.00**.
- **When** **Procurement** amends line 2 by **+₹25,00,000.00** and line 3 by **+₹20,00,000.00**, a total increase of **₹45,00,000.00**.
- **Then** only **₹45,00,000.00** is revalidated, not the new total of ₹3,95,00,000, and the check passes because ₹45,00,000 is less than ₹65,00,000.
- **And** `MSG-PRC-001` is shown: *PO-2026-2002 has increased from ₹3,50,00,000 to ₹3,95,00,000. The additional ₹45,00,000 has been revalidated against CAPEX-2026-002.2.1 (Plant & Machinery), where ₹65,00,000 is available.*
- **And** Open PO Commitment becomes **₹2,75,00,000.00**, Actual CWIP is unchanged at **₹1,20,00,000.00**, Available Budget becomes **₹20,00,000.00** and utilisation becomes **95.2%**, firing `MSG-BUD-003` exactly once.
- **And** the outbound `PUT {BASE_V3}/purchaseorders/{purchaseorder_id}` body contains the complete `line_items` array, not only the changed lines.

#### AC-25 — Cancellation and closure release the right amount (US-25)
- **Given** `PO-2026-2003` for USD 25,000.00 at 88.0000, equal to **₹22,00,000.00**, is unbilled; and `PO-2026-2005` for **₹18,00,000.00** has **₹5,00,000.00** billed.
- **When** `PO-2026-2003` is cancelled and `PO-2026-2005` is closed.
- **Then** for `PO-2026-2003` the whole **₹22,00,000.00** is released, Exposure on **Utilities** returns to **₹0.00** and Available Budget returns to **₹60,00,000.00**, with `MSG-PRC-002`.
- **And** for `PO-2026-2005` only the unbilled residual **₹13,00,000.00** is released, Actual CWIP remains **₹5,00,000.00**, and `MSG-PRC-003` names billed ₹5,00,000, ordered ₹18,00,000 and residual ₹13,00,000.
- **And** the frozen cancellation position is reproduced for the unbilled case: PO Value **20L**, Actual Bill **0**, Open Commitment **0**, Budget Exposure **0**.

#### AC-26 — Purchase order raised outside the process is detected (US-26)
- **Given** a purchase order carrying CAPEX code `CAPEX-2026-002` exists in Zoho with no matching approved Purchase Request in the control layer.
- **When** the nightly coverage reconciliation runs.
- **Then** the purchase order appears on SCR-25 as a coverage exception naming the purchase order number, its value and the missing Purchase Request.
- **And** the commitment is still recorded, because the money is genuinely committed; the exception concerns governance, not arithmetic.

### 37.6 E5 — Receipt, vendor bill and actual CWIP

#### AC-27 — Goods receipt does not release commitment (US-27)
- **Given** `PO-2026-2001` is ordered at **₹1,20,00,000.00** with **₹0.00** billed.
- **When** receipts `GRN-2026-0001` for **₹35,00,000.00** and `GRN-2026-0002` for **₹25,00,000.00** are recorded.
- **Then** Open PO Commitment remains **₹1,20,00,000.00** and Actual CWIP remains **₹0.00**.
- **And** Exposure is unchanged at **₹1,20,00,000.00**; receipt moves nothing between buckets.

#### AC-28 — Received-but-unbilled is its own bucket (US-28) — **load-bearing**
- **Given** `PO-2026-2001` has ordered **₹1,20,00,000.00**, received **₹60,00,000.00** and billed **₹45,00,000.00**.
- **When** a **Project Finance Controller** opens SCR-16 or SCR-18.
- **Then** three distinct figures are shown: Open PO Commitment **₹75,00,000.00**, Received but unbilled **₹15,00,000.00**, Actual CWIP **₹45,00,000.00**.
- **And** received-but-unbilled is included in exposure and is neither added to commitment nor added to actual, so no value falls between the two events.
- **And** `MSG-PRC-005` is available on ageing, naming the amount and the age of the oldest unbilled receipt.
- **And** the screen states plainly that received-but-unbilled is reconstructed by the control application because Zoho purchase receive lines carry no link to a purchase order line and the module has no list endpoint.

#### AC-29 — Vendor bill posts to the right CWIP account (US-29)
- **Given** budget head **Civil** is bound to CWIP account `1802 CWIP - Civil`.
- **When** bill `BILL-2026-0006` of **₹30,00,000.00** coded to that head is ingested.
- **Then** the Actual Ledger row carries account `1802`, project `CAPEX-2026-002`, WBS `.1.2.1` and budget head **Civil**.
- **And** the sum of Actual Ledger rows per account equals the sum of Zoho bill lines per `account_id` for the same period, to ₹0.00.

#### AC-30 — Bill line matched to purchase order line automatically (US-30)
- **Given** bill `BILL-2026-0006` line 1 carries `purchaseorder_item_id` equal to the identifier of `PO-2026-2001` line 1.
- **When** the bill is ingested.
- **Then** the match is made on `purchaseorder_item_id` with no manual intervention, and commitment relief is applied to that purchase order line only.
- **And** a bill line with no `purchaseorder_item_id` is treated as a direct CWIP bill: it increases Actual CWIP, relieves no commitment, and is flagged for review because the client document does not state the treatment of bills booked without a purchase order.

#### AC-31 — No double counting (US-31) — **load-bearing**
- **Given** the four frozen commitment-to-actual positions.
- **When** each is evaluated.
- **Then** the part-billed position reproduces exactly: PO **20L**, Actual Bill **12L**, Open Commitment **8L**, Budget Exposure **20L**.
- **And** Budget Exposure for a purchase order is unchanged by billing progress at every position — only its split between commitment and actual moves.
- **And** a purchase order line contributes to commitment only for its unbilled balance, and a bill line converts commitment to actual for its own value, never adding to both.
- **And** at project level for `CAPEX-2026-001` the totals are Open PO Commitment **₹47,00,000**, Actual CWIP **₹63,00,000**, Exposure **₹1,10,00,000** and Available Budget **₹40,00,000**, agreeing with the frozen TOTAL row.

#### AC-32 — Bill exceeding the purchase order line (US-32)
- **Given** `PO-2026-2001` line 1 is ordered at **₹50,00,000.00** with **₹30,00,000.00** already billed.
- **When** a bill line of **₹25,00,000.00** is ingested against it, taking billed value to ₹55,00,000.00.
- **Then** `MSG-PRC-004` is raised naming bill number, line number, bill amount ₹25,00,000, purchase order line amount ₹20,00,000 remaining and an excess of **₹5,00,000**.
- **And** the excess increases Actual CWIP and is separately reported, and commitment for that line floors at **₹0.00** — it never goes negative.
- **And** the transaction is held for confirmation rather than silently posted, because two defensible treatments exist and the client has not chosen one.

#### AC-33 — Credit note and bill reversal (US-33)
- **Given** Actual CWIP on budget head **Electrical** for `CAPEX-2026-001` is **₹8,00,000.00**.
- **When** a vendor credit of **₹1,50,000.00** against the originating bill is ingested through `GET {BASE_V3}/vendorcredits` with scope `ERP.debitnotes.READ`.
- **Then** Actual CWIP falls to **₹6,50,000.00** and Available Budget rises by **₹1,50,000.00**.
- **And** where the credit relates to an unbilled portion, commitment is restored rather than actual reduced, and the two cases are distinguished on SCR-18 rather than netted.

### 37.7 E6 — Budget revision, supplement, return and transfer

#### AC-34 — Budget supplement raised (US-34)
- **Given** `PR-2026-0007` for ₹20,00,000 is **Exception Pending** against **Plant & Machinery** on `CAPEX-2026-001` with a shortfall of ₹5,00,000.
- **When** a **Project Finance Controller** raises revision `REV-2026-0001` for **₹5,00,000** with a justification.
- **Then** the revision is created with type **Budget Supplement**, status **Submitted**, and it is linked to the Purchase Request that triggered it.
- **And** the Current Approved Budget is unchanged until approval; a pending revision has no control effect.

#### AC-35 — Revision approved with full attribution (US-35)
- **Given** `REV-2026-0001` is **Submitted**.
- **When** a **CAPEX Committee** member approves it on 14-Jul-2026 with reason *Vendor price escalation on melting package* and approval reference `CAPEX-COM/2026/07/11`.
- **Then** the revision becomes **Approved**, and the record stores requestor, approver, `2026-07-14`, reason and approval reference.
- **And** `MSG-BUD-005` is shown: *Revision REV-2026-0001 approved by A. Mukherjee on 14-Jul-2026. Current approved budget for CAPEX-2026-001 (Plant & Machinery) is now ₹85,00,000 (original ₹80,00,000, revisions ₹5,00,000). The original budget is unchanged.*

#### AC-36 — Version history and immutability (US-36) — **load-bearing**
- **Given** `CAPEX-2026-001` has budget version 1 (original) and version 2, and `REV-2026-0001` has just been approved creating version 3.
- **When** a **Project Finance Controller** opens SCR-10 and compares version 2 with version 3.
- **Then** the comparison shows, per budget head, the version 2 figure, the version 3 figure and the delta, with **Plant & Machinery** moving from ₹80,00,000 to ₹85,00,000 and every other head unchanged.
- **And** the identity holds at ₹0.00: Current Approved Budget = Original Budget + Approved Supplements - Approved Returns +/- Approved Transfers.
- **And** version 1 remains readable and its figures are byte-identical to the day it was released.

#### AC-37 — Budget transfer is net zero and cannot strand commitment (US-37)

### 37.12 E11 — Sync operation, failure recovery and reconciliation

#### AC-60 — Initial full synchronisation (US-60)
- **Given** an empty control-layer master-data cache.
- **When** the administrator runs the initial sync of vendors, items, locations and chart of accounts.
- **Then** the four counts match the source exactly, pagination uses `page` starting at 1 and `per_page` of 200, and the `Sync Cursor` for each records a full-refresh snapshot rather than a timestamp.
- **And** a second run produces zero net changes and does not duplicate any record.

#### AC-61 — Incremental synchronisation with a look-back window (US-61)
- **Given** a stored cursor at `2026-07-03T10:00:00+05:30` and a look-back window of fifteen minutes.
- **When** the incremental poll runs.
- **Then** the request filters on `last_modified_time` from `2026-07-03T09:45:00+05:30`, records already ingested are deduplicated on their idempotency key, and the cursor advances only after the page is fully processed.
- **And** a failure mid-page leaves the cursor unmoved, so the page is re-fetched rather than skipped.

#### AC-62 — Token refresh, and failure of refresh (US-62)
- **Given** the access token has expired.
- **When** any call returns unauthorised.
- **Then** the client refreshes once, retries the original call once, and both succeed, with a single refresh and a single retry visible in the log and both token values redacted.
- **And** where refresh itself fails, sync pauses and `MSG-INT-002` names the organisation and the time since the pause, rather than the client retrying indefinitely.
- **And** the wizard warns before a re-consent that would take the user past the documented maximum of 20 refresh tokens per user, because exceeding it silently deletes the oldest token whether or not it is in use. `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]`

#### AC-63 — Rate-limit handling (US-63)
- **Given** the documented limit of 100 requests per minute per organization and a concurrent soft limit of 10 calls. `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`
- **When** the Simulator returns throttled responses for 30 seconds during a sync of 400 records.
- **Then** the client backs off with jitter, never exceeds 10 concurrent calls, and all 400 records are ingested with zero loss and zero duplication.
- **And** `MSG-INT-003` names the organisation and the pending count, and SCR-38 shows calls used against the limit for the current window.

#### AC-64 — Retry and dead letter (US-64)
- **Given** a record that fails permanently because its payload is malformed.
- **When** it exhausts the configured retry count.
- **Then** it is moved to a `Dead-Letter Record` with the last error preserved verbatim, and `MSG-INT-004` names the record type, identifier, attempt count and last error.
- **And** it appears on SCR-39, is replayable by a **System Administrator** only, and replay after correction closes the record.
- **And** no record is discarded and no record is retried without bound.

#### AC-65 — Line-level reconciliation (US-65)
- **Given** `PO-2026-2001` line 1 is ordered **₹50,00,000.00**, received **₹35,00,000.00**, billed **₹30,00,000.00**.
- **When** the reconciliation run executes.
- **Then** the row shows ordered **₹50,00,000.00**, billed **₹30,00,000.00**, open commitment **₹20,00,000.00**, received but unbilled **₹5,00,000.00**, released residual **₹0.00**.
- **And** the identity **ordered = billed + open commitment + released residual** holds at **₹0.00**.
- **And** the exposure identity **Exposure = Open PO Commitment + Actual CWIP** holds at budget-head and project level at **₹0.00** against the sum of the underlying ledger rows.

#### AC-66 — Reconciliation exceptions surface with both values (US-66)
- **Given** a deliberately corrupted bill line makes the control layer's value differ from Zoho's by **₹2,500.00** against a tolerance of ₹0.00.
- **When** the reconciliation run executes.

### 37.13 Cross-cutting acceptance criteria

These apply to every screen and every code path. Visual, accessibility and responsive criteria are specified in §50 UI Acceptance Criteria and are not duplicated here.

| # | Criterion | How it is tested |
|---|---|---|
