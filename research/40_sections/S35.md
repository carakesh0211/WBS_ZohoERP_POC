## 35. POC Scope

### 35.1 What this section fixes

This section fixes the boundary of the proof of concept: for each of the 36 demonstration steps mandated by the brief, what is actually built, what is replaced by a controlled mock and why, and the single observable signal that proves the step passed. It is written so that a coding agent can implement the POC without reinterpreting a business rule.

Three rules govern everything below.

1. **A step is only "demonstrated" if a named person can see a named number on a named screen.** Every acceptance signal in §35.5 names a screen from `C8_screens.json`, a value, and where the value comes from.
2. **Nothing is mocked for convenience.** Every mock in §35.4 is justified either by a proven absence in the Zoho ERP OpenAPI specification, or by the brief's own permission to mock where live credentials are unavailable (step 24). Mocks introduced for any other reason are out of order.
3. **The seed data is the state immediately *before* step 1 runs.** Steps that mutate data — the PO amendment (step 14), the PO cancellation (step 15), the budget revision (step 16) and the capitalisation (steps 19–20) — act on seeded records and produce a post-state. §38 Sample Data gives both the seed value and the post-demonstration value for every record the demonstration touches.

**Provenance warning.** Steps 2, 23–29 and 32 exercise capability that has no basis in the client document. The client PDF contains no WBS hierarchy at all — its budget structure is CAPEX/CWIP project code plus budget head only (CONF-02) — and its complete statement on integration mechanics is a single architecture line (CONF-07). These steps are `provenance=MASTER-PROMPT` and must never be presented to Atha Group as confirmed client requirements.

### 35.2 The demonstration environment

| Component | POC form | Why |
|---|---|---|
| Control Hub application | Real. Web client plus Control API plus the three ledgers (Budget Ledger, Commitment Ledger, Actual Ledger), per §12 Recommended Architecture | It is the thing being proved |
| Control Hub database | Real, seeded from §38 Sample Data | The seed is the demonstration script's starting position |
| Zoho ERP organisation | Two connection profiles. **Profile A** points at a live Zoho ERP organisation where credentials exist. **Profile B** points at the Zoho ERP Simulator | Satisfies the two-organisation acceptance criterion in §14 without requiring two paid tenants |
| Zoho ERP Simulator | A controlled mock that serves the exact request and response shapes of the endpoints listed in §17 Zoho ERP Endpoint Inventory, backed by the same seed data | Makes the demonstration deterministic and repeatable, and makes rate-limit and failure injection possible without abusing a live tenant |
| Identity | Eleven named demonstration users, one per role exercised (§35.6) | Approval routing and permission denial are only demonstrable with distinct identities |

**The Simulator is a fixture, not a product.** Its only contract is that a request the Control Hub sends to Profile B is byte-identical to the request it would send to Profile A. If a request would not be valid against the real API, the Simulator must reject it. This is what makes "mocked" defensible: the client code path is the production code path.

**Base path resolution.** The Simulator must reproduce the two-root split: 64 of 78 modules are served from `https://www.zohoapis.in/erp/v3` and 14 from `https://www.zohoapis.in/erp/v1` (OAS-01). A single hard-coded base path in the connector is a POC defect, not a shortcut.

### 35.3 Mock strategy

Six mock classes, applied per step in §35.4.

| Code | Meaning |
|---|---|
| `HUB` | Runs entirely inside the Control Hub. No Zoho ERP call. Nothing is mocked because nothing crosses the boundary. |
| `LIVE` | Runs against a real Zoho ERP organisation over an endpoint confirmed in the vendor specification. |
| `LIVE/SIM` | Runs live on Profile A where credentials exist; otherwise identically against the Simulator on Profile B. The brief permits this explicitly at step 24. |
| `SIM` | Runs against the Simulator in the POC by design, with the reason stated. |
| `HUB+SIM` | The Hub owns the record; the Simulator stands in for the Zoho counterpart. |
| `MANUAL` | A human action in the Zoho ERP user interface that no API can perform, then discovered by the connector. |

The seven things that are mocked, and the evidence that forces each:

| # | What is mocked | Class | Why it must be, or may be, mocked |
|---|---|---|---|
| K1 | Zoho Purchase Request | Not mocked — **replaced** | Purchase Request does not exist anywhere in the official ERP API specification: zero matching paths, zero matching modules, zero matching scopes across all 78 modules, 561 paths and 163 scopes (OAS-02). It is a mechanically proven clean negative. The Purchase Request is therefore built and owned by the Control Hub (CONF-01). There is nothing to mock because there is nothing to call. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` |
| K2 | OAuth authorisation code exchange | `LIVE/SIM` | Step 24 states the permission verbatim: complete OAuth authorisation *or demonstrate the full flow using a controlled mock where live credentials are unavailable*. The Simulator serves the token endpoint shape `POST https://accounts.zoho.in/oauth/v2/token?refresh_token=…` `[source: https://www.zoho.com/erp/api/v3/oauth/ — verified 2026-08-05]` |
| K3 | Purchase Receive retrieval | `HUB+SIM` | Purchase Receive exposes only `POST /purchasereceives`, `GET /purchasereceives/{purchasereceive_id}`, `PUT` and `DELETE`. There is **no list endpoint**, receipt lines carry **no** `purchaseorder_item_id`, and receipt lines carry no project, tag or custom-field coding (OAS-03). Received-but-unbilled exposure therefore cannot be derived from Zoho at all and is reconstructed in the Control Hub from the receipt identifier captured at creation. |
| K4 | Custom-field definitions on Purchase Order, Bill and Journal | `MANUAL` | There is no API to create a custom field **definition**; the only custom-field paths are value-setting paths on eight modules (OAS-06). In the POC these are pre-created in the Simulator's metadata and, on Profile A, created by hand once. This is a documented go-live prerequisite, not a POC shortcut. |
| K5 | Rate-limit responses | `SIM` | The documented limit is 100 requests per minute per organization `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`, with a concurrent soft limit of 10 calls for all plans and 5 for Trial plans `[source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05]`. Deliberately exhausting a live tenant's quota to prove backoff works is destructive; the Simulator returns the throttled response on demand. |
| K6 | Webhook delivery | **Not used in the POC** | No webhook framework exists in the ERP REST API. Zoho ERP webhooks are configured in the user interface and no API creates or lists them. Polling is the only ingestion mechanism in the POC (CONF-16). Step 30/31 therefore poll; they do not wait for an event. |
| K7 | Outbound CAPEX/WBS reference push (step 32) | `LIVE/SIM` | The write path is real — `PUT /purchaseorders` with `X-Unique-Identifier-Key` / `X-Unique-Identifier-Value` upsert, and `PUT /purchaseorder/{purchaseorder_id}/customfields`. It is run against the Simulator by default so that a demonstration does not mutate a live tenant's purchase order. `[source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399… — verified 2026-08-05]` |

**One thing that is emphatically not mocked.** The budget arithmetic. Every number on every screen in the demonstration is computed by the Control Hub from the seeded ledgers using the formulas in §22 Budget and Commitment Calculation Logic. No figure in the POC is a hard-coded display value. The frozen worked examples in §38 are seed inputs, not display constants.
