## 16. Zoho ERP API Capability Matrix

### 16.1 Basis of assessment

This section answers one question per business object: **what can the CAPEX and CWIP Control Hub actually do against Zoho ERP through its published API, and how confident are we?** Section 17 Zoho ERP Endpoint Inventory carries the operation-by-operation detail. This section carries the verdicts.

Every assessment below is derived from the Zoho ERP official OpenAPI bundle `openapi-all.zip`, sha256 `E95A039969F5C2FC2A44C47CFF77E41BACFF18957DCA1C870D48DDDA15C447F8`, downloaded 2026-08-05 [source: Zoho ERP OpenAPI bundle openapi-all.zip, sha256 E95A0399... — verified 2026-08-05]. The bundle contains **869 operations, 561 distinct paths, 163 distinct OAuth scopes, across 78 modules**.

Three consequences of that basis, stated plainly because they change how the matrix should be read:

1. **The negatives in this section are proven, not merely unfound.** A documentation search cannot establish that something does not exist; enumerating a complete vendor specification can. Where this section says a capability is absent, all 78 modules, 561 paths and 163 scopes were searched.
2. **CONF-04 is closed by the method, not by argument.** CONF-04 required each endpoint to be recorded as VERIFIED-ERP, VERIFIED-BUT-DOCUMENTED-ONLY-FOR-BOOKS-OR-INVENTORY, or NOT-FOUND, because the master prompt's baseline endpoint list is path-for-path the recognisable Zoho Books and Zoho Inventory surface. Because every row in this matrix originates in the **Zoho ERP** specification bundle rather than in a Books or Inventory page, every capability asserted here is **VERIFIED-ERP**. No path in this blueprint is carried across from another Zoho product on the assumption of path equivalence.
3. **The client PDF asserts nothing about APIs.** Its section 10 labels — Standard, Configuration, Customization — are product and effort classifications, not API-availability statements. No row of the client document is cited anywhere in this section as evidence that an endpoint exists. This matters most for REQ-INT-001, Purchase Request, and is dealt with in 16.2 and 16.9.

**Legend used throughout section 16**

| Symbol | Meaning |
|---|---|
| **Y** | Capability is present in the vendor specification |
| **N** | Capability is absent from the vendor specification. Mechanically established across all 78 modules |
| **N (load-bearing)** | Absent, and the absence changes the architecture. Every one of these is expanded in 16.9 |
| n/a | The concept does not apply to this object — for example line-level coding on an object with no line array |
| UNVERIFIED - REQUIRES ZOHO CONFIRMATION | The specification neither confirms nor denies it. Listed in 16.10, never assumed either way |

### 16.3 Line-level coding-carrier matrix

This is the single most consequential table in the integration design. A CAPEX Project code and a Budget Head have to travel on a transaction line, because that is the only granularity at which budget control is meaningful — a purchase order can legitimately carry Civil lines and Plant & Machinery lines at once.

**There is no field named `capex`, `wbs`, `budget` or `cost_centre` anywhere in the Zoho ERP specification.** The code must therefore ride on one of three existing carriers. This table states which carriers each transaction object supports.

| Transaction object | Carrier A: line `project_id` | Carrier B: line reporting `tags` | Carrier C: line `item_custom_fields` | Header fallback | Recommended carrier for CAPEX code | Recommended carrier for Budget Head |
|---|---|---|---|---|---|---|
| Purchase Order line | **Y** | **Y** | **Y** | header `custom_fields`, header `tags`, header `location_id` | Line `project_id` — it is a real foreign key to a Zoho project, so it cannot be mistyped | Line reporting tag option — a controlled vocabulary maintained from the Budget Head register |
| Bill line | **Y** | **Y** | **Y** | header `custom_fields` only — **header carries no `project_id`** | Line `project_id` | Line reporting tag option |
| Vendor Credit line | **Y** | **Y** | **Y** | header `custom_fields` | Line `project_id` | Line reporting tag option |
| Journal line | **Y** | **Y** | **N** | header `custom_fields`, header `tags`, header `location_id` | Line `project_id` | Line reporting tag option |
| Expense line | **N** | **Y** | **N** | header `project_id` **and** header `tags` | **Header `project_id`** — an expense is a single-project document in this design | Line reporting tag option |
| **Purchase Receive line** | **N** | **N** | **N** | header `custom_fields`, header `receive_number` | **None available** — the receipt inherits its coding from the PO line it is derived from, and that derivation is performed and stored by the Control Hub | **None available** |

**Evidence for the carriers.** Reporting tags are applicable at line level: `preference string Preference type. Currently, only 'transaction' and 'line_item' is supported for this node.` [source: https://www.zoho.com/erp/api/v3/reporting-tags/ — verified 2026-08-05]. The entities that can be tagged are `entity_name string Entity Name. Possible Values: Sales - sales, Purchases - purchases, Journal - journals, Inventory Adjustment - inventory_adjustment` [source: https://www.zoho.com/erp/api/v3/reporting-tags/ — verified 2026-08-05]. Note what that list does **not** contain: purchase receives. The tag surface and the receipt-line schema agree with each other, which is why the Purchase Receive row is empty in all three carrier columns rather than merely undocumented.

**Three binding rules follow, and the field-mapping workbench in section 19 must enforce them:**

1. **Map at line level, never at header level.** Finding OAS-10 established that the bill header carries no `project_id` while the bill line does. A design that codes CAPEX at header level works on purchase orders, silently fails on bills, and produces a CWIP figure that is wrong in a way no reconciliation will catch, because both sides will agree with each other.
2. **Expenses are the exception, and must be handled as one.** The expense *line* carries `tags` but not `project_id` and not `item_custom_fields`; the expense *header* carries both `project_id` and `tags`. An expense is therefore a single-CAPEX-Project document in this design. If Atha Group needs one expense split across two CAPEX Projects, it must be entered as two expenses. That is a stated functional constraint to confirm with the client, not a workaround to discover during build.
3. **The Purchase Receive carries no coding and never will.** Its CAPEX attribution is derived by the Control Hub from the purchase order it was raised against, and that derivation is stored in GRN Reference and GRN Line. It cannot be recovered from Zoho ERP afterwards.

**Carrier selection is a client decision, not a technical one.** All three carriers work on purchase orders, bills, vendor credits and journals. The recommendation above prefers `project_id` for the CAPEX code because it is referentially enforced, and reporting tags for the Budget Head because tag options give a controlled vocabulary that Zoho itself validates and that Zoho Analytics can slice natively — which matters given that REQ-INT-013 and REQ-INT-017 place the management dashboard in Zoho Analytics. Provenance of the recommendation: DERIVED-RECOMMENDATION. Confirm with the client before the field-mapping workbench is configured, because changing the carrier after transactions exist requires re-coding history.

| Vendor Payment | Y, paginated, filterable | **Y** | Incremental cursor, hourly | Low volume | Cursor |

**Seven of twenty-one objects support a true incremental cursor.** They are, without exception, the transactional objects that drive the numbers — purchase orders, bills, vendor credits, vendor payments, journals — plus the two accounting masters, chart of accounts and taxes. That is a fortunate distribution: the high-volume objects are cheap to poll and the expensive-to-poll objects are low-volume. The two exceptions are the two load-bearing negatives, and both of them sit at the capitalisation end of the lifecycle rather than the procurement end.

### 16.5 Write capability and direction of authority

Capability is not permission. Zoho ERP exposes write on almost everything in scope; this design enables it on very little. The principle, carried through from section 13 Source-of-Truth Matrix, is that **Zoho ERP remains the accounting and procurement system of record** and the Control Hub owns budget, commitment and control.

| Business object | Write capability in the API | Enabled by this design | Direction of authority | Rationale |
|---|---|---|---|---|
| Purchase Order | Create, update, submit, approve, reject, status transitions | **Create and update enabled** | Control Hub raises, Zoho ERP owns | The approved Purchase Request must become a real Zoho purchase order — that is REQ-PO-002. Zoho keeps the number series (`ignore_auto_number_generation` left false) |
| Project | Create, update, upsert via `X-Unique-Identifier-Key` | **Create and update enabled** | Control Hub raises, Zoho ERP owns | The Zoho project is the anchor for line-level `project_id` coding. Budget fields are deliberately not written |
| Reporting Tag option | Create, update, activate, deactivate | **Conditionally enabled** | Control Hub raises, Zoho ERP owns | Only when reporting tags are the selected Budget Head carrier |
| Purchase Receive | Create, update | **Create enabled** | Control Hub raises, Zoho ERP owns | Not for preference but for necessity — see 16.9. A receipt created in the Zoho UI cannot be found again through the API |
| Journal | Create, publish, reverse, submit, approve | **Create, publish and reverse enabled** | Control Hub raises, Zoho ERP owns | The CWIP-to-asset transfer is a Control Hub-originated posting (REQ-CAP-001). Two-phase: create draft, then publish |
| Fixed Asset | Create, update, status transitions | **Create enabled** | Control Hub raises, Zoho ERP owns | Capitalisation creates the asset. The returned `fixed_asset_id` must be persisted immediately |
| Bill | Create, update, submit, approve, void | **Not enabled** | Zoho ERP owns outright | Accounts payable enter bills in Zoho ERP. A budget-control application must not be able to create a liability |
| Vendor Payment | Create, update, refund | **Not enabled** | Zoho ERP owns outright | The Control Hub never moves money. This is structural, enforced by the connector allow-list, not a matter of user permissions |
| Contact (vendor) | Create, update, bulk update | **Not enabled** | Zoho ERP owns outright | Two systems creating vendors produces duplicate vendor master |
| Item | Create, update, bulk update | **Not enabled** | Zoho ERP owns outright | Same reason |
| Chart of Accounts | Create, update, activate, deactivate | **Not enabled** | Zoho ERP owns outright | GL account creation is a controlled finance activity. Automating it would let the Control Hub redefine what counts as CWIP |
| Tax, Currency, Location, Department, User, Organization | Create and update all present | **Not enabled** | Zoho ERP owns outright | Statutory and administrative configuration |
| Any object | Delete | **Never enabled, on any object** | n/a | REQ-SEC-001 requires an audit trail from budget approval to capitalisation. Corrections are made by void, cancel or reversal — all of which exist — never by deletion |

**Delete is disabled globally and that is a design commitment, not an oversight.** The specification exposes DELETE on nineteen of the twenty-one modules in scope. The connector allow-list denies all of them.

### 16.6 Lifecycle and approval capability

CONF-21 records a genuine ambiguity in the client document: section 3 step 6 says the approved purchase order "reserves/commits the budget", conflating creation with approval, while section 8's first commitment position is labelled "PO approved". The document never says whether a draft purchase order consumes budget. The researchable half of that question is now answered.

| Question from CONF-21 | Specification answer | Evidence |
|---|---|---|
| Does a Zoho ERP purchase order carry a draft and approval status model? | **Yes.** The list endpoint accepts a `status` filter, and three status-transition endpoints exist: `/status/open`, `/status/billed`, `/status/cancelled` | OpenAPI bundle, `purchase-order` module |
| Are submit, approve and reject exposed as API actions? | **Yes.** `POST /purchaseorders/{purchaseorder_id}/submit`, `/approve` and `/reject` all exist | OpenAPI bundle, `purchase-order` module |
| Is last-modified filtering available for incremental pull? | **Yes.** `last_modified_time` is a documented list query parameter | OpenAPI bundle, `purchase-order` module |
| Can the Control Hub therefore detect the exact moment of commitment? | **Only to within one poll interval.** There is no push mechanism the Control Hub can provision itself — see 16.7 | Findings OAS-01 to OAS-11 and the webhook evidence in 16.7 |

**Approval-action capability across the objects that have a lifecycle:**

| Object | Submit | Approve | Reject | Status transitions available | Used by this design |
|---|---|---|---|---|---|
| Purchase Order | Y | Y | Y | `open`, `billed`, `cancelled` | Commitment is recognised on status becoming open or approved; released on `cancelled` |
| Bill | Y | Y | **N** | `void`, `open` | Actual CWIP recognised on open; reversed on `void` |
| Vendor Credit | Y | Y | **N** | `open`, `void` | Negative actual recognised on open |
| Journal | Y | Y | Y | `publish` | Capitalisation journal created as draft, then published as a second call |
| Fixed Asset | N | N | N | `active`, `cancel`, `draft` | Asset created, then activated |
| Project | N | N | N | `active`, `inactive` | Project status mirrored from the CAPEX Project lifecycle |
| Everything else in scope | N | N | N | `active` / `inactive` on masters only | Not used |

**The residual control limitation, stated rather than buried.** Commitment is recognised when the Control Hub *observes* the purchase order reaching open or approved status, not when the transition occurs in Zoho ERP. With a 15-minute delta poll the maximum detection latency is 15 minutes plus one poll duration. During that window budget is consumed in Zoho ERP and not yet visible in the Control Hub, so an availability check run in that window can approve a transaction that should have been routed to exception. This is quantified here and must be presented to the client as a stated control limitation with three mitigations available: shorten the poll interval (cost: API budget), configure a Zoho workflow webhook to trigger an immediate re-read (cost: manual configuration, see 16.7), or require that capital purchase orders be raised only through the Control Hub, in which case the Control Hub knows first by construction. The third is the recommendation.

### 16.7 Event and webhook capability

CONF-16 records an internal inconsistency in the master prompt: parts of it presuppose webhooks exist, other parts forbid assuming they do. The evidence resolves it, and the resolution is neither "yes" nor "no" but a specific shape.

| Capability | Status | Evidence |
|---|---|---|
| Webhook management API in the ERP REST surface — create, list, update, delete a webhook | **N (load-bearing).** No webhooks, events, notifications, subscriptions or callbacks page exists in the ERP REST API. Four independent probes, including a DOM re-enumeration of the API navigation returning 84 unique top-level pages, and direct URL probes returning HTTP 404 | [source: https://www.zoho.com/erp/api/v3/introduction/ — verified 2026-08-05] |
| Webhooks as a product feature | **Y**, as a workflow ACTION configured only in the Zoho ERP UI: "Webhooks are user-defined HTTP & HTTPS callbacks that are triggered when a particular event occurs at the source site." | [source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05] |
| Outbound method | PUT, POST or DELETE. "By default, the system selects the POST method." No GET option | [source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05] |
| Payload format | "You can choose from Default Payload, x-www-form-urlencoded, and Raw body parameters." | [source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05] |
| Schema of the Default Payload | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** | Not documented on the vendor page |
| Signature or secret verification | **Y.** A secret token, "alphanumeric and range between 12 - 50 characters", which "cannot be edited or viewed once the webhook is created" | [source: https://www.zoho.com/en-in/erp/help/automation/workflow-actions/webhooks.html — verified 2026-08-05] |
| Delivery guarantee, retry behaviour, ordering | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** | Not documented |

**Design consequences, and they are not negotiable:**

1. **Scheduled polling is the correctness guarantee; webhooks are an accelerator.** The Control Hub must produce a correct budget position with every webhook disabled. Any design in which a missed webhook produces a permanently wrong commitment figure is rejected.
2. **Webhook endpoints cannot be provisioned as code.** Like custom fields, they are a manual Zoho ERP UI prerequisite, performed once per organisation and recorded as a named handover item in the setup wizard.
3. **Inbound webhooks are treated as a hint, not as data.** Because the Default Payload schema is undocumented, the Control Hub must not parse business values out of it. The correct handling is: verify the secret token, extract only the record identifier, then issue an authenticated `GET` for the record and trust that. This also makes the duplicate-webhook and out-of-order cases trivially safe.
4. **The test case is restated.** Per CONF-16's treatment, "Duplicate webhook" becomes **"Duplicate inbound event (webhook or repeated poll)"**, so the scenario remains valid whether or not webhooks are configured at Atha Group.

| PO cancellation releases commitment | REQ-PO-009 | `POST /purchaseorders/{purchaseorder_id}/status/cancelled` and the `status` list filter | **Supportable** | Control Hub closes commitment rows on observing status `cancelled` |
| Purchase Receive and partial GRN tracking | REQ-GRN-001, REQ-ALT-005 | **No list endpoint; receipt lines carry no PO-line link and no coding** | **Not supportable through Zoho ERP alone** | Control Hub reconstructs it, and must originate receipts to hold their identifiers |
| CWIP GL posting | REQ-PRJ-015, REQ-INT-007 | Chart of accounts readable and incrementally pollable; bill and journal lines carry `account_id` | **Supportable** | Control Hub holds the CWIP account allow-list; Zoho posts the entries |
| Asset capitalisation | REQ-CAP-001, REQ-CAP-003 | Asset creation and journal posting both exist; **no link field from asset to project, PO or bill** | **Partially supportable** | Posting works. Traceability is anchored on the Control Hub Capitalisation Request, which becomes a mandatory record |
| Budget revision with version history | REQ-REV-001 to REQ-REV-007, REQ-SEC-003, REQ-SEC-004, REQ-INT-011 | No budget object, therefore no revision object | **Not supportable through Zoho ERP** | Entirely Control Hub |
| Exception and overrun approval | REQ-REV-002, REQ-INT-012 | Approval actions exist on purchase orders, bills, vendor credits and journals, but there is **no API to configure an approval matrix** | **Partially supportable — UNVERIFIED, see 16.10** | Control Hub owns the CAPEX approval matrix; Zoho approval actions are invoked, not configured |
| Management dashboard | REQ-RPT-001 to REQ-RPT-006, REQ-INT-013, REQ-INT-017 | Out of scope for this matrix — the client PDF assigns dashboards to Zoho Analytics | See section 34 Reporting and Dashboard Catalogue, and CONF-08 | Control Hub and Zoho Analytics |
| Audit trail end to end | REQ-SEC-001, REQ-SEC-005 | Zoho exposes per-record comment and attachment endpoints but no cross-object audit query | **Supportable only in the Control Hub** | Audit Log and Connector Audit Log are Control Hub entities |
| Bidirectional connection via API and webhook | REQ-INT-015 | API: yes. Webhook: exists as a UI-configured workflow action with no management API | **Supportable, with webhooks as a manual prerequisite** | See 16.7 |

**The pattern is consistent and worth stating once.** Zoho ERP supplies transactions with enough line-level structure to be attributed to a CAPEX Project and a Budget Head. It supplies no budget, no commitment, no availability control and no revision history. Every requirement that involves *controlling* spend lands in the Control Hub; every requirement that involves *recording* spend stays in Zoho ERP. That division is not a preference — it is what the specification permits.

### 16.9 The load-bearing negatives, expanded

Four absences change the architecture. Each is stated with what was searched, what was found, and what it costs.

| # | Absence | What was searched | Consequence | Cost if ignored |
|---|---|---|---|---|
| 1 | **Purchase Request has no API** (OAS-02) | All 78 modules, 561 paths, 163 scopes, for purchase-request, purchaserequest, requisition and PR | The Purchase Request is a Control Hub-owned entity. REQ-INT-001 classifies it as Standard in the client PDF; that is correct at product level and irrelevant at API level. This is CONF-01, surfaced not resolved | A build plan that assumes a Zoho Purchase Request API loses the entire pre-approval control point — the place where REQ-BUD-004's availability check actually happens |
| 2 | **Purchase Receive cannot be listed, and its lines carry no coding and no PO-line link** (OAS-03) | `purchasereceives` module enumerated in full; four operations exist, none of them a list | Received-but-unbilled exposure is reconstructed by the Control Hub. Receipts should be originated from the Control Hub so their identifiers can be held. A receipt created in the Zoho ERP UI is invisible until it surfaces in the PO position or a bill | REQ-ALT-005, pending GRN and billing, degrades to inference. A `purchasereceive_id` lost to a timeout is unrecoverable and a blind retry creates an undetectable duplicate receipt |
| 3 | **No API creates a custom-field DEFINITION** (OAS-06) | All eight `customfield` paths in the bundle; every one sets values on an existing record | The CAPEX and WBS custom-field layout is a **manual Zoho ERP UI prerequisite per organisation**, then discovered by the connector. It becomes a blocking step in the setup wizard and a named handover item | An implementation plan that assumes field provisioning is automatable underestimates onboarding and produces a connector that fails on a fresh organisation with an unhelpful error |
| 4 | **Fixed assets carry no source link and cannot be incrementally synced** (OAS-09) | Fixed-asset create body and list parameters enumerated field by field | Capitalisation traceability is anchored on the Control Hub Capitalisation Request — there is no other anchor. Asset sync is full refresh | If the Capitalisation Request is not treated as a permanent record, the trace from a fixed asset back to the CWIP that funded it is lost and cannot be rebuilt from Zoho ERP |

A fifth absence sits just below these in impact and is recorded here because it is routinely assumed away: **there is no webhook management API** (16.7). Webhook provisioning joins custom-field provisioning as manual setup work.

### 16.10 Capability items that remain UNVERIFIED

The specification is authoritative about what it contains. It is silent on the items below, and silence is not evidence either way. Each is carried into section 44 Open Questions and must be resolved with Zoho or with Atha Group before the corresponding design element is treated as settled.

| # | Item | Why it matters | Status |
|---|---|---|---|
| 1 | Schema of the webhook **Default Payload** | Decides whether an inbound event can be parsed at all. The design already assumes it cannot, and re-reads the record instead, so a negative answer costs nothing | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 2 | Webhook **delivery guarantee, retry behaviour and ordering** | Decides how much the Control Hub can lean on events. The design already assumes none of them | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 3 | Whether the **rate limit of 100 requests per minute per organisation** applies identically to `/erp/v1` modules | Affects only `departments` in this scope, a trivial-volume module, so the practical risk is low | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 4 | Whether a custom field created in the Zoho ERP UI **appears automatically in API responses** for that object, and under what key | Decides whether the connector can discover the CAPEX custom-field layout after the manual prerequisite is performed. If it cannot, the carrier choice must fall back to `project_id` or reporting tags | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 5 | Whether Zoho ERP's **approval workflow can be configured through any API**, as opposed to invoked | REQ-INT-002 classifies PR/PO approval as Standard or Configuration. Approval *actions* are confirmed to exist; approval *matrix configuration* is not evidenced anywhere in the bundle | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 6 | Whether `receive_number` on a purchase receive is **unique and enforced** | Would give a weak recovery route for a lost `purchasereceive_id` — weak because there is still no endpoint to search on it | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 7 | Allowed values of `filter_by` on the **fixed-asset list** | Would allow the nightly full refresh to be narrowed. Does not change the full-refresh conclusion, only its cost | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 8 | Whether purchase order **status transitions enforce an approval workflow** or can be invoked directly | Decides whether the Control Hub can move a purchase order to open without Zoho-side approval, which affects the commitment-recognition trigger in 16.6 | **UNVERIFIED - REQUIRES ZOHO CONFIRMATION** |
| 9 | Whether a **draft purchase order consumes budget** in Atha Group's intended process | CONF-21. Not an API question at all — a client decision. The blueprint's default is that commitment is recognised at open or approved status, not at draft | **UNVERIFIED - REQUIRES CONFIRMATION** (client) |
| 10 | Whether a **capital advance** should reduce Available Budget | CONF-15 territory. No `is_advance` flag exists (OAS-11), so both the classification rule and the control treatment are Control Hub decisions | **UNVERIFIED - REQUIRES CONFIRMATION** (client) |

None of the ten blocks the POC. Items 4, 5 and 8 should be answered before the production connector is hardened; items 9 and 10 should be answered before the availability-check logic in section 22 is signed off.

### 16.11 Summary verdict

| Dimension | Verdict |
|---|---|
| Can Zoho ERP be read reliably enough to compute Open PO Commitment? | **Yes.** Purchase order lines are paginated, filterable, incrementally pollable and line-coded |
| Can Zoho ERP be read reliably enough to compute Actual CWIP? | **Yes.** Bill lines carry `purchaseorder_item_id`, `project_id`, `tags`, `account_id` and `item_custom_fields`. Vendor credits and expenses complete the picture |
| Can commitment-to-actual conversion be done without double counting? | **Yes**, against documented fields, on the PO-to-bill leg |
| Can received-but-unbilled be derived from Zoho ERP? | **No.** It is reconstructed by the Control Hub |
| Can budget, availability control and revision live in Zoho ERP? | **No.** No budget object of the required shape exists |
| Can the Purchase Request live in Zoho ERP? | **No API exists.** It lives in the Control Hub |
| Can capitalisation be posted to Zoho ERP? | **Yes**, as a journal with WBS-coded lines, plus a fixed-asset create |
| Can capitalisation be traced back from the asset using Zoho fields? | **No.** The Control Hub Capitalisation Request is the only anchor |
| Can the integration be provisioned entirely as code? | **No.** Custom-field definitions and webhooks are manual UI prerequisites |
| Is any endpoint in this blueprint carried across from Zoho Books or Zoho Inventory? | **No.** Every path originates in the Zoho ERP specification bundle. CONF-04 closed |
